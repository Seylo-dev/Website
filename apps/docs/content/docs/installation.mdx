## Requirements

| What | Needs |
| --- | --- |
| System | Linux with systemd, x86-64 (amd64) or ARM64. Ubuntu 22.04 and 24.04 and Debian 12 are tested; RHEL, Rocky, AlmaLinux and CentOS 9 and Fedora 40 or newer should work. |
| Kernel | Linux 5.6 or newer, with cgroup v2 |
| Docker | Docker Engine 23 or newer (25 or newer recommended), installed from Docker's packages with a `docker.service` unit, and the buildx plugin (`docker-buildx-plugin`, part of Docker's packages) on nodes that build. The snap package does not work. When Docker is missing, the installer installs it for you. Docker 28 or newer is best on the panel server if you close its IP address (see [Serve on IP address](/self-hosting/the-panel#serve-on-ip-address)). |
| Ports | 80 and 443 for your sites, 3000 for the panel until it has a domain, and 3443 on the panel server for other nodes' agents. See [Firewalls](#firewalls) for the rest. |
| Tools | OpenSSL 3 or `minisign`, to check the release signature. Current distributions ship OpenSSL 3. |
| Memory | 1 GB works for a small panel node; 2 GB or more is recommended once you build images on it |

Run the installer as root on a server you reach over SSH. A fresh VPS is the easy case. A server that already runs other containers is fine too: Seylo only lists, changes or removes what it created itself.

## Install

<Steps>
<Step>

### Run the installer

```bash
curl -fsSL https://install.seylo.dev | sudo sh
```

New in 0.2.6: run from a terminal without arguments, the installer first asks what this server should do:

```text
What should this server do?
  1) Set up a new Seylo panel here (this server becomes its first node)
  2) Join this server to a Seylo panel you already have
```

**1** (or Enter) sets up a panel, as below. **2** asks for the join command from the panel's **Nodes → Add node**: paste it whole (the installer only reads its `--panel`, `--token`, `--pin` and `--version`, it never runs it), or paste the panel's address and then the token. See [Join a server](/guides/adding-nodes#join-a-server). A run that names a mode (`panel`, `join`, `uninstall`) or passes `--panel` or `--token`, or that has no terminal, asks nothing.

Setting up a panel, the installer makes this server its first node. It:

1. checks the system (Linux, systemd, CPU architecture),
2. checks that ports 80 and 443, the panel's port (3000) and the agents' TLS port (3443) are free, and stops if another program holds one of them (nginx or Apache, for example), before it changes anything,
3. downloads the release manifest and checks its signature with OpenSSL 3 or `minisign`; it stops if the signature is wrong or neither tool is there,
4. checks Docker, and installs it with the official script from get.docker.com when it is missing, without asking (new in 0.2.1, see [Docker](#docker)). It refuses snap Docker, Docker without a `docker.service` unit and Docker older than 23, and turns on Docker's live-restore so services keep running while Docker restarts (see below),
5. downloads the `seylo` binary, checks its SHA-256 against the signed manifest and installs it to `/usr/local/bin/seylo`,
6. writes the `seylo.service` systemd unit,
7. opens ports 80, 443, the panel's port and the agents' TLS port in ufw or firewalld when one of them is active,
8. starts the panel container, pinned to the image digest in the signed manifest, and joins this server to it as a node.

It starts with one line that names the release and what the run does, such as `Seylo 0.2.1 installer - the panel and a node on this server`, and ends with a block that holds the link to create the owner account:

```text
==> Starting the panel
Starting the panel (ghcr.io/seylo-dev/seylo:0.2.1@sha256:...)...

╭────────────────────────────────────────────────────────────────────────
│ The panel is running. Open this link to create the owner account:
│
│   http://203.0.113.10:3000/setup?t=seylo_setup_...
│
│ It works once, within an hour (until 21:34 UTC).
│ If 203.0.113.10 is not this server's public address, use the public one
│ with the same path.
│ Tip: the panel uses plain HTTP until it has a domain. Add one in the
│ setup wizard to switch to HTTPS.
│
│ Next: open it in a browser, create the owner account and follow the
│ setup wizard.
│ A new link when this one expires: seylo panel setup-link
│ Docs: https://docs.seylo.dev
╰────────────────────────────────────────────────────────────────────────
```

New in 0.2.1: on a terminal the output has colors, check marks and that framed block. `NO_COLOR=1` turns the colors off. In a log, a pipe or CI it stays plain text, with `+`, `|` and `-` for the frame and every sentence on one line. The block counts the warnings printed above it, if there were any. The 0.2 installer printed the link with three lines of warning about plain HTTP under it, and 0.1 the link alone.

</Step>
<Step>

### Create the owner account

Open the link. It works once and expires after one hour. Create the owner with an email and a password (at least 10 characters), or with **Continue with GitHub** when the panel offers it: GitHub sign-in uses the device flow, like `gh auth login`, so you type a short code on github.com and nothing has to be configured on the panel first.

Setup then asks for a few optional things, each of which you can skip and change later in **Settings**:

- **Panel domain**: a hostname for the panel itself, with HTTPS. Without one, the panel stays on `http://<server-ip>:3000`, unencrypted (see below).
- **Node wildcard domain**: see the next step.
- **First project**: a group for your first services.

If the link expired before you used it, run this on the server to get a new one:

```bash
seylo panel setup-link
```

<Callout title="Plain HTTP until the panel has a domain">
On `http://<server-ip>:3000` the setup link, your password and your session cookie cross the network unencrypted. Browsers also send a cookie of `http://<server-ip>` to every port of that address, including a service someone else runs there. So set the **Panel domain** before you invite anyone. To stay off plain HTTP from the very first sign-in, open the link through an SSH tunnel instead: run `ssh -L 3000:127.0.0.1:3000 root@203.0.113.10` on your computer and open the same link with `http://127.0.0.1:3000` in place of `http://203.0.113.10:3000`.

Changed in 0.2.1: the installer and `seylo panel setup-link` print one tip under an `http://` link instead of a warning, and the setup and sign-in pages show nothing. Inside the panel, pages on plain HTTP show one line, **HTTPS is off until the panel has a domain.**, with **Set a domain** and the tunnel command under **More** (see [Give the panel a domain](/self-hosting/the-panel#give-the-panel-a-domain)).
</Callout>

</Step>
<Step>

### Point a wildcard at the node

One DNS record lets every service on this node get its own domain with HTTPS, with no further DNS work:

```text
*.de1.example.com   A   203.0.113.10
```

Then set `de1.example.com` as the node's **Wildcard domain** (on **Nodes**, or in the setup step). See [Domains and HTTPS](/guides/domains-and-https).

</Step>
</Steps>

<Callout title="Already running Wings?">
The agent detects Pelican or Pterodactyl Wings on the node. If that Wings build runs Traefik on ports 80 and 443, Seylo shares it instead of starting its own. See [Running next to Wings](/guides/running-next-to-wings).
</Callout>

## Installer options

Pass options after `sh -s --`:

```bash
curl -fsSL https://install.seylo.dev | sudo sh -s -- --port 8080 --name de1
```

| Option | What it does |
| --- | --- |
| `panel` | Install the panel and a node on this server (the default) |
| `join --panel <url> --token <t>` | Add this server to an existing panel; the panel's **Add node** dialog gives you the full command, with `--version` set to the panel's own release. See [Adding nodes](/guides/adding-nodes). |
| `uninstall [--purge]` | Remove the agent; see [Uninstall](/self-hosting/uninstall) |
| `--version <v>` | Install this release instead of the installer's own, checked against that release's signed manifest. `install.seylo.dev` serves the installer of the latest stable release; the join commands from **Add node** add `--version` with the panel's release. |
| `--downgrade` | Install the release although this node runs a newer one (new in 0.2, see below) |
| `--port <n>` | Port for the panel until it has a domain (default 3000) |
| `--agent-tls-port <n>` | Port where other nodes' agents reach the panel over TLS with a pinned key until it has a domain (default 3443; `0` turns it off) |
| `--image <ref>` | Panel image (default: the release's image, pinned by the digest in its signed manifest) |
| `--allow-unsigned` | Install a release without checking its signature, for development builds that have no release key |
| `--name <name>` | Node name shown in the panel (default: the hostname; a re-join keeps the current one) |
| `--can-build` | Only sets `can_build` in the joining node's `config.yml`. Whether the panel sends a node builds is chosen with **Build images on this node** in **Add node** when the join command is made (on by default since 0.2.1), and later on **Nodes**; the node can't change it (see [Join a server](/guides/adding-nodes#join-a-server)). |
| `--no-can-build` | Clear `can_build` in `config.yml` on a node that joins again. Without `--can-build` or `--no-can-build`, a re-join keeps the current setting. |
| `--pin <sha256:...>` | Panel certificate pin, for joining (the Add node command carries it) |
| `--insecure` | Join a panel at a plain `http://` URL on another server; the agent's traffic is then unencrypted |
| `--force` | Join again although this node already belongs to a panel (the node keeps its key, so the panel keeps the same node, and since 0.2 its other settings in `config.yml`); install the panel although another program holds 80 or 443 |
| `--no-docker-install` | Never install Docker; stop if it is missing. Without it, a missing Docker is installed (see [Docker](#docker)). |
| `--no-telemetry` | New in 0.2.4. Start the setup page with anonymous usage reports off; `SEYLO_TELEMETRY=off` or `DO_NOT_TRACK=1` in the installer's environment do the same (see [Telemetry](/self-hosting/telemetry)). |
| `--install-docker` | Also reinstall Docker with the script from get.docker.com when it is installed but does not start. Before 0.2.1: install Docker without asking when it is missing. |
| `--yes`, `-y` | The same as `--install-docker`; the installer asks nothing since 0.2.1 |
| `--data-dir <dir>` | Data folder (default `/var/lib/seylo`) |
| `--release-url <url>` | Download releases from a mirror of the GitHub releases page |
| `--binary <path>` | Install this binary instead of downloading one |
| `--dry-run` | Print what would be done and change nothing |
| `-h`, `--help` | Print the installer's help |

Running the installer again is safe: it updates the binary and the systemd unit and keeps the node's data and identity.

New in 0.2: it never installs an older release than the node runs. `install.seylo.dev` serves the latest stable release, so on a node whose agent (or, on the panel's node, the panel) runs a pre-release or a release the panel updated it to, the installer stops before it changes anything and names that release. Update nodes from the panel instead, re-run with `--version <that release>` to reinstall it, or add `--downgrade` to install the older one anyway. A `--binary` is installed as given.

### Docker

New in 0.2.1: when the server has no Docker, the installer installs it with the official script from get.docker.com, without asking, for a panel install and for a join alike. It says so as it starts. `--no-docker-install` makes it stop there instead.

A Docker that is installed but does not answer is started with `systemctl start docker`. If it still does not answer, the installer stops before it changes anything and points at `systemctl status docker` and `journalctl -u docker`: whatever stops this Docker (a broken `/etc/docker/daemon.json`, a masked unit) would stop a new one too. To reinstall it with get.docker.com anyway, add `--install-docker`; that replaces the distribution's `docker.io`, `containerd` and `runc` packages with Docker's own.

It still stops, with what to do, for snap Docker, Docker older than 23 and a distribution that get.docker.com does not support (it supports Ubuntu, Debian, Raspberry Pi OS, CentOS, Fedora and RHEL): install Docker by hand from [Docker's docs](https://docs.docker.com/engine/install/) and run the installer again.

### Without a terminal

New in 0.2.1: the installer asks nothing without a terminal, so it runs the same from cloud-init, automation, a CI job or `ssh` without `-t`, and a `join` command from **Add node** works as it is. The 0.2.6 menu only shows to a person at a terminal who named no mode; `SEYLO_NO_PROMPT=1` turns it off there too. `--yes` and `--install-docker` still work; they only matter for a Docker that does not start.

Installers before 0.2.1 asked whether to install a missing Docker. Without a terminal they stopped before installing anything and said to re-run with `--install-docker` (the v0.1.0 one stopped with `cannot create /dev/tty`). A join command from a 0.2.1 pre-release panel still runs that older installer, the latest stable one, so **Add node** says to add `--install-docker` at its end for a server without Docker.

### Exit status

New in 0.2.1: a join waits up to a minute for the agent's first connection and ends with a block that says whether it connected (see [Join a server](/guides/adding-nodes#join-a-server)). The exit status says what happened, for cloud-init, Terraform and scripts:

| Status | When |
| --- | --- |
| `0` | Installed. Also for a join that can't reach the panel yet: the agent keeps trying, and the join token stays valid for the rest of its hour. |
| `3` | A join the panel refused: a used or expired token, a wrong `--pin`, or a node that was removed or disabled. That command never works: make a new one in **Add node**. |
| `1` | Any other error. |

## Firewalls

When ufw or firewalld is active, the installer adds rules for what Seylo needs and prints what is left to you:

| Port | Who needs it | How it is served |
| --- | --- | --- |
| 80, 443 | Everyone: your sites | Traefik, published by Docker |
| 3000 (panel port) | You, until the panel has a domain | The panel, published by Docker, on the panel server. Since 0.2.1 the panel can publish it on `127.0.0.1` only (**Serve on IP address**). |
| 3443 (agents' TLS port) | Your other nodes: until the panel has a domain, then as their way back when the domain stops answering (see [Adding nodes](/guides/adding-nodes#when-the-panel-gets-a-domain)) | The panel, published by Docker, on the panel server. Since 0.2.1 the panel can publish it on `127.0.0.1` only (**Agents' port**). |
| 5756 on the `seylo-edge` bridge | Traefik on the same server, for maintenance pages and tool hosts | The agent; the installer allows it in ufw |
| 5757 | Your other nodes only, for [load balancing](/guides/load-balancing) | Traefik, published by Docker; it only serves nodes with a certificate from the panel. A joining node also allows it in ufw from the panel's address when the join URL is an IP address, which Docker's rules bypass (see below) |
| IP:port addresses | People you give them to: first-run access, [timed expose](/features/dev-access-and-tunnels), exposed databases | The agent: open each port you want reachable |

Ports published by Docker bypass ufw and firewalld: Docker sends their traffic through its own rules before the host firewall sees it. So 80, 443, 3000, 3443 and 5757 answer from everywhere whatever ufw says, and closing them in ufw does not close them. To limit who reaches them, use your provider's firewall (security groups), which sits outside the server, or rules in Docker's `DOCKER-USER` chain. For 3000 and 3443, 0.2.1 has a switch of its own: once the panel has a domain or is on your tailnet, the **Panel domain** card in **Settings → General** closes them on the server itself (see [Serve on IP address](/self-hosting/the-panel#serve-on-ip-address)).

The IP:port addresses the panel shows are served by the agent itself, not published through Docker, so the host firewall applies to them. When a node's firewall is on, the panel shows the command that opens each port next to the address, and the node health check names the ones that are still closed.

### Keeping the panel private

With Tailscale, the panel does it itself since 0.2.1: **Settings → Tailscale** serves it on your tailnet at `https://<machine>.<tailnet>.ts.net`, and **Lock to Tailscale** then closes 3000, and 3443 when no other node needs it (see [The panel on Tailscale](/self-hosting/tailscale)).

For another VPN such as WireGuard, close 3000 and 3443 in your provider's firewall and open the panel at the server's VPN address (`http://<VPN address>:3000`). VPN traffic arrives inside the server, so the provider's firewall does not stop it. Open it at that address the first time too: join commands use the address you set the panel up at, so your other nodes then reach it over the VPN as well and need to be on it. Leave 80 open while the panel or your sites use Let's Encrypt certificates, and 443 for your sites.

## Docker live-restore

Seylo runs every container with Docker's restart policy off, because the agent owns the crash policy. Without Docker's `live-restore`, restarting Docker (an update, unattended upgrades) stops every service and the panel until the agent starts them again. The installer turns it on in `/etc/docker/daemon.json` and reloads Docker, which restarts nothing, and keeps the old file as `daemon.json.before-seylo`.

Changed in 0.2.13: on Docker 29.0 to 29.2 that reload also empties Docker's `dns` setting, when it has one: a `"dns"` key with entries in `daemon.json`, or `--dns` on the command line `docker.service` starts dockerd with. Every container created after the reload, the panel, Traefik and build workers included, then gets `nameserver invalid IP` until Docker restarts, so builds cannot pull images (moby#52060, fixed in Docker 29.3.0). On those versions with a `dns` setting, the installer now runs `systemctl restart docker` right after the reload, once Docker reports live-restore on, so containers keep running through the restart. It waits up to a minute for Docker to answer again, and stops there if it does not, pointing at `systemctl status docker` and `journalctl -u docker`. When Docker does not report live-restore within a few seconds of the reload, the installer restarts nothing, since that restart would stop every container, and warns: check `journalctl -u docker`, then run `systemctl restart docker` once live-restore is on, or at a time when every container may stop. Docker 28, 29.3.0 and later, and Docker without a `dns` setting get the reload alone, as before. A node an earlier installer set up this way may still have containers with `nameserver invalid IP`: the [Container DNS](/guides/node-health#container-dns) health check finds them and says how to fix it.

It leaves Docker alone when `daemon.json` sets `"live-restore": false`, when Docker is in swarm mode, and on servers that run Wings. On a Wings server it only says how to turn live-restore on, and since 0.2.13 that advice adds the restart after the reload in the same case. The **Docker live-restore** node health check warns while it is off, and the **Update Docker** dialog warns before an update restarts Docker without it. Both give the same steps, with the restart after the reload on Docker 29.0 to 29.2 with a `dns` setting (see [Reloads on Docker 29.0 to 29.2](/guides/node-health#reloads-on-docker-290-to-292)).

## Where things live

Everything Seylo keeps on a node is in one folder:

<Files>
  <Folder name="/var/lib/seylo" defaultOpen>
    <File name="config.yml" />
    <File name="agent.key" />
    <Folder name="panel">
      <File name="panel.db" />
      <File name="metrics.db" />
      <File name="master.key" />
      <File name="agent-tls.key" />
    </Folder>
    <Folder name="services">
      <Folder name="<id>">
        <Folder name="volumes" />
        <Folder name="files" />
      </Folder>
    </Folder>
    <Folder name="logs" />
    <Folder name="builds" />
    <Folder name="registry" />
    <Folder name="network" />
    <Folder name="run" />
    <Folder name="state" />
    <Folder name="traefik" />
    <Folder name="tools" />
    <Folder name="update" />
  </Folder>
</Files>

| Path | What it is |
| --- | --- |
| `config.yml` | The node's config: panel URL, node id, panel certificate pin, and settings only root on the node can change, such as `no_host_shell`, `git_proxy_resolves` and, since 0.2.1, `no_tailnet` |
| `agent.key` | The node's private key; it signs every connection to the panel |
| `panel/` | Only on the node that runs the panel: `panel.db` (everything the panel knows), `metrics.db` (metric history), `master.key` and `agent-tls.key` with its certificate (what agents pin while the panel has no domain, see [Secrets at rest](/security#on-the-panels-node)), and since 0.2.1 `tailnet.sock`, where Tailscale Serve sends the panel's tailnet requests (see [The panel on Tailscale](/self-hosting/tailscale#how-it-works)). Mode 0700, owned by the panel's user (uid and gid 61000), so only root and the panel can read it. |
| `services/<id>/volumes/<name>` | Service volumes. New in 0.2: `services/` and each `services/<id>/` are mode 0700, so only root reaches the volumes and file mounts under them; the agent closes older folders when it starts. |
| `services/<id>/files` | File mounts, mode 0700. New in 0.2: one folder per version of the service's settings, so a deploy that fails, and the old version it rolls back to, keep their own files |
| `logs/<service id>/` | Service logs, kept across deploys |
| `builds/` | Build workspaces and uploaded sources |
| `registry/` | Image registry storage (panel node only) |
| `network/` | Ports the agent picked for IP:port addresses, kept across restarts, and the key that signs tool session cookies on the node's edge listener |
| `run/` | The agent's local socket (`agent.sock`), which the node commands such as `seylo status` talk to |
| `state/` | The last desired state from the panel and reports waiting to be sent |
| `traefik/` | Traefik's config, route files and certificates |
| `tools/` | Pinned helper binaries (Railpack, Nixpacks) |
| `update/` | The previous agent binary (`agent.prev`) and, on the panel's node, the copies of `panel.db` and `metrics.db` taken before each panel update (`panel-snapshots/`); see [Updates](/self-hosting/updates) |

Keep a copy of `master.key` somewhere other than the server: it decrypts the secrets in `panel.db` (see [Backing up the panel](/self-hosting/backups)).

New in 0.2: the panel container runs as uid and gid 61000, which no login user has. On 0.1, it ran as uid 1000, which on most cloud images is the default login user (`ubuntu`, `debian`, `ec2-user`), and that user could read `master.key` and `panel.db` without sudo. An upgraded panel's node moves the folder to the new user by itself, the first time its agent starts the panel after the update. A new panel install warns when an account on the server already has uid or gid 61000, since that account could read the folder.

## If something goes wrong

```bash
seylo status          # the agent, its panel connection and the services on this node
seylo health          # the node health checks, with a fix for each failure
seylo panel status    # the panel's state, version, URL, where its ports answer and its tailnet address
seylo troubleshoot    # upload a redacted report and get a link to share
```

More in [Troubleshooting](/troubleshooting).
