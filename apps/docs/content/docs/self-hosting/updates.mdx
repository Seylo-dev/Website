## Auto-update

**Settings → Updates → Update automatically** is one switch for the panel and all nodes. It is off until you turn it on. The panel looks for a new release every 6 hours (**Check now** looks right away), and with the switch on it rolls a new release out in this order:

1. The panel updates first.
2. Then each node, one at a time. A node that fails its update rolls itself back and the rollout stops, so one problem doesn't spread.

A node that was offline during a rollout updates itself when it reconnects. **History** lists every update run with its steps, who or what started it and how it ended.

With the switch off, **Updates** shows **Update available** with the new version and its changelog, and **Update to `<version>`** runs the same steps when you choose. The **Update available** alert can tell you. On **Nodes**, **Update now** updates a single node's agent to the panel's version.

## Signed releases

Every release has a manifest (`manifest.json`) signed with the project's minisign key, listing the panel image by digest and the agent binaries with their SHA-256 checksums and sizes. The panel checks the signature before it offers an update, and each agent checks it again itself before it installs anything: an agent never takes the panel's word for it. An agent also refuses a version that is not newer than its own, or one the manifest says it cannot upgrade to directly.

The panel works with agents up to two minor versions older than itself. An agent that is too old is refused at connect and installs the newest signed release by itself.

## How the panel updates

Two panels can't share one SQLite file, so a panel update is a short stop, not a swap:

1. Pull the new image.
2. Stop the running panel.
3. Copy `panel.db` and `metrics.db` to `/var/lib/seylo/update/panel-snapshots/`.
4. Start the new version and wait until it runs.
5. If it does not come up, stop it, restore the copy and start the old version again.

The panel shows an updating page for those seconds. Apps are not affected: they run on the nodes, not in the panel. A journal on disk lets the agent finish or undo a swap that was interrupted, for example by a reboot.

New in 0.2: when the panel's update to a release was rolled back, automatic runs do not start for that release at all, and the nodes, which update after the panel, wait with it. The **Update failed** alert ends with "Automatic updates wait for a newer release; updating the panel by hand installs this one." **Update to `<version>`** in **Settings → Updates** or on **Nodes** tries it again.

## How a node updates

1. The agent downloads its new binary, checks its size and SHA-256 against the signed manifest, and makes sure it runs.
2. It keeps the old binary as `/var/lib/seylo/update/agent.prev` and arms a systemd timer as a guard.
3. It swaps the binary in and restarts. Containers keep running through the restart; the agent adopts them when it comes back.
4. The new agent confirms once it has reconnected to the panel. If it does not within 3 minutes, the guard puts the old binary back and restarts it.

Either way the panel gets exactly one result for the node.

New in 0.2: a release the guard rolled back is held for that node, so a bad release does not keep restarting the agent, and with it builds, shells and consoles:

- The panel's automatic runs (the check every 6 hours with **Update automatically** on) leave the node out for that release, with no time limit, until a newer release comes out. The panel's alert, **Update to `<version>` failed on `<node>`**, ends with "Automatic updates leave this node out until a newer release; Update now installs this one."
- The node itself waits before it installs that release again on its own (when it connects with auto-update on, or when the panel refuses it as too old): an hour after the first rollback, then a day after each later one. Its own **Update failed** alert says until when.

**Update now** for the node (on **Nodes** or in **Settings → Updates**) installs the release right away and lifts the hold. A confirmed update to that release or a later one clears it as well, and resolves the node's alert.

## Upgrading from 0.1

The update to 0.2 runs like any other. A few security fixes in it change what people see afterwards, such as one more sign-in for everyone; [Upgrading from 0.1](/self-hosting/upgrading-from-0-1) lists them.

## Docker

Docker Engine is not updated with the rest. Update it per node with **Update Docker** on **Nodes**, which uses the system's package manager (apt, dnf or yum) and shows the version change first. With Docker's live-restore on, which the installer sets up, containers keep running while the daemon restarts; when it is off, the dialog warns first (see [Docker live-restore](/installation#docker-live-restore)).
