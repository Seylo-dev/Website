## Auto-update

**Settings → Updates → Update automatically** is one switch for the panel and all nodes. It is off until you turn it on. The panel looks for a new release every 6 hours (**Check now** looks right away), and with the switch on it rolls a new release out in this order:

1. The panel updates first.
2. Then each node, one at a time. A node that fails its update rolls itself back and the rollout stops, so one problem doesn't spread.

A node that is offline when its turn comes is skipped, and the rollout goes on with the next one. **History** lists every update run with its steps, who or what started it and how it ended.

With the switch off, **Updates** shows the new version and its changelog, and **Update to `<version>`** runs the same steps when you choose. The **Update available** alert can tell you. On **Nodes**, **Update now** updates a single node's agent to the newest release on the release channel. It refuses when the node already runs that release or a newer one.

### Nodes that were offline

New in 0.2. When a node that was skipped as offline reconnects, the panel updates it in a run of its own, to the version and the signed manifest of the run it missed. **History** shows that run as started by **Node came back**, and the skipped step says what became of the node when you hover it:

- **It gets `<version>` when it reconnects**: still waiting for the node.
- **It came back and was updated in a run of its own**: the catch-up run.
- **A later update run included it**: nothing to catch up.
- **It came back already running `<version>` or newer**: nothing to do.
- **It came back but had rolled `<version>` back, so it was not retried**: the node holds that release (see [How a node updates](#how-a-node-updates)); **Update now** installs it.

The catch-up run waits while another run is active, and the node applies the same waits as to its own automatic updates. On 0.1, a skipped node only caught up through its own update when it connected, which needs **Update automatically** on.

## Release channel

New in 0.2. **Settings → Updates → Release channel** picks which releases the panel offers:

- **Stable**, the default: final releases only.
- **Pre-release**: release candidates too, before they are final. The panel takes the highest version of all releases, and a final release is newer than its release candidates. Switching to it asks you to confirm (**Follow pre-releases**). With **Update automatically** on, auto-update then installs release candidates as well.

Only the owner can change the channel; for everyone else the row says "Only the owner can change it." The change is in the activity log, and the panel checks for updates on the new channel right away. A pre-release is checked like any other release: its manifest must be signed with the release key and name the version it is for. The **Panel** section shows **Running** and **Newest stable** (**Newest** on the pre-release channel), with a **Pre-release** chip when the newest release is a release candidate.

Nothing offers an older version. Back on **Stable**, a panel that runs a release candidate stays on it until a newer stable release is out, and **Updates** says so. A run also keeps the manifest it started with, so a check or a channel switch during a run never changes what its later steps install.

## Signed releases

Every release has a manifest (`manifest.json`) signed with the project's minisign key, listing the panel image by digest and the agent binaries with their SHA-256 checksums and sizes. The panel checks the signature before it offers an update, and each agent checks it again itself before it installs anything: an agent never takes the panel's word for it. An agent also refuses a version that is not newer than its own, or one the manifest says it cannot upgrade to directly.

The panel works with agents up to two minor versions older than itself. An agent that is too old is refused at connect and installs the newest signed release by itself.

## How the panel updates

Two panels can't share one SQLite file, so a panel update is a short stop, not a swap:

1. Pull the new image.
2. Stop the running panel.
3. Copy `panel.db` and `metrics.db` to `/var/lib/seylo/update/panel-snapshots/`.
4. Start the new version and wait until it runs.
5. If it does not come up, stop it, restore the copy and start the old version again.

The panel shows an updating page for those seconds. Apps are not affected: they run on the nodes, not in the panel. A journal on disk lets the agent finish or undo a swap that was interrupted, for example by a reboot.

New in 0.2: when the panel's update to a release was rolled back, automatic runs do not start for that release at all, and the nodes, which update after the panel, wait with it. The **Update failed** alert ends with "Automatic updates wait for a newer release; updating the panel by hand installs this one." **Update to `<version>`** in **Settings → Updates** or on **Nodes** tries it again.

## How a node updates

1. The agent downloads its new binary, checks its size and SHA-256 against the signed manifest, and makes sure it runs.
2. It keeps the old binary as `/var/lib/seylo/update/agent.prev` and arms a systemd timer as a guard.
3. It swaps the binary in and restarts. Containers keep running through the restart; the agent adopts them when it comes back. New in 0.2: while a deploy on the node is in its health check, the agent waits with the swap until it is done, at most 5 minutes, so the update does not roll that deploy back.
4. The new agent confirms once it has reconnected to the panel. If it does not within 3 minutes, the guard puts the old binary back and restarts it.

New in 0.2.1, for steps that take too long:

- A node that is busy with another update gets its update again, after 5 seconds, then twice as long each time up to a minute. On the panel's own node, the agent also waits up to a minute for the panel's update to let go before it answers busy. In 0.2.0, the agent step on the panel's node could hang there and fail after 10 minutes with "The update did not finish in time."
- A step that does not finish within 10 minutes fails with that message and raises **Update to `<version>` did not finish on `<node>`** (or **Update of the panel to `<version>` did not finish**). A node's step is tried once more 5 minutes later. When the node gets there after all, the alert resolves by itself.

Either way the panel gets exactly one result for the node.

New in 0.2: a release the guard rolled back is held for that node, so a bad release does not keep restarting the agent, and with it builds, shells and consoles:

- The panel's automatic runs (the check every 6 hours with **Update automatically** on) leave the node out for that release, with no time limit, until a newer release comes out. The panel's alert, **Update to `<version>` failed on `<node>`**, ends with "Automatic updates leave this node out until a newer release; Update now installs this one."
- The node itself waits before it installs that release again on its own (when it connects with auto-update on, or when the panel refuses it as too old): an hour after the first rollback, then a day after each later one. Its own **Update failed** alert says until when.
- The node applies the same waits to updates the panel sends without a person asking (the automatic run, and a [catch-up after it was offline](#nodes-that-were-offline)), and also waits an hour after an automatic update of the release failed before the swap. While it waits it installs nothing, and the run's step for it ends as skipped with the node's message.

**Update now** for the node (on **Nodes** or in **Settings → Updates**) installs the release right away and lifts the hold. A confirmed update to that release or a later one clears it as well, and resolves the node's alert.

## Upgrading from 0.1

A 0.1.x panel sees the newest 0.2 release in **Settings → Updates** and updates to it the same way as to any other release: the panel first, then each node. A few security fixes in 0.2 change what people see afterwards, such as one more sign-in for everyone; [Upgrading from 0.1](/self-hosting/upgrading-from-0-1) lists them and what to do about each.

## Docker

Docker Engine is not updated with the rest. Update it per node with **Update Docker** on **Nodes**, which uses the system's package manager (apt, dnf or yum) and shows the version change first. With Docker's live-restore on, which the installer sets up, containers keep running while the daemon restarts; when it is off, the dialog warns first (see [Docker live-restore](/installation#docker-live-restore)). New in 0.2: a Docker update without a result from the node after an hour fails, and so does one on a node that was removed, so it no longer holds up later updates.
