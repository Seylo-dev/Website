title: What's new in 0.2.17
description: Templates from their own signed catalog, private template catalogs, a DNS cache for containers per node, a Container DNS check that tries a real lookup, clone errors that point at the node's network, status dots that show whether an app is up during a deploy, and backups and restores that survive a slow bucket.
---

0.2.17 updates a 0.2.16 panel like any other release: **Settings → Updates** shows it with its changelog, and **Update to 0.2.17** updates the panel first, then each node. Nothing needs to be run on the servers, and there is no database step to do by hand.

## New

- **Templates come from their own repository.** The templates now live in [Seylo-dev/Templates](https://github.com/Seylo-dev/Templates), under the MIT License, where anyone can open a pull request for a new one: `bun run new my-app`, fill in `meta.yaml` and `index.ts`, add a logo, run `bun run check my-app` (the check every pull request runs, with the panel's own code and sandbox) and open the pull request. Every merge publishes one catalog file signed with the same key as Seylo releases. Panels check for a newer catalog when they start, every 6 hours and when someone with **templates.manage** clicks **Check for new templates** on the **Templates** page, and only take one whose signature, file hashes and sequence check out. Panels without internet access, and every panel until the first catalog is published, keep the catalog bundled with them: the same 23 templates as 0.2.16. The line under the **Templates** title says where the templates come from, when that catalog was built and why the last check failed; templates a newer catalog brought carry a **New** tag, and templates that need a newer panel (`minPanel` in their `meta.yaml`) are counted, with a link to **Settings → Updates**. Until the Templates repository publishes its first catalog, the line says "The official catalog is not published yet." and the checks raise no error. In the API and MCP, `templates.catalogStatus`; in the API, `templates.refreshCatalog`; templates carry `catalog` and `unsigned`. See [Where the catalog comes from](/guides/templates#where-the-catalog-comes-from) and [Add a template](/guides/templates#add-a-template).
- **A private template catalog.** The owner can turn catalog downloads off, for a panel without internet access, or add one catalog of their own next to the official one (**Catalog source** on the **Templates** page). A private catalog is checked with its own minisign key, or taken unsigned only when the owner allows it, with a warning. Its templates carry a **Private catalog** tag (**Private catalog, unsigned** without a key), and the install dialog says the catalog is not reviewed. An official template wins over a private one with the same name, and both win over your own templates. Changes are in the activity log. In the API, `templates.setCatalogSource`. See [Private catalogs](/guides/templates#private-catalogs).
- **A DNS cache for containers, per node.** The node's **Settings** has **DNS cache for containers**, off by default. Turned on, the node's agent answers DNS on `169.254.53.53` and, once a test from inside containers passed, gives the containers it creates that address as their first DNS server, with the servers Docker would give them as fallbacks. Lookups of the same name are answered from memory for their TTL, and identical lookups at the same moment share one question to the outside, so far fewer UDP sessions leave the server; some providers' firewalls block a server that opens too many. It does not help with many different names, it is not a limit (a container falls back to the outside servers when the cache does not answer), and it does not keep apps working when the server's outbound connections are blocked. Docker is never restarted and its settings are not changed: containers get the cache, or lose it after you turn it off, when they are next created, so deploy a service again to apply it; **Restart** does not. The node's **Settings** shows the cache's state, hit rate and upstream lookups per minute, which running containers use it and which do not yet. A **DNS cache** health check runs the test and names the fix when it fails, for example a host firewall that drops DNS from containers; on servers with ufw the installer allows DNS to the cache's address from Docker's private ranges. `dns_cache_address` in `config.yml` moves the cache when `169.254.53.53` clashes with something on the server. Wings game servers keep the DNS servers of Wings' own config, and builds do not use the cache yet. Needs the node's agent 0.2.17; tested on Ubuntu 24.04 with Docker 29.5. In the API and MCP, `nodes.setDnsCache` and `nodes.dnsCacheStatus`. See [DNS cache for containers](/guides/node-health#dns-cache-for-containers).

## Improved

- **The Container DNS check tries a real lookup.** After reading which servers containers get, it resolves `github.com` from a short-lived test container on the node's `seylo-edge` network, through Docker's embedded DNS, the way apps do. It says whether lookups work (with the time), are slow (a second or more: a warning) or fail (with `nslookup`'s error and the servers Docker forwards to, and how to test them from the node with `dig`), next to what `daemon.json` says, as before. Until now the check only read the settings, so a node whose servers looked right but did not answer from the node passed. The test container uses an image already on the node, is cut off after 20 seconds and touches no running service; when it cannot run, for example on a node whose only image has an old busybox `nslookup`, the check skips the lookup and says why. Needs the node's agent 0.2.17. See [The test lookup](/guides/node-health#the-test-lookup).
- **A clone that fails on the node's network says so.** A deploy whose clone could not reach the git host no longer always says "check the address, the branch and the credentials". A timeout, an unreachable network, a failing DNS server, a proxy's error (such as "CONNECT tunnel failed, response 502") or a TLS error now says it is a network problem on that node, with the host it tried and the connection's own error, and the build log has "The git connection to `<host>` failed: ...". On the **Overview** and the **Deployments** tab, the hint under the deploy links owners and admins to the node's **Health** tab. A host name that does not exist and a refused port ask you to check the address first. Wrong credentials, missing branches and refused addresses keep their messages. Needs the node's agent 0.2.17. See [A clone fails with "a network problem on the node"](/troubleshooting).
- **Status dots show whether an app is up while a deploy goes on.** While a build waits for a slot, builds or rolls out on top of a live version, a service's dot follows that version: green while it runs, amber while it partly runs or starts, red when it crashed or is unhealthy, and gray only when it is stopped. The label still says **Building**, **Waiting for a build slot** or **Deploying**. A first deploy that waits for a build slot shows a hollow amber ring instead of the gray dot of a stopped service. This covers the sidebar, the home page's **Cards**, **List** and **Table**, the project page, search, the service header and a compose stack's members; the **List** view's chips now have a dot too. In the API and MCP, services carry `runtimeStatus`, what runs now. See [The status dot during a deploy](/features/zero-downtime-deploys#status-dot).
- **The console follows what runs during a deploy.** The **Console** tab and the Overview's console read what runs while a build waits, builds or rolls out: they say the app is not running once the live version crashed, instead of trying to attach until the deploy ends, and attach to a first deploy's container as soon as it runs. See [The console reconnects by itself](/features/logs-and-terminals#the-console-reconnects-by-itself).
- **Template logos refresh when they change.** Their address carries a version from the file's hash, so a new logo shows without waiting for the browser's cache.

## Fixed

- **Database backups failed on a slow upload.** The node uploads a backup in 32 MiB parts and read nothing from the dump while a part uploaded, so on a slow uplink MariaDB and MySQL dropped the dump ("mariadb-dump: Error 2026: TLS/SSL error: unexpected eof" or "Error 2013: Lost connection") and Redis, Valkey and KeyDB dumps broke ("I/O Error reading RDB payload"). The agent now keeps reading and holds what the upload has not taken yet: up to 16 MiB in memory for every backup, then, for MySQL, MariaDB, Redis, Valkey and KeyDB dumps and volume backups that stop their service, in temporary files in `/var/lib/seylo/backup-spool`, at most 4 GiB per backup and never leaving less than 15% of the disk and 10 GiB free. Beyond that the dump waits for the upload as before, and when the database then drops it, the error says the upload fell behind and what to change. Needs the node's agent 0.2.17. See [When the bucket is slow](/guides/backups#slow-buckets).
- **Restores failed on a slow download.** MySQL and MariaDB restores ended with "Server has gone away" (2006) or "disconnected by the server because of inactivity" (4031), and a whole-server PostgreSQL restore hit `idle_session_timeout`. Restore sessions, and mysqldump 8.4 and later, now raise those timeouts for their own session only; the database's settings are never changed. Needs the node's agent 0.2.17.
- **A dump or restore that lost its database connection said little.** After the tool's own line, the error now says the database closed the connection and what usually causes it: the database restarted or ran out of memory, with the line to look for in its **Logs** ("Aborted connection" for MySQL and MariaDB, "Disconnecting timedout replica" for Redis, Valkey and KeyDB, "terminating connection" for PostgreSQL). See ["The database closed the connection"](/guides/backups#connection-closed).
- **A volume backup that stops its service kept it down for the whole upload.** The service starts again as soon as its archive is written, while the upload goes on. Needs the node's agent 0.2.17.
- **A template could add a domain the Domains tab refuses.** A template's custom domain host and path now follow the same rules as adding a domain by hand, and a template that breaks them fails with the field it got wrong.
- **Excalidraw's template used the moving `latest` tag.** It is pinned to an image digest.

## After the update

- The panel adds the node DNS cache setting to its database by itself when it starts on 0.2.17 (migration 0026). Nothing to run by hand.
- Update the nodes too; the update does that, after the panel. These need the node's agent from 0.2.17: the DNS cache, the Container DNS check's lookup, the clone network errors, and the backup and restore fixes. Everything else needs only the panel.
- The DNS cache is off on every node until you turn it on. On a node with ufw on that was installed before 0.2.17, the update adds no firewall rule for it, since updates do not run the installer: add the rule before you turn the cache on (see [Firewalls](/guides/node-health#dns-cache-firewalls)), or the cache stays **Blocked** and containers keep Docker's servers.
- MySQL, MariaDB, Redis, Valkey and KeyDB backups, and volume backups that stop their service, can now use up to 4 GiB of the node's disk each while the upload catches up, and always leave 15% of the disk and 10 GiB free. Other backups keep to memory.
- The official template catalog switches on by itself when Seylo-dev/Templates publishes its first signed catalog. Until then panels list the 23 bundled templates, as in 0.2.16. Panels up to 0.2.16 keep the templates they shipped with.
- Scripts that read a service's `status` still get `building` or `deploying` while a deploy goes on; read `runtimeStatus` for what runs meanwhile.
