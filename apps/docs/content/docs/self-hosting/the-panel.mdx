## How it runs

The panel is one container: the API, the web app and the MCP server. It runs as the protected service of the **Panel** project on the node you installed it on, managed by that node's agent like any other service. Being protected means it can't be deleted, stopped, deployed or moved from the panel itself, so a wrong click can't take the panel down. It updates itself from **Settings → Updates** instead (see [Updates](/self-hosting/updates)).

It runs as uid and gid 61000, which no login user has (new in 0.2; on 0.1, it ran as uid 1000, often the server's default login user, see [Secrets at rest](/security#on-the-panels-node)). Its data is in `/var/lib/seylo/panel/` on that node, a folder only root and the panel can read (mode 0700):

| File | What it is |
| --- | --- |
| `panel.db` | Everything the panel knows, in SQLite: projects, services, environment, domains, people, settings, the activity log |
| `metrics.db` | Metric history, kept apart so it can be dropped without losing anything else |
| `master.key` | The key that encrypts secrets inside `panel.db`: environment variables, tokens, passwords, backup credentials |

Service logs are not stored by the panel. They stay on each node and are streamed when you look at them. Built images live in a registry on the panel's node, in `/var/lib/seylo/registry`.

## Give the panel a domain

After installation the panel answers on `http://<server-ip>:3000`, which is plain HTTP: passwords and the session cookie cross the network unencrypted, and browsers send a cookie of `http://<server-ip>` to every port of that address, including services other people run there. Set a domain before you invite anyone. Until then, reach the panel through an SSH tunnel (`ssh -L 3000:127.0.0.1:3000 root@<server-ip>`, then `http://127.0.0.1:3000`), or serve it on your tailnet (see [The panel on Tailscale](/self-hosting/tailscale)).

Changed in 0.2.1: pages on plain HTTP show one calm line at the top, **HTTPS is off until the panel has a domain.**, with **Set a domain** and, under **More**, the SSH tunnel command for the page's port. **Dismiss** hides it in that browser. The setup and sign-in pages show nothing, and neither do pages opened through the tunnel (`localhost`, `127.0.0.1`) or on the tailnet URL. In 0.2, every plain HTTP page, the setup page included, showed an orange **This connection is not encrypted** box.

Point an `A` record at the panel's node, type the hostname in **Panel domain** on the **Panel domain** card in **Settings → General**, and click **Save domain**. The panel gets a certificate like any other service; the card shows **Waiting for DNS**, **Getting a certificate**, then **Active**.

The panel checks the domain every 5 minutes until it is active, and about once an hour after that. New in 0.2.1: the state shows when it was last checked, and **Check now** next to it checks at once, for example right after you changed the record (once every 10 seconds). Saving the domain again checks it at once too.

Once the domain is active:

- page loads on `http://<server-ip>:3000` redirect to the domain (API calls and the local agent keep working on the old address),
- the session cookie is `Secure` (since 0.2, `__Host-seylo_session`, see [Sessions](/people/sign-in-and-security#sessions)) and HTTPS answers carry HSTS,
- new join commands on **Nodes** use `https://<panel domain>`,
- nodes that joined over the panel's agent port (`https://<server-ip>:3443`) move to the domain by themselves and keep that address as a fallback.

Nodes that joined over plain HTTP (`--insecure`) stay on their address; run a new join command on them with `--force` added. The node keeps its key, so the panel keeps the same node and its services. Details, and what happens to nodes when you later remove or change the domain, are in [Adding nodes](/guides/adding-nodes#when-the-panel-gets-a-domain).

To go back to IP:port, clear **Panel domain**. Nodes that moved to the domain from the panel's IP come back through their fallback address by themselves after 5 minutes of failed connects, so expect them offline for a few minutes. New in 0.2.1: while nodes connect over the domain, removing or changing it asks first (**Remove the panel domain?** or **Change the panel domain?**) and names them, since a node that joined over the domain has no fallback and stays offline until it is joined again with `--force`.

A domain is worth setting early:

- it is what puts the panel on HTTPS; set it before you invite people,
- passkeys need it,
- GitHub needs an address it can reach to deliver webhooks,
- nodes you add later join through it, with no certificate pin to carry around,
- with it, the panel can stop answering on its IP address (see [Serve on IP address](#serve-on-ip-address)).

**Default node** on the same page is where new services go when nobody picks a node.

### Behind Cloudflare's proxy

The panel domain can be proxied by Cloudflare (orange cloud). DNS then answers with Cloudflare's addresses, not the node's, so the panel can't check where the record points. New in 0.2.1: when every address of the domain is one of Cloudflare's, the panel shows **Proxied by Cloudflare**, skips the record check, and counts the domain as active once `https://<panel domain>/api/health` answers through Cloudflare with a trusted certificate. Since 0.2.8 that answer must also prove it comes from this panel (a one-time nonce only this panel can answer), so a record that still points at another server, an old panel of yours included, never counts. A domain that is already active stays active when you turn the proxy on later, as long as that check passes. Before 0.2.1 a proxied panel domain stayed at **Waiting for DNS**.

In Cloudflare:

1. Point the `A` record at the panel's node, with the proxy on.
2. Set **SSL/TLS** to **Full (strict)**. Flexible sends plain HTTP to the node, which redirects to HTTPS, which loops.
3. Turn off **Always Use HTTPS** (**SSL/TLS → Edge Certificates**). The node gets its certificate from Let's Encrypt, which checks `http://<panel domain>/.well-known/acme-challenge/` over plain HTTP, for the first certificate and for every renewal. Always Use HTTPS sends that check to HTTPS, where the node does not answer it, so the certificate is never issued or renewed. The panel redirects plain HTTP to HTTPS itself, so visitors still end up on HTTPS.

Until HTTPS answers, the state is **Getting a certificate** and the message under it says what to set.

Nodes reach a proxied panel domain through Cloudflare too. The agent's connection is a WebSocket, which Cloudflare passes on, and agents check the certificate Cloudflare presents with the node's trusted roots: nothing pins the panel's own certificate on the domain. The panel reads each node's own address from Cloudflare's `CF-Connecting-IP` header (see [The panel behind Cloudflare](/guides/domains-and-https#the-panel-behind-cloudflare)).

Cloudflare refuses request bodies over 100 MB on its Free and Pro plans (200 MB on Business, 500 MB on Enterprise). Through a proxied panel domain, larger uploads fail with `413`: a file over that size in a volume's **Files** browser, or an archive for an [upload source](/guides/images-and-uploads#upload) (up to 512 MB). Upload those through the SSH tunnel, or turn the proxy off (DNS only) while you upload.

## Serve on IP address

New in 0.2.1. Docker publishes the panel's port past ufw and firewalld (see [Firewalls](/installation#firewalls)), so before 0.2.1 closing it took your provider's firewall. Now the **Panel domain** card has two switches. Both are on by default, which is how 0.2.0 behaves:

| Switch | Off means |
| --- | --- |
| **Serve on IP address** | `http://<server-ip>:3000` answers only on the server itself (`127.0.0.1`). The domain keeps working, because the server's proxy reaches the panel over Docker's network, and so does the panel node's own agent, which connects over `127.0.0.1`. |
| **Agents' port** | Port 3443 answers only on the server itself, and nodes reach the panel over the domain. It closes only together with **Serve on IP address**. |

The agent recreates the panel container with the port published on `127.0.0.1` only, which closes it whatever the host firewall says. Each change restarts the panel once, for a few seconds. `3000` and `3443` are the defaults; a panel installed with `--port` or `--agent-tls-port` shows its own numbers.

To turn it off:

<Steps>
<Step>

### Get a way in that is not IP:port

Set the panel domain and wait for **Active**, or serve the panel on your tailnet (see [The panel on Tailscale](/self-hosting/tailscale)). The card lists these under **Ways in without IP:port**, each **Working** or **Not working**, and marks the one you are on with **You are here**.

</Step>
<Step>

### Open the panel there

Open `https://<panel domain>`, or the tailnet URL, and sign in there. A switch turns off only from a page that came in over a working private path: that proves you can still reach the panel once the port closes.

</Step>
<Step>

### Save the ways back in

Copy the commands under **Ways back in**: the SSH tunnel and `sudo seylo panel ip-access on` (see [Ways back in](#ways-back-in)).

</Step>
<Step>

### Turn off Serve on IP address

Turn off **Serve on IP address**. The dialog shows the SSH tunnel command, and that API keys, the CLI and scripts on `http://<server-ip>:3000` stop working: point them at the domain first. Confirm with **Turn off**. The panel restarts for a few seconds, then the card says **IP access is closed**.

</Step>
<Step>

### Optional: the agents' port

Turn off **Agents' port** once every other node connects over the domain (**Connects to** in each node's sheet on **Nodes**). Nodes that joined over the agents' port move to the domain by themselves while it is active (see [When the panel gets a domain](/guides/adding-nodes#when-the-panel-gets-a-domain)). A panel without other nodes can close it right away.

</Step>
</Steps>

Only the owner turns things off, from a browser that signed in or confirmed it's you within the last 15 minutes; API keys, MCP and the assistant can't. When something stands in the way, the card says **Can't turn it off yet** and lists why, each with its fix:

- no private path works yet, or this page came in over IP:port,
- the panel node's agent is offline, or too old (update it in **Settings → Updates**),
- an update is running,
- a node connects over plain `http://` (it joined with `--insecure`), online or offline: closing would cut it off. Run the https join command from **Add node** on it, with `--force` added,
- a node has not connected since the panel was updated, so the panel can't tell how it connects: bring it online once, or disable it on **Nodes**,
- the panel's own node connects over the server's public address instead of `127.0.0.1` (it was joined again with an **Add node** command). The card shows the command that joins it on `127.0.0.1` again,
- for the agents' port: nodes that don't connect over the domain yet.

Turning a switch back on is always allowed for owners and admins, from a browser or an API key (not MCP or the assistant). Every close and every reopen raises a **Security change** alert and is in the activity log. While the panel's server runs Docker older than 28, the card and the node's **Docker Engine** health check warn that machines on the same local network may still reach ports on `127.0.0.1`: update Docker from the node's page.

### If the private path stops working

**If the domain stops working** on the same card decides what happens when no private path works any more: the domain failed 2 checks in a row (5 to 10 minutes), or the tailnet did not work for 5 minutes. While IP access is closed, the panel checks its domain every 5 minutes, also once it is active.

- **Reopen IP access**, the default: `http://<server-ip>:3000` answers again and an alert says so. It closes again by itself once a private path has worked for an hour. That gives back what 0.2.0 does, never less.
- **Keep IP access closed**: it stays closed, and only the SSH tunnel, the server command and the domain itself get you back in. Only the owner picks it, after ticking **I saved the recovery commands below**, with **Keep it closed**.

Some changes reopen at once: removing or changing the domain while it is the only working path, and a panel container that does not start with the port closed (the agent puts the open one back, and the card says so). In **Keep IP access closed** mode, the panel refuses to remove or change the domain while it is the only way in: switch to **Reopen IP access** first.

### Ways back in

When the domain or the tailnet does not let you in:

1. An SSH tunnel, from your computer:

   ```bash
   ssh -L 3000:127.0.0.1:3000 root@<server-ip>
   ```

   then open `http://127.0.0.1:3000`. Use `127.0.0.1`, not `localhost`: Docker publishes the closed port on IPv4 only. It keeps the port there even while the agent is down.

2. On the panel's server, as root:

   ```bash
   sudo seylo panel ip-access on
   ```

   It turns both switches back on and sets **If the domain stops working** back to **Reopen IP access**. The panel restarts twice, a few seconds each, and the activity log records it as done from the server's command line.

3. The domain itself, once it answers again.

4. **Reopen IP access**, which does it for you unless you chose **Keep IP access closed**.

More in [Locked out of the panel](/troubleshooting#locked-out-of-the-panel).

## On your tailnet

New in 0.2.1. **Settings → Tailscale** serves the panel on your own tailnet, through the Tailscale on the panel's server, and **Lock to Tailscale** closes its IP address and port from there. See [The panel on Tailscale](/self-hosting/tailscale).

## Look and branding

**Settings → Appearance** changes how the panel looks for everyone who uses it:

- **Color mode** (light, dark or system) and a **Theme preset**: Default, Night, Classic or Midnight, with an optional custom **Accent**.
- **Branding**: the panel name, a logo for light and dark backgrounds and a favicon (PNG, SVG, WebP, JPEG or ICO, up to 512 KB), a **Sign-in page message**, and **Hide "Powered by Seylo"** in the footer.
- **Custom CSS**, applied after the theme. Only owners can change it.

The theme and branding are part of the first page load, so there is no flash of the default look.

## When the panel is down

Services keep running. Nodes keep restarting crashed containers, routing traffic, running cron jobs, serving maintenance pages and closing timed exposes without the panel, and keep their reports on disk until it is back. Only things that need the panel wait: deploys, changes and the web app.

On the panel's node:

```bash
seylo panel status       # its state, version and URL, where its ports answer and its tailnet address
seylo panel logs -f      # its output
seylo panel start        # start it if it was stopped
seylo panel setup-link   # a new owner setup link, while no owner exists
seylo panel ip-access on # answer on http://<server-ip>:3000 again
```

New in 0.2.1: `seylo panel status` also says how Docker publishes the panel's ports, for example `IP access: closed (127.0.0.1:3000); agents' port: open (0.0.0.0:3443)`, and adds a `Tailnet:` line on a server that runs Tailscale.

If a copy of `/var/lib/seylo/panel/` leaked, `sudo seylo panel rotate-key` gives the panel a new `master.key` (see [If a copy leaked](/self-hosting/backups#if-a-copy-leaked)).

## Moving the panel to another server

New in 0.2.8. The owner moves the panel to another server in **Settings → General → Move the panel to another server**. The new server has to be one of your nodes first: join it with **Nodes → Add node**, then pick it here.

What moves: everything in `/var/lib/seylo/panel/` (`panel.db`, `master.key`, `metrics.db`, the agents' TLS key, branding, uploaded sources) and the image registry with every built image. Your apps do not move: they keep running where they are, and you can move services with each service's **Move** afterwards.

What it does, in order:

1. Checks first, and refuses with the reason: the new server must be online, run the panel's version and connect over https:// (not a plain `http://` join from another host); no update, deploy, build, move, backup or restore may be running, and (since 0.2.10) no service export download and no import upload of volume data; the last move's old copy must be deleted; **Serve on IP address** must be on, Tailscale Serve off (both are tied to the old server; turn Tailscale Serve back on afterwards) and no master key rotation half done.
2. The panel is read-only for the few minutes the move takes. Your apps keep running and serving.
3. It copies the registry, then a consistent snapshot of the panel's folder, with a checksum for every file.
4. It starts the panel on the new server, waits until it answers, and checks it presents the same agents' TLS key your nodes pin.
5. It tells every node the new address, and each node checks it reaches the moved panel there (not the old one). Until the switch, the moved panel turns nodes away, so a node that loses the old panel for a moment comes back to it. If any step fails, nothing switches: the move stops, the new server's copy is deleted, and the old panel carries on.
6. It switches: the new server confirms it takes over, the old panel stops, and every node goes to the new address by itself, usually within half a minute, keeping its pin. The new panel runs no scheduled work until the first node reaches it.

If the new server stops answering right at the switch, the panel cannot tell whether it took over, so it waits, read-only, and keeps your nodes; it carries on by itself once the server answers again. Only if that server is gone for good, press **Cancel anyway** (offered after 10 minutes).

Nodes that are offline, or that joined over plain `http://` from another host, cannot follow. The check lists them; you can move anyway and join them again later with `seylo join --force`.

After the move:

- Open the panel at `http://<new server>:3000` (or your domain). Your sign-in, API keys and CLI logins keep working; a CLI logged in with the old IP address needs `seylo login http://<new server>:3000`.
- With a panel domain, point its DNS record at the new server. Until then the domain does not reach the panel; nodes use the new IP address meanwhile and go back to the domain once it is active again.
- The old server keeps a stopped copy of the panel, `master.key` included, until you press **Delete the old copy** on the moved panel. Delete it once the panel works on the new server.

A panel installed again from scratch is a different panel to your nodes, even on the same server: since 0.2 each node refuses it until it is joined again with `seylo join --force` (see [The panel's identity](/guides/adding-nodes#the-panels-identity)).
