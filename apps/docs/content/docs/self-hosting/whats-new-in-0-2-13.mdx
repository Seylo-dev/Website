title: What's new in 0.2.13
description: A Users tab on databases and a way to change the main user's password and name, seylo set-panel for a joined node whose network decrypts HTTPS, a Container DNS node check, self-signed database certificates explained, and certificates behind Cloudflare redirects to https.

0.2.13 updates a 0.2.12 panel like any other release: **Settings → Updates** shows it with its changelog, and **Update to 0.2.13** updates the panel first, then each node. Nothing needs to be run on the servers, and there is no database step to do by hand.

## New

- **Point a joined node at the panel's IP: `seylo set-panel`.** A node that joined over the panel's domain went offline when its network began decrypting HTTPS (a firewall doing TLS inspection re-signs the domain's certificate, and the agent refuses it), and getting it back meant a hand edit of `/var/lib/seylo/config.yml` or a new join with a token. Now `sudo seylo set-panel 'https://<panel IP>:<port>' --pin 'sha256:<key>'` on the node checks that the address is the panel this node belongs to, then writes `panel_url` and `panel_pin` (the previous file stays as `config.yml.bak`), restarts the agent and prints whether it connected. Another panel, a wrong pin or an address that does not answer changes nothing. The node keeps its id, its services and its other settings, with no join token. **Add node** shows the command filled in under **Already joined? Point it here**, below the join command over the panel's IP. It needs agent 0.2.13 (for an older one, see [After the update](#after-the-update)). `nodes.createJoinToken` returns `setPanelCommand`. See [Point a joined node at another address](/guides/adding-nodes#point-a-joined-node-at-another-address).
- **A Users tab on databases.** PostgreSQL, MySQL, MariaDB, MongoDB and ClickHouse databases have a **Users** tab next to **Connection**. It lists the users that can sign in, read from the database itself, with the main user first: the one Seylo signs in with for the shell, the web UI, backups and the connection URLs. Each row shows what the user may do: **Read only**, **Read and write**, **Admin of `<database>`**, **Full admin**, or **Custom** with its grants. **New user** makes one with such a level (MySQL and MariaDB also take its **Host**), and a row's menu changes its password, renames it, deletes it or makes it the main user. Other users' passwords show once, with their connection URLs, and Seylo does not keep them. Deleting a user keeps the data: a PostgreSQL user that owns tables gives them to the main user first, and MySQL warns about views, routines, triggers and events that run as the user. See [Users](/guides/databases#users).
- **Change the main user's password and name.** On the **Connection** tab, **Change** next to the user and the password opens the **Users** tab with that change; the password change replaces **Reset password**, with the same step of typing the service name. The name changes in place on PostgreSQL, which then restarts so its health check uses the new name (the restart can wait), on MySQL and MariaDB for a main user other than root, and on ClickHouse with a restart. For root on MySQL and MariaDB, and MongoDB's main user, **Use another user as the main one** makes a new user with full rights or gives an existing one a new password, signs in as it before anything is saved, and can remove the old one (for root only `root@%`). Afterwards the dialog lists the services that use the database's user, password or URLs, each with **Redeploy**. Redis, Valkey, KeyDB and Dragonfly have one user, `default`, so only its password changes. See [The main user](/guides/databases#the-main-user).
- **Through the API and MCP.** `databases.users`, `databases.createUser`, `databases.setUserPassword`, `databases.renameUser`, `databases.deleteUser` and `databases.switchMainUser`, all with the `databases.credentials` permission. The four that change or remove a user wait for a person's approval when an AI tool calls them. `databases.resetPassword` still works, and returns `deploymentId` when the database restarts. See [Permissions, API and MCP](/guides/databases#permissions-api-and-mcp).
- **A Container DNS node check.** **Container DNS**, on a node's **Health** view and in `seylo health`, checks that Docker gives containers DNS servers they can use. Docker 29.0 to 29.2 loses its `dns` setting on `systemctl reload docker` (moby#52060, fixed in 29.3.0), and entries that are not addresses do the same on any Docker 29: every new container gets `nameserver invalid IP`, so builds cannot pull images and apps cannot look up outside names, while the server's own DNS works. The check runs a short test container from an image already on the node, reads the DNS servers of Seylo's containers and Docker's `dns` setting, and says which entries are wrong and where. Its fix ends with `systemctl restart docker`, not a reload, and warns that the restart stops every container on the server unless live-restore is on. Hints that turn live-restore on with a reload add the restart on those Docker versions (see [Reloads on Docker 29.0 to 29.2](/guides/node-health#reloads-on-docker-290-to-292)). The check never changes Docker's settings or restarts Docker. See [Container DNS](/guides/node-health#container-dns).

## Improved

- **Tested on the real images.** The commands the panel runs for each step of the **Users** tab ran on PostgreSQL 18, MySQL 8.4, MariaDB 11.8, MongoDB 9.0 and ClickHouse 26.8 in Seylo's test setup: each access level checked with the database's own client, passwords, renames and deletes, the main user's changes, and then the shell, a backup and its restore as the new main user. The panel's side of the tab was tested against a stand-in node, not yet through a real panel. See [Permissions, API and MCP](/guides/databases#permissions-api-and-mcp).
- **A build that fails on a name lookup says where to look.** After "The build failed - the lines above say why", a build whose output shows a failed DNS lookup gets one more line pointing at the node's **Container DNS** check. See [In the build log](/guides/node-health#in-the-build-log).
- **Why an exposed database has a self-signed certificate.** The **Exposed connection** card has a **Self-signed certificate** note that says why (no **TLS host name**, no Let's Encrypt certificate for it yet, with the last error, or MariaDB, which always serves its own), how to get a trusted certificate, and which client settings connect meanwhile, such as `sslmode=no-verify` for node-postgres. **Download certificate** saves the certificate, so a client can trust that file instead. `databases.get` has `exposure.selfSignedReason`, `exposure.certificateError` and `exposure.certificatePem`. See [Self-signed certificates](/guides/databases#self-signed-certificates).

## Fixed

- **The installer's reload emptied Docker's DNS setting.** The installer turns on live-restore with `systemctl reload docker`, which on Docker 29.0 to 29.2 with a `dns` setting gave every new container, the panel, Traefik and build workers included, `nameserver invalid IP` until Docker restarted. There it now runs `systemctl restart docker` right after the reload, once live-restore is on, so containers keep running. On a Wings node its live-restore advice says the same. See [Docker live-restore](/installation#docker-live-restore).
- **A second MongoDB password reset before a deploy failed** ("the database refused"): it signed in with the password the database first started with, and now uses the one Seylo stores. PostgreSQL resets also sign in as the stored user, and send the new password only as its SCRAM hash, so the database's log shows no password. See [The main user's password](/guides/databases#reset-a-password).
- **ClickHouse and Dragonfly kept the old password** until something else redeployed them, so the shell, the web UI, backups and services with the new URL could not sign in, and Redis, Valkey and KeyDB went back to the old one on their next restart. These now restart with the new password right after the change, which needs the permission to deploy the database; a stopped one has to be started first. See [The main user's password](/guides/databases#reset-a-password).
- **A PostgreSQL restore stopped part way on a missing user.** A backup that names a user the database no longer has stopped after the tables it replaces had been dropped. A restore now runs in one transaction: it fails with nothing changed, and its error names the user. Make a user with that name on the **Users** tab and restore again. See [Postgres backups and missing users](/guides/backups#postgres-backups-and-missing-users).
- **The self-signed certificate was not made as one**, so node-postgres on Bun and other clients on BoringSSL or OpenSSL 1.1 said "unable to verify the first certificate", and some, such as LibreSSL, did not accept it even when told to trust that file. The new one is self-signed to those clients and only vouches for its own host name and the names under it. A node on 0.2.13 makes it again once, and the database serves it without a restart. See [Trust the certificate file](/guides/databases#trust-the-certificate-file).
- **The Certificate line of an exposed database.** PostgreSQL and MySQL with a TLS host name stayed on **being issued** after they had their Let's Encrypt certificate, and MongoDB, ClickHouse or a Redis-like engine whose certificate was never issued said **valid** while serving the self-signed one. The line now shows what the port serves. See [Expose with TLS](/guides/databases#expose-with-tls).
- **No certificate behind a Cloudflare redirect to https for every path.** **Always Use HTTPS** leaves Let's Encrypt's check of `http://<domain>/.well-known/acme-challenge/...` on http, but a Redirect Rule or Page Rule that sends every request to https does not: with SSL/TLS on **Full**, Let's Encrypt reached the node on port 443, where the app answered, and every order and renewal failed, counting against Let's Encrypt's limit of 5 failed validations per host name an hour. Nodes now answer the challenge on port 443 too, for domains whose DNS does not point straight at the node, automatic domains and the panel's own domain. A domain that points straight at its node keeps that path for its app over https, as before. Domains with **HTTPS** set to **HTTP only** also answer the panel's check on port 443, so behind **Always Use HTTPS** with SSL/TLS **Full** they no longer read **Cloudflare proxy, not this node**. See [Redirects to HTTPS in Cloudflare](/guides/domains-and-https#redirects-to-https-in-cloudflare).
- **Certificate waits for Cloudflare, and why.** A proxied domain whose certificate waits for the panel's check read **Certificate waits for DNS**. It now reads **Certificate waits for Cloudflare**, and when Cloudflare's own answer says why, the row says that instead: **Full (strict)** refusing the node's temporary certificate (525, 526), Cloudflare unable to reach the node on 443 or 80 (521, 522), Cloudflare's security answering in the node's place (let `/.well-known/` through), or a 404 from the server it reaches. A 403 from Cloudflare's security used to read as another server answering; now the domain keeps waiting and is checked again. `domains.list` and `domains.checkDns` say `originReason`. See [Certificate waits for Cloudflare](/guides/domains-and-https#certificate-waits-for-cloudflare).

## After the update

- Update the nodes too; the update does that. The **Users** tab and the main user's changes need only the panel. These need the node's agent from 0.2.13: `seylo set-panel`, the **Container DNS** check and the build's DNS line, the PostgreSQL restore in one transaction, the new self-signed certificate with **Download certificate** and its reason for a TLS host name, the **Certificate** line, and Let's Encrypt's challenge on port 443.
- A node that is offline because its network decrypts HTTPS cannot get the update, since agents update from the panel. Set `panel_url` and `panel_pin` in its `/var/lib/seylo/config.yml` by hand to the address and pin of the join command over the panel's IP, then run `sudo seylo restart`. See [Agents before 0.2.13](/guides/adding-nodes#agents-before-0213).
- Once a node updates, its exposed databases that serve Seylo's self-signed certificate (not MariaDB, which serves its own) get a new one; open connections keep the old one until they reconnect. A client that pinned the old certificate needs the new one: **Download certificate** again.
- Run the checks on each node once it updated (**Health**, then **Run checks now**). On Docker 29.0 to 29.2, **Container DNS** finds a node whose containers lost their DNS servers to an earlier reload. Its fix restarts Docker, which stops every container on the server unless live-restore is on (see [The fix](/guides/node-health#the-fix)).
- The panel keeps the reason a check through Cloudflare failed in memory only, so right after the update a waiting domain shows the general note until its next check. Opening the **Domains** tab runs one, and so does **Check again** on the row.
- Scripts that call `databases.resetPassword` on ClickHouse, Dragonfly, Redis, Valkey or KeyDB: the call now restarts the database, needs the permission to deploy it, refuses a stopped one, and returns `deploymentId`.
