---
title: What's new in 0.2.18
description: Alerts that name the service's project, the project and service in every notification channel, a template catalog check when the Templates page opens, the catalog's controls beside the search with a warning dot, downloads only of a changed catalog, and the first signed template catalog in the release.
---

0.2.18 updates a 0.2.17 panel like any other release: **Settings → Updates** shows it with its changelog, and **Update to 0.2.18** updates the panel first, then each node. Nothing needs to be run on the servers, and there is no database step to do by hand.

## New

- **Alerts name the service's project.** With many projects that each have an `api` or a `web`, an alert titled "api crashed" did not say which one. Every alert about a service now starts with `<project> / <service>`, and for a member of a compose stack `<project> / <stack> / <member>`: "acme-shop / api crashed", "acme-shop / api failed to deploy" (was "Deploy of api failed"), "acme-shop / api failed to build" (was "Build of api failed"), "acme-shop / api is unhealthy". What is about one part of the service follows a colon: "acme-shop / db: backup failed", "acme-shop / worker: cron job weekly failed", "acme-shop / web: Homepage is down" for an uptime check, "acme-shop / web: no certificate for shop.example.com". That covers crashes and the crash limit, deploy and build results, health checks, backups (failed and never reported), cron jobs, uptime checks and certificates. Node, update, approval and security alerts keep their titles. A title is written when the alert is raised, so renaming a project or a service later leaves the alerts already sent as they were. On the dashboard's **Alerts** card, an alert about a service links to its page. In the API and MCP, `alerts.list` adds `projectName`, `serviceName` and `stackName`, the current names of the alert's project and service. See [Alert titles](/features/notifications#alert-titles).
- **Notifications say which project and service.** The webhook JSON adds `projectName`, `stackName`, `serviceName` and `serviceUrl` (the service's page in the panel). Discord and Slack messages get the fields **Project**, **Stack** (members of a compose stack) and **Service**, the service linked to its page; Telegram messages and emails get the same as lines, such as "Project: acme-shop". ntfy, Pushover, Gotify and push notifications on your own devices open the service's page for an alert that has no page of its own, such as a failed cron job; before, a push opened the dashboard and the others opened nothing. See [What a notification says](/features/notifications#what-a-notification-says) and [Webhook format](/features/notifications#webhook-format).
- **A catalog check when Templates opens.** Opening the **Templates** page asks the panel to check for new templates in the background when a catalog it downloads was last checked 10 minutes ago or more, so a new template no longer waits for the 6-hour check once someone opens the page. Anyone signed in triggers it, once per visit. One check runs at a time across the panel, page opens make it ask GitHub at most 6 times an hour, and when the check brings a newer catalog, an open page shows it by itself. In the API and MCP, `templates.catalogStatus` carries `checkDue`; in the API, `templates.checkCatalogIfDue`. See [When the panel checks](/guides/templates#when-the-panel-checks).

## Improved

- **The template catalog's controls sit beside the search.** The line under the **Templates** title is gone. **Catalog source** (the owner) and a refresh button (**Check for new templates**, for people with **templates.manage**) are on the title row, left of the search; on a phone the search takes its own row under them. The refresh button spins while the panel checks and ends with the same messages as before. A problem is an amber dot on it, with a tooltip that says what is wrong and what to do: a failed check or a catalog the panel refused, a private catalog that failed, official downloads turned off, or a build without the catalog key. Nothing shows while all is well, and an official catalog that is not published is no problem. The **Catalog source** dialog now starts with what is in use: where the catalog comes from, when it was built, its commit (linked to GitHub) and the last check, then the problems. Templates that need a newer panel or could not be read keep a short note under the title, only when there are any; the count of new templates is gone, their **New** tags stay. See [The toolbar](/guides/templates#catalog-toolbar) and [What is in use](/guides/templates#what-is-in-use).
- **An unchanged catalog is one short answer.** A check asks for `catalog.json` only if it changed since the download the panel uses (`If-None-Match` and `If-Modified-Since`), so an unchanged catalog is a `304` from GitHub and no signature download. A private catalog gets the same when its server sends `ETag` or `Last-Modified`.
- **The release ships the first signed template catalog.** Seylo-dev/Templates published its first catalog, signed with the release key, and 0.2.18 ships it: catalog number 8, with the same 23 templates as before. A panel without internet access lists this signed copy; a 0.2.17 panel that can reach GitHub downloads the same catalog.

## After the update

- Everything in 0.2.18 needs only the panel; nothing waits for the node's agent, and there is no migration.
- Alerts raised before the update keep their titles ("api crashed", "Deploy of api failed"); alerts raised after it name the project. Mail filters, chat rules or scripts that match titles such as "Deploy of", "Build of", "Backup of" or "Cron job" need the new wording; match on `event` and the ids, or the new name fields, instead.
- Webhook receivers get four more fields. None was renamed or removed, and the signature is made the same way.
- The first catalog check after the update downloads the catalog in full, once; later checks ask only whether it changed.
- Where the catalog comes from, its commit and the last check are in the owner's **Catalog source** dialog now. Others with **templates.manage** see problems as the refresh button's dot and tooltip; people without it no longer see where the catalog comes from, only the note about templates left out.
