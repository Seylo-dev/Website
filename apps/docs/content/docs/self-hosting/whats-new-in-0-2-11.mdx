---
title: What's new in 0.2.11
description: Any tag or digest of a database's engine image, version changes that were refused going ahead once you accept the risk, a mysql_native_password check before MySQL 8.4, password resets that keep root in step, and MongoDB 9.0.8 and 8.0.38.
---

0.2.11 updates a 0.2.10 panel like any other release: **Settings → Updates** shows it with its changelog, and **Update to 0.2.11** updates the panel first, then each node. Nothing needs to be run on the servers, and there is no database step to do by hand.

## New

- **Run any image of a database's engine.** A database can run any tag or digest of its engine's own image, like any other Docker app: `mongo:8.2.12`, `mongo:8.2`, `mongo:latest`, an old release or a digest, and the same for `postgres` (or `pgvector/pgvector`), `mysql`, `mariadb`, `redis`, `valkey/valkey`, `clickhouse/clickhouse-server`, `eqalpha/keydb` and `ghcr.io/dragonflydb/dragonfly`. On a database's **Version** card, **Use another image** takes it, starting from the image that runs; it replaces 0.2.10's **Another tag of `<engine>` `<version>`**. The **New database** form has **Use another image** under **Version**, starting from the picked version's image. Such images are not tested by Seylo, and for a floating tag the form says that what it points at can change on the next deploy. Images of other repositories are still refused: Seylo's settings for a database (its environment, data folder, health check and command) are made for its engine's image. See [Use another image](/guides/databases#use-another-image).
- **What the Version card refused, it now asks you to accept.** A change the card used to refuse lists under **What can go wrong** one line for each risk, and goes ahead once you tick **I understand**: an older version or release than what runs (newer data files may not open on it), a Postgres major (it does not open another major's files in place), a skipped version, a version outside Seylo's catalog (not tested by Seylo), a floating tag (what it points at can change on the next deploy), a digest (its release does not show), or another Postgres base system (text indexes may need `REINDEX`). The versions under **Change to** that take a risk say so in a short note, and the deploy's log says `Risk accepted:` with the risks. The backup step stays for every change but a newer patch, and a new version that never gets healthy brings the old container back on the same data. Still refused: an image of another repository, a database on no node, a stopped one, one with a deploy running, and the image that already runs. See [What can go wrong](/guides/databases#what-can-go-wrong).
- **`PGDATA` for Postgres moves.** Postgres images from 18 on keep their data in another folder than older ones, so a 17 image on an 18 database's volume would start healthy on an empty database. Before such a move, Seylo sets `PGDATA` in the database's own variables to the folder of the data that runs, so a version that cannot read the data fails and the old container comes back. A Postgres database made from a tag that names no release, such as `postgres:latest`, gets `PGDATA` when it is created, so its data stays on the data volume. See [Postgres and PGDATA](/guides/databases#postgres-and-pgdata).
- **MongoDB's compatibility step, for Seylo's upgrades only.** Seylo sets the feature compatibility version first only for a one-step upgrade between its versions (7.0 to 8.0, 8.0 to 9.0). For other MongoDB moves, **What can go wrong** says MongoDB may refuse data whose compatibility version it does not support. See [MongoDB](/guides/databases#mongodb).
- **The version a database shows.** The page header and the card show the version its tag names ("MongoDB 8.2" for `mongo:8.2.12`), or the image when the tag names none ("MongoDB (mongo:latest)").
- **Imports keep the image a database ran.** Exported with its data and imported on another panel, a database keeps the image it ran whenever that panel's own image of the version could read the data differently: a newer release, a floating tag, a digest, or another Postgres base system. A version the panel does not offer starts on the image the file ran. See [Export and import](/guides/export-and-import#databases).
- **Through the API and MCP.** `databases.create` takes `image`. `databases.setVersion` takes any `image` (its `version` is then not needed) and `acceptRisk`, and without it refuses with reason `riskNotAccepted` (`details.risk`, `details.risks`, `details.message`). `databases.versionChoices` says `risk` and `risks` for each version, and `anyImage`, `repository` and `release`; `customOnCurrent` is deprecated. See [Through the API and MCP](/guides/databases#through-the-api-and-mcp).

## Improved

- **Every version change Seylo makes without a risk ran on the real images.** MySQL 8.0 to 8.4, MariaDB 11.4 to 11.8, Redis 7.4 to 8.2, Valkey 8.1 to 9.0 to 9.1 (and 8.1 straight to 9.1), ClickHouse 26.3 to 26.8 and a PostgreSQL 17 patch update (the pinned 17.6 to 17.11) now run in Seylo's test setup the way a node runs them, on the same data with the same settings, and every one kept the data, like MongoDB 7.0 to 8.0 to 9.0 and MariaDB 10.11 to 11.4 since 0.2.9. Some of the risks ran there too: a MongoDB 8.0 database moved to `mongo:8.2.12`, a version outside the catalog, kept its data; a MongoDB 9.0 database set to the 8.0 image, and a PostgreSQL 18 database set to 17 (with `PGDATA` set) or a 17 one set to 18, never got healthy and came back on the version they ran, with their data. Exposing a MongoDB 9.0 database over TLS ran there too. See [Tested version changes](/guides/database-engines#tested-version-changes).
- **MongoDB 9.0.8 and 8.0.38.** New MongoDB 9.0 and 8.0 databases start on these newest patch releases, and existing ones can take them as a patch update on the **Version** card (no backup needed). The upgrade from 7.0 to 8.0 to 9.0, backups, the web UI and TLS ran on them in the test setup. MongoDB 7.0 stays on 7.0.45: Docker Hub's `mongo:7.0.48` had no Linux image when this release was made. See [MongoDB](/guides/database-engines#mongodb).
- **A clearer message for a tag of another version.** A release of another version, such as `mongo:8.2.12` on a MongoDB 8.0 database, used to be refused as not an exact MongoDB 8.0 release. It is now a move to that version, and **What can go wrong** says which version the tag is and that Seylo does not offer it, so the change is not tested by Seylo (8.2 was MongoDB's short-lived rapid release, which no longer gets fixes). A moving tag such as `mongo:8.2` or `latest` says that it is not an exact release and moves to each new release.

## Fixed

- **MySQL 8.0 to 8.4 could lock out some logins.** MySQL 8.4 turns the old `mysql_native_password` sign-in method off, so accounts made with it (common for older apps, and users made by hand) could no longer sign in, while the data was fine. Before that change the panel now checks the running database for such accounts. If it finds any, nothing changes and the dialog names them, with two ways out: switch them to `caching_sha2_password` (`ALTER USER ... IDENTIFIED WITH caching_sha2_password BY '...'`, which needs each account's password), or tick **Keep mysql_native_password logins working in 8.4**, which starts 8.4 with `--mysql-native-password=ON`. Later deploys, clones and 8.4 updates keep that, and the card shows "Old mysql_native_password logins are on". The check signs in as MySQL's root user, so it works for databases whose admin user is not root too, also right after a password reset, before the next deploy.
  - A MySQL 8.4 database can turn those logins on or off without changing its image: the **Version** card has a **Keep old mysql_native_password logins working** switch with **Apply**, which restarts the database on the image it runs, also a tag such as `mysql:8.4`, with nothing to accept and no backup step. Turning them off checks for such accounts first.
  - A move to a MySQL image from 8.4 on that Seylo does not offer, such as `mysql:9.1.0`, or to a tag that names no release, gets the same check first. MySQL 9 removed that sign-in method, so there the only way out is switching the accounts.
  - An import keeps the option when the exported MySQL 8.4 ran with it; nothing else of the file's command comes along.
  - Through the API and MCP, `databases.setVersion` refuses with reason `nativePasswordUsers` (or `nativePasswordCheckFailed` when the check cannot run) and takes `keepNativePassword`, also alone on the image the database runs; `databases.versionChoices` says `nativePassword`.

  See [MySQL 8.4 and mysql_native_password](/guides/databases#mysql-84-and-mysql_native_password).
- **A password reset left MySQL's or MariaDB's root on the old password.** For a database whose admin user is not root, a reset changed the admin's password only, while the container got the new one as `MYSQL_ROOT_PASSWORD` (`MARIADB_ROOT_PASSWORD`) on its next deploy. Signing in as root with it failed (ERROR 1045), and so did the panel's own steps that sign in as root, such as the next reset and the MySQL 8.4 check above. A reset now gives root the new password too. A database an older reset already left that way still takes a reset: the admin's password changes, and the **New password** dialog says that root kept its older password and how to set it (`databases.resetPassword` returns it as `warning`). Once root has that password, later resets keep both in step. See [Reset a password](/guides/databases#reset-a-password).
- **Rollbacks a database refuses were offered.** The **Deployments** tab offered **Roll back** on a database's deployments from before a version change, and the API and MCP listed them with `canRollback`, while the rollback itself refuses them (reason `databaseVersion`), since an older version may not read the files a newer one changed. `deployments.list` and `deployments.get` now say `canRollback: false` for a database's deployment of another image than the one it runs, and the tab offers no **Roll back** there. See [Rollbacks](/guides/databases#rollbacks).

## After the update

- Update the nodes too; the update does that. None of the changes above needs a newer agent on the node.
- Existing MongoDB 9.0 and 8.0 databases keep the image they run until you take the patch update on their **Version** card (no backup needed). MongoDB 7.0 databases stay on 7.0.45.
- A MySQL or MariaDB database whose admin user is not root and whose password was reset before 0.2.11 has root on an older password. The next **Reset password** changes the admin's password, says so, and says how to set root's. Until root has the admin's password, the check before a MySQL 8.4 change cannot list the accounts, and the change is refused unless you tick **Keep mysql_native_password logins working in 8.4**.
- Scripts that call `databases.setVersion`: a change it refused before now comes back as `riskNotAccepted`, and still changes nothing without `acceptRisk`. Read `anyImage` instead of `customOnCurrent`.
