---
title: What's new in 0.2.16
description: Right-click menus, timed exposes and connections without TLS for databases, DOMAINS in references, database backups of chosen databases and tables, a database's Advanced tab with Move to another node, Use port when the app listens elsewhere, the deploy in progress on the Overview, separate folding in the sidebar and on the home page, domains that do not exist, and live updates that survive a sleeping laptop.
---

0.2.16 updates a 0.2.15 panel like any other release: **Settings → Updates** shows it with its changelog, and **Update to 0.2.16** updates the panel first, then each node. Nothing needs to be run on the servers, and there is no database step to do by hand.

## New

- **Right-click menus.** Right-click a service or a project in the sidebar, on the home page (the **Cards**, **List** and **Table** views) or on the project page, a node's row on **Nodes**, or a row on the **Deployments**, **Domains**, **Backups**, **Cron jobs**, **Alerts**, database **Users** or assistant chat screens, or any table row with a **...** menu, to get the same menu its **...** button has. On a touch screen a long-press opens it; from the keyboard, Shift+F10 or the context menu key. A service's menu has **Open**, **Open in new tab**, **Deploy**, **Cancel deploy** or **Restart**, **Stop** and **Start** (a Box: **Stop** and **Open editor**), **Logs**, **Console**, **Clone**, **Move to project**, **Move to another node**, **Copy address**, **Copy ID** and **Delete**; **Stop** and **Delete** ask first, as the header and the **Settings** tab do. A project's menu has **Open**, **Open in new tab**, **New service**, **Rename**, **Collapse** or **Expand** (for the view it was opened in), **Hide project**, **Settings**, **Copy ID** and **Delete**, which waits until the project has no services. Each row on **Nodes** gets a **...** too, with the node's views, **Run health checks**, **Update now** and its addresses and ID to copy. The browser's own menu stays on text fields, the code editors, terminals, logs, code and copy fields, selected text, and anywhere with Shift+right-click; on a touch screen, a long-press there keeps the browser's selection and copy. See [Right-click menus](/concepts#right-click-menus).
- **Timed expose for databases.** A database's **Connection** tab has a **Timed expose** card. It opens the database's port to your IP (or the IPs you type) for 15 minutes to 24 hours, 1 hour by default, and shows the address, the connection URL (with the password only for people who may see the credentials) and a ready `psql`, `mysql`, `mariadb`, `mongosh`, `redis-cli` or `clickhouse-client` command that asks for the password at the prompt, so it never lands in your shell history. ClickHouse can open its HTTP port 8123 too, with a `curl` command. A timed expose adds no TLS of its own: the card says when the database's own TLS applies (MySQL, MariaDB 11.4 and later, and a Postgres while it is exposed) and otherwise says plainly that the connection is not encrypted. Only the allowed IPs get through, and the node closes it on time even with the panel down. Before, the panel offered timed exposes only on the **Domains** tab, which databases do not have. In the API and MCP, `exposures.openTimed`'s `targetPort` is optional (a database's port, else the service's main port), and a database takes only its own port (ClickHouse: 9000 or 8123); a database's timed exposes carry `database` (the client command and the URL without the password), and `databases.connection` lists their URLs with the password (`timed`). See [Timed expose](/guides/databases#timed-expose).
- **Exposed databases can accept connections without TLS.** The **Exposed connection** card on a database's **Connection** tab has **Allow connections without TLS**, off by default. Turned on, the node passes clients that do not ask for TLS on to the database instead of refusing them (Postgres clients got "this port only accepts TLS connections", MySQL and MariaDB clients error 3159), for Postgres, MySQL, MariaDB, MongoDB, Redis, Valkey, KeyDB, Dragonfly and ClickHouse. TLS clients connect as before, the allowed IPs still apply and the connection URL keeps asking for TLS. It asks you to confirm first, since queries, data and, with some sign-in methods, the password travel unencrypted (for the Redis-like engines and ClickHouse, the password itself), in stronger words while the port is open to every IP; emptying the allowed IPs later while it is on asks again. Turning it off refuses new clients without TLS at once and closes the ones that are connected, without touching TLS sessions. It is in the activity log, and it needs the node's agent 0.2.16: until then the switch says so and the port stays TLS only. MySQL clients without TLS need the server's public key to send the password (`mysql --ssl-mode=DISABLED --get-server-public-key`, or `allowPublicKeyRetrieval=true` in JDBC). In the API and MCP, `databases.setExposure` takes `allowPlain`; `databases.get` returns `exposure.allowPlain` and `exposure.plainNeedsNodeUpdate`, and `databases.connection` returns `exposed.allowPlain`. An AI tool working through the MCP server or the assistant waits for a person's approval before it lets clients in without TLS, or, while they are let in, empties the allowed IPs or adds addresses the list did not cover (`0.0.0.0/0`, `::/0`, a new IP); its other exposure changes run right away, and MCP tokens skip the approval while **Ask before destructive actions** is off. See [Connections without TLS](/guides/databases#connections-without-tls).
- **`DOMAINS`: every domain of a service in one reference.** Apps, compose members and Boxes now have `${{api.DOMAINS}}` next to `DOMAIN`. It lists every host the service answers on, comma separated with no spaces: the primary domain first, then the others in the order the **Domains** tab lists them (`api.example.com,www.example.com`). Redirect-only domains are left out, a host with several paths counts once, and it is empty while the service has no domain. `${{api.DOMAINS[1]}}` picks one domain, counting from 0, so `DOMAINS[0]` is the primary domain, the same host as `DOMAIN`; it works inside longer values too (`https://${{api.DOMAINS[1]}}/v1`). The **Environment** editor treats both like any reference: completions offer `DOMAINS[0]`, `DOMAINS[1]`, ... with their hosts when the service has two or more, the hover shows the host, and the **References** panel has a `DOMAINS` chip. An index past the last domain gets an amber warning that says how many the service has ("api has 2 domains: DOMAINS[0] and DOMAINS[1]") and stays empty until it has that many; an index on another variable, such as `${{api.URL[1]}}`, is a red error; a broken index (`DOMAINS[-1]`, `DOMAINS[ 1 ]`, `DOMAINS[]`) blocks the save. A host variable that spells out a service's domains (`ALLOWED_HOSTS=api.example.com,www.example.com`) gets the hint to use `${{api.DOMAINS}}`, and one that spells out its second domain gets `${{api.DOMAINS[1]}}`. As with `DOMAIN`, a domain change shows in the **References** panel right away and reaches running containers on their next deploy. In the API and MCP, `env.references` marks the variable `list: true`, and `env.set`, `env.setVariable` and `env.analyze` return two new diagnostics, `not-a-list` (error) and `index-out-of-range` (warning). See [Every domain of a service: DOMAINS](/guides/environment-variables#domains).
- **Choose what a database backup holds, and see it.** A database's backup schedule backs up **Everything on this server** (as before: all databases, for PostgreSQL the users and roles too) or **Chosen databases**, picked from a live list with their sizes. With one database chosen it can take only some of its tables (PostgreSQL, MySQL, MariaDB) or collections (MongoDB); Redis, Valkey, KeyDB, Dragonfly and ClickHouse still back up everything. Each backup shows its databases as chips with their size, the compressed file size and how long it took, and the arrow opens its tables with their size and approximate rows; backups made before 0.2.16, or by older nodes, show **Everything on this server**. A chosen database or table that no longer exists is skipped with a warning on the run, and when nothing is left the backup fails and says why. Restoring a backup of chosen databases replaces only those databases, tables or collections and leaves everything else, users included, as it is; the restore dialog names them, and **Back up the current data first** backs up the same selection (and goes on without it when none of it is on the server any more). A PostgreSQL table that another table references cannot be restored alone: the restore fails and changes nothing. Several PostgreSQL or MongoDB databases in one backup are one object (`.bundle`), so **Keep newest**, downloads and deletes work as before. Images of MySQL 5.7 list their databases too. Choosing databases needs nodes on 0.2.16 (the dialog says "Update `<node>` to choose databases"); older nodes keep backing up and restoring everything. In the API and MCP, `backups.listDatabases` and `backups.runContents`; `backups.createPolicy` and `backups.updatePolicy` take `selection`, and runs carry `scope`, `contents` and `warnings`. See [Choose what a database backup holds](/guides/backups#choose-what-a-database-backup-holds).
- **An Advanced tab for databases, and Move to another node.** A database's page has an **Advanced** tab, between **Alerts** and **Notes**, with **Move to another node**, **Resource limits** (**Save and restart** applies them, offline for a few seconds) and the crash policy, and its menus have **Move to another node**. Before a move, the card says what happens on the node you pick: the database stops while its data is copied (with its size at the last full backup), it starts there with the same data, users and passwords, its internal address stays the same (and the card names the services on other nodes that lose it, since nodes share no private network), its exposed port and timed exposes move to the new node's address with the same allowed IPs and TLS settings, the services that read its `EXPOSED_*` variables need a deploy (listed), and its backup schedules carry on there, with **Back up now** to take a fresh backup first. Nodes that cannot take it say why (offline, an agent too old to copy volumes, or one that would close its exposed port or refuse the clients without TLS it accepts now). No service moves while one of its backups or restores runs, **Back up now** and **Restore** are refused while it moves, and a schedule that comes due during a move runs once it ends, on the new node. In the API and MCP, `services.moveImpact`. See [Moving a database](/guides/moving-services#databases).
- **Use port 6000 when the app listens on another port.** When the default health check was refused for the whole wait, the agent reads which ports the new container listens on (nothing is needed in the image) and the deploy says so: "The app listens on port 6000, not 80", or that the app listens only on 127.0.0.1 and must listen on 0.0.0.0. For an app (not a compose member) the deploy dialog and the **Deployments** tab then offer **Use port 6000**: it sets the service's port, moves the domains, the IP:port access and the Cloudflare tunnel that were on the old port, and deploys. With a live version these move when the new version rolls out, and go back if it fails or is cancelled. It is offered on the service's newest deploy only and waits while a deploy runs. In the API and MCP, `services.usePort`. Changing the main port by hand (**Advanced → Container → Ports**, or `services.update`) moves the same things the same way, and **Ports** says what follows the port and when. See [The app listens on another port](/features/zero-downtime-deploys#the-app-listens-on-another-port).

## Improved

- **The Overview's Deploys card shows the deploy in progress and the live one.** While a deploy is queued, waiting for a build slot or running, the card shows that deploy with its steps (**Queued** first while it waits) and how long it has run; under it, one line shows the version that is live now, and a note counts the deploys queued behind it. With nothing in progress it shows the newest deploy as before. See [Follow a deploy](/features/zero-downtime-deploys#follow-a-deploy).
- **A failed deploy keeps the app's output apart.** The error is now the reason alone, and the new container's last output is a collapsed, copyable **Last output of the new container** block in the deploy dialog and under the deploy on the **Deployments** tab, not inside the step log or the red error. The **Deploy failed** alert carries the reason alone too. Messages from older agents, and deploys that failed before the update, are split the same way when shown. See [A failed deploy's output](/features/zero-downtime-deploys#last-output).
- **The sidebar and the home page fold projects separately.** Collapsing a project in the sidebar leaves it open on the home page and the other way round, and **Expand all** and **Collapse all** change only the home page. Both are saved per person on the panel, so they follow you to other browsers, and the update keeps what you had folded. While projects load, the placeholders take the shape they last had in this browser, so a reload no longer shows every project open first. In the API, `projects.setCollapsed` takes `where` (`sidebar`, the default, or `dashboard`), and projects carry `dashboardCollapsed` next to `collapsed`. See [Project](/concepts#project).
- **Icons on Restart, Stop and Start.** The service header's **Restart**, **Stop** and **Start** buttons have icons (Restart's spins while it runs); **Deploy** stays text only.
- **Domains that do not exist say so.** A domain under a registrable domain that does not exist (not registered, no name servers yet, or a typo) no longer says to add its record "where co.il's DNS is managed": zones now stop at the registrable domain, taken from the Public Suffix List (`co.il`, `co.uk`, `com.au`, ...), and a delegated sub-zone with its own name servers is still found first. The row says "`<domain>` does not exist: it is not registered, or has no name servers yet. Check the spelling.", adds "Did you mean ...?" when another domain you can see in the panel is a likely spelling, and still shows the record to create once it exists. Adding such a domain still works and shows the same warning. In the API and MCP, `domains.checkDns` answers `zoneMissing`, `registrable` and `didYouMean`, and `domains.add` and `domains.addAuto` return `warning`. See [A domain that does not exist](/guides/domains-and-https#a-domain-that-does-not-exist).
- **The red count on the Domains tab counts only what needs you.** A domain behind Cloudflare's proxy that the panel has not checked yet, or is still checking, no longer counts; it counts once the panel's checks through Cloudflare have not reached the node for 30 minutes. The count's tooltip names the domains, every counted row says why with **Check again**, and while a proxied domain is being checked its DNS chip says "Checking that requests reach `<IP>`...". See [The count on the Domains tab](/guides/domains-and-https#the-count-on-the-domains-tab).
- **An indexed reference is judged by its item.** The **Environment** editor's **Secret** and **Public** chips judge `${{api.DOMAINS[1]}}` by that one domain, not by the whole list, and agree with what the panel decides on save.
- **A database's timed exposes keep idle connections for 2 hours**, like its exposed port. They were cut after 15 idle minutes, which broke the pooled connections of SQL clients. Needs the node's agent 0.2.16.
- **Changing a service's nodes or moving it while a deploy runs is refused**, naming the deploy to wait for or cancel, because a deploy rolls out on the nodes it started with. Replica counts, sticky sessions and the entry node alone can still change. On the **Advanced** tab, **Save** (when the nodes change) and **Move** wait, with the reason on the button. See [Nodes during a deploy](/features/zero-downtime-deploys#nodes-during-a-deploy).
- **Exports keep a schedule's chosen databases.** A service export carries a database schedule's `selection` when it has one, so exports of schedules that back up everything are unchanged. A panel before 0.2.16 imports such a schedule as one that backs up everything.

## Fixed

- **The Overview could show an old deploy after a new one went live.** The Overview's Deploys card could keep the previous deploy (for example "Failed, 1 hour ago") while the console above it already showed the new generation, until the page was reloaded. Every update to a deploy marked all cached deploy lists as fresh, the Overview's too, so coming back to it did not fetch again. Now an update touches only the lists that hold that deploy, and the card also checks every minute while nothing is deploying, and again when the browser tab is shown.
- **Live updates stopped after a laptop slept or changed networks.** A browser cannot tell a connection that died silently from one that is just quiet, so after a Mac slept, changed Wi-Fi, or a proxy lost the connection, a panel tab could stop hearing about changes for good, with no error. The panel now sends a heartbeat every 15 seconds; a tab that hears nothing for about 40 seconds, or gets no answer within 10 seconds of being shown again or of the network coming back, reconnects and reloads what it shows. The panel also closes a connection that went silent for 2.5 minutes, or that fell more than 16 MiB behind, so its tab reconnects instead of missing updates unseen. See [Panel](/concepts#panel).
- **A deploy that ended while its browser tab was hidden stayed "Building".** The **Deployments** tab and the header's deploy in progress check again as soon as the tab is shown, instead of up to 15 seconds later.
- **Deploy clocks count with the panel's time.** A running deploy's elapsed time no longer adds the error of a computer clock that is off, and it stops as soon as the deploy has ended.
- **A deploy could wait forever after its service moved to another node.** A rollout on a node that no longer runs the service now fails at its next check, saying so ("Deploy again to roll it out on ..."), and a node that reports no progress for the health timeout plus 5 minutes fails the rollout with "No progress from `<node>` for N minutes" (plus "(`<node>` is offline)" when it is). See [Nodes during a deploy](/features/zero-downtime-deploys#nodes-during-a-deploy).
- **Back up now on a schedule started a second backup while its backup was running.** It is refused now, and the schedule's menu says "This schedule is still backing up." In the API and MCP, `backups.runNow` with a `policyId` returns CONFLICT with reason `running` and the run's `runId`.
- **"+1 hour" on a timed expose shortened it** when more than an hour was left: it set the end to one hour from now. It now adds an hour to the time left, on the **Domains** tab and on a database's card, and an expose that ended leaves the screen without a reload.
- **On a touch screen, a swipe that began dragging a card and turned into a scroll could leave every later tap dead** until a reload.
- **A proxied domain could stay "needs setup" for good.** Overlapping checks of one domain stored whichever finished last, so an old answer from before the node served the route could replace the newer proof that requests reach it; and when the certificate arrived, the panel cleared that answer but never checked again. Older answers no longer replace newer ones, and the panel keeps checking a domain's origin until it knows it (every 2 minutes in the first hour, every 15 minutes in the first day, then every 6 hours), also once it is live.
- **A moved service's IP:port access stayed on the old node.** After a move, a database's exposed port, its timed exposes and a service's first-run IP:port access kept pointing at the old node and stopped working. They now move with the service once it is live on the new node, on the same port unless another service has it there; services moved by older versions are fixed when the panel starts. See [IP:port access moves with the service](/guides/moving-services#ip-port-access).
- **Two timed exposes of the same port opened in the same second could swap ports.** Each port now carries its expose's id (from older agents, they are matched by their end time to the millisecond).
- **A Postgres's timed exposes asked for TLS a few seconds early.** Turning on the exposed connection switched their URL and command to `sslmode=require` before TLS was on inside the database; the card now follows what the node reports.

## After the update

- The panel adds what it needs to its database by itself when it starts on 0.2.16 (migrations 0021 to 0025: folding per view, Use port's pending move, what backups hold, connections without TLS, and the origin checks of domains). Nothing to run by hand.
- Update the nodes too; the update does that. These need the node's agent from 0.2.16, which the update installs: connections without TLS, the "listens on port N" hint and **Use port**, choosing what a database backup holds and seeing what it holds, the 2-hour idle time of a database's timed exposes, a timed expose's own port id, and the TLS state of an exposed Postgres that the timed expose card follows. Everything else needs only the panel.
- Every existing project keeps its fold: the home page starts folded where the sidebar was, and from then on each view folds on its own.
- Exposed databases stay TLS only after the update. **Allow connections without TLS** is off on every one until you turn it on, and an import starts TLS only too.
- Backup schedules keep backing up everything until you choose databases; backups from before 0.2.16 show **Everything on this server** and restore exactly as before.
- A service whose own `.env` sets a variable named `DOMAINS`: other services that reference `${{<it>.DOMAINS}}` now get the built-in list of its domains, the way `${{<it>.DOMAIN}}` always got the built-in. Rename the variable if they need its value.
- Deploys that failed before the update keep the app's output in their deploy log; their error and the output block are split when shown. The stored rows are not rewritten.
- Scripts that call `services.setPlacements` with other nodes, or `services.move`, while a deploy runs: they get CONFLICT with reason `deployRunning` and the `deploymentId` to wait for or cancel.
