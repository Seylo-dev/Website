---
title: What's new in 0.2.15
description: A Panel address choice per node and why a node is offline, env.setVariable, backup downloads and Back up now for every schedule, deploys that wait for the image's HEALTHCHECK, an init process, NODE_ENV=production for apps, Builds at once on Auto with waiting builds shown as waiting, secret and public variables in the editor, and the visitor's address over IPv6 and through another node.
---

0.2.15 updates a 0.2.14 panel like any other release: **Settings → Updates** shows it with its changelog, and **Update to 0.2.15** updates the panel first, then each node. Nothing needs to be run on the servers, and there is no database step to do by hand.

## New

- **Panel address, per node.** A node's **Settings** has a **Panel address** choice: **Follow the panel's domain** (the default, as before: the node moves to the panel's domain once it is live) or **Stay on this address**, which keeps the node on the address it connects to now, usually the panel's IP and pin, and the panel never names its domain to it. It is for a server whose network decrypts HTTPS (a firewall doing TLS inspection re-signs the domain's certificate, and the agent refuses it), where moving to the domain only cuts the node off. `sudo seylo set-panel` on the node now sets **Stay** by itself, also when `config.yml` already points at that address, and so does a join with `--pin` at the panel's IP address while the panel has a domain (the **Add node** dialog's second command). While a node has an open "could not move to the panel address" alert because its network re-signed the domain's certificate, the panel keeps it on **Stay** until you choose, and **Settings** says why. Choosing **Follow** on a connected node reconnects it, so it moves at once. The panel's own node has no choice. In the API and MCP, `nodes.updateSettings` takes `panelAddressChoice` (`follow` or `stay`), and `nodes.get` returns `panelAddressChoice`, `panelAddressChoiceBy` and `panelAddressChoiceAt`. See [Panel address](/guides/adding-nodes#panel-address).
- **Why a node is offline.** An offline node's row on **Nodes** says why when the panel knows: the connect it refused since the node was last seen ("Refused 4 min ago: This agent (0.2.1) is too old for this panel...", or a signature that does not match the node's key), else when it was last seen. Once a node is back, its agent tells the panel the last connect error it had while away, which the panel could not see (a certificate it refused, a name it could not look up, a connection that timed out), and the node's page shows it for a week: "Was offline from 17:39 to 17:46: dial panel: x509: certificate signed by unknown authority ...". The agent keeps that error across a restart while it is away. In the API, `nodes.list` and `nodes.get` have `rejectedHello` for an offline node, and `nodes.get` has `lastOffline`. See [Why a node is offline](/guides/adding-nodes#why-a-node-is-offline).
- **Set one variable through the API and MCP: `env.setVariable`.** An AI tool working through the MCP server could not fix one line of a service's environment: `env.get` hides every value from models, and `env.set` replaces the whole file, so changing one line meant wiping the values it could not see. `env.setVariable` takes a service, a key and a value and changes only that line. The last line with the key (the one that wins) gets the new value and keeps its quotes when the value fits them, its `export`, its comment and the comment lines above it, `# @public` included. A new key goes at the end, and a `null` value removes the key. The value can hold references and goes through the same checks as a save from the editor. The activity log shows the key, never the value, and a change that would make the file longer than 256 KiB is refused. `env.setSharedVariable` does the same for a project's shared variables. See [Set one variable through the API](/guides/environment-variables#set-one-variable-through-the-api).
- **Download a backup.** A backup's menu on the **Backups** tab has **Download**. The browser saves the file straight from the bucket, so nothing passes through the panel and the bucket needs no CORS settings. The file is named after the service, what it holds and when it started, for example `vault-warden-data-2026-11-13_0300.tar.gz`. The link the panel signs is for that one file and works for 5 minutes, and the bucket's keys are never in it. It needs the restore permission, and on a database also the permission to see its credentials, since a dump holds its logins. Each download is in the activity log. In the API and MCP, `backups.downloadUrl`; an AI tool or an MCP token waits for a person's approval first, like a delete, unless **Ask before destructive actions** is off. See [Download a backup](/guides/backups#download-a-backup).

## Improved

- **References list the service's own URL, DOMAIN and internal address.** On the **Environment** tab, the **References** panel now starts with the service you edit, marked **this service**, and its own built-in variables: `URL`, `DOMAIN`, `INTERNAL_URL`, `INTERNAL_HOST` and `INTERNAL_PORT` for an app, the connection set for a database. A click inserts `${{<its name>.DOMAIN}}` like any other reference. Its own `.env` keys are not listed: a reference to another line of the same file is refused. See [The References panel](/guides/environment-variables#the-references-panel).
- **References list only variables that have a value.** A variable that is empty right now gets no chip: `URL` and `DOMAIN` of a service without a domain, a database's `EXPOSED_*` while it is not exposed, and an empty shared variable. A value you may not see keeps its chip, and a reference typed by hand still works and gets its value later. See [The References panel](/guides/environment-variables#the-references-panel).
- **A shorter, wider References panel.** The panel stops at the editor's height and its list scrolls inside it. Each group (the service you edit, every other service, the shared variables) collapses and expands from its header row; a group with more than 12 variables starts collapsed, **Expand all** and **Collapse all** do every group, and the choice is remembered in the browser for each project. The panel is up to 440px wide instead of about 320px. See [The References panel](/guides/environment-variables#the-references-panel).
- **The Environment tab says which variables are secrets.** A **Secret** chip follows each variable that builds and crash reports treat as a secret, and a **Public** chip follows one whose name or value looks secret but is public. Hovering it says why, what it changes for builds and crash reports, and which comment changes it. Values of framework-public and `# @public` variables are no longer shown as dots; a `# @secret` one is. In the API and MCP, `env.references` says `secret` for every variable of other services and every shared variable. See [Secret and Public chips](/guides/environment-variables#secret-and-public-chips).
- **Hardcoded service URLs get a "use the reference" fix.** A value that spells out another service's address, such as `NEXT_PUBLIC_API=https://api.example.com/v1` while `api.example.com` is the api service's domain, gets a blue hint with a quick fix to `${{api.URL}}/v1`. For browser variables (`NEXT_PUBLIC_`, `VITE_` and the like) the fix uses the public URL, since a browser cannot reach the project network. The hint does not block saving. In the API and MCP it is the diagnostic `hardcoded-reference` (severity `info`), which names the key and the reference, never the value. See [An address written out](/guides/environment-variables#an-address-written-out).
- **References the app would get as text get a warning.** `${{api.URL}}` inside single quotes and `api.DOMAIN` written without `${{ }}` get an amber warning with a quick fix: **Use double quotes**, or **Use `${{api.DOMAIN}}`**. Saving is never blocked. In the API and MCP they are `single-quoted-reference` and `bare-reference` (severity `warning`). See [References the app gets as text](/guides/environment-variables#references-the-app-gets-as-text).
- **Apps run with `NODE_ENV=production` unless their environment says otherwise.** Every app, whether built from a repository, a Dockerfile or an upload, run from an image, a compose stack member or a pull request preview, now gets `NODE_ENV=production` in its containers, the way apps built from a repository get `PORT`. A `NODE_ENV` in the app's `.env` (for a compose member, its `environment:` block) or in the project's shared variables wins, whatever its value. Builds do not get it, so `npm ci` in a Dockerfile still installs devDependencies. Databases, Boxes and cron services get none. Running apps get it on their next deploy. See [NODE_ENV for apps](/guides/environment-variables#node_env-for-apps).
- **Builds at once has an Auto setting.** A node's **Settings → Builds at once** is now **Auto** or a fixed number from 1 to 16. **Auto** runs one build per 4 cores and per 4 GB of memory, whichever allows fewer, from 1 to 16 (a node with 28 cores and 157 GB runs 7), and the field shows what it runs now ("Auto - 7 now"). New nodes start on **Auto**; existing nodes keep their number until you pick **Auto**. **Automatic** build node picks now prefer the node with the most free build slots. See [Node settings](/guides/adding-nodes#node-settings) and [Where builds run](/guides/github-and-git#where-builds-run).
- **Deploys wait for the image's own HEALTHCHECK.** An app or compose member with no health check of its own used to get TCP on its first port, which passes as soon as the app listens. Now, when the image declares a `HEALTHCHECK`, the deploy switches traffic only once Docker calls the new container healthy, and fails as soon as Docker calls it unhealthy, with the check's last output in the deploy error. At the default health timeout the deploy waits long enough for the image's start period. The **Health check and deploys** card says what applies, and `services.get` returns `imageHealthCheck`. Images without a `HEALTHCHECK` keep TCP, and a check you set still replaces it. See [The image's HEALTHCHECK](/features/zero-downtime-deploys#the-images-healthcheck).
- **Containers run with an init process (Tini) by default.** Apps, compose members and cron jobs ran their program as PID 1, where Linux ignores signals it has no handler for and nothing reaps zombie processes, so an app started through a wrapper could miss the stop signal. Now their containers run Docker's init (`docker run --init`), which passes the signals on and reaps zombies. **Advanced → Container → Init process** picks **Auto** (the default: on, except for images that run their own init as PID 1, such as s6-overlay's `/init`), **On** or **Off**; a compose member takes the file's `init:`. In the API and MCP, `services.update` takes `container.init`. See [Init process](/features/zero-downtime-deploys#init-process).
- **A deploy whose container never listens on its port says so.** A background worker with the default port 80 and no check of its own failed after the whole 5 minute health timeout with only "connection refused". When that TCP check was refused on every try, the error now says nothing listens on the port, and to remove the port or set a check that fits, or to listen on `0.0.0.0`. See [Nothing listens on the port](/features/zero-downtime-deploys#nothing-listens-on-the-port).
- **A new Traefik image no longer adds its download to the downtime.** When a node replaces its Traefik (an update that changes its image or settings), it now pulls the new image while the old Traefik still serves, and only then swaps them. Sites on the node are down only for the swap itself, about half a second in Seylo's test setup.
- **`seylo status` names the node as the panel does.** It printed the server's hostname (or the name given when it joined), so a node renamed in the panel showed under another name on the server. Once the agent has connected it shows the panel's name, also after a restart while the panel is away. See [Health, updates and reboots](/guides/adding-nodes#health-updates-and-reboots).
- **A failed move is remembered across restarts.** A node whose move to the panel's domain failed because the domain's certificate came from an issuer it does not trust, or did not match the pin, waited before trying again only in memory: every agent restart, an update included, tried the move once more, dropped the first session the panel accepted and raised the same alert again. The wait is now kept on the node, in `/var/lib/seylo/state/panel.json`, and ends when the panel stops naming that address or names another, or when the move works. `sudo seylo set-panel '<url>'` moves the node by hand, for example after adding a CA to the server's trust store. See [When the panel gets a domain](/guides/adding-nodes#when-the-panel-gets-a-domain).
- **The console reconnects by itself.** The **Console** tab and the Overview's console card used to follow a restart for two minutes only; any other break left them at "Disconnected. Reconnect" while the app ran. Now, while the app runs or is starting, the console connects again by itself, after 1 second and backing off to 8 seconds, and while nothing runs it connects as soon as the app starts or a deploy goes live. It stops at **Reconnect**, with the reason, when the panel refuses it, after about 25 seconds of tries that cannot attach, or after the 30-minute idle timeout. A shell still never reopens by itself. See [The console reconnects by itself](/features/logs-and-terminals#the-console-reconnects-by-itself).
- **Back up now backs up every schedule.** On a service's **Backups** tab, **Back up now** ran only the first schedule, so a service with a schedule per volume got one backup. It now starts every schedule that is on at once, each to its own destination and counted toward its own **Keep newest**, and the toast says how many started. **Back up now** on a database's **Connection** tab does the same. In the API and MCP, `backups.runAll`. See [Schedule backups](/guides/backups#schedule-backups).
- **Backups say what they hold.** Each row of **Backups and restores** names what it backed up next to its date: "Database", "Volume data", and for a restore "Restore of the Nov 12 03:00 backup of Volume data". In the API and MCP, runs have `volumeName`, and restores `sourceStartedAt`. See [Restore](/guides/backups#restore).
- **The repository picker starts on the service's repository.** On the **Source** tab of a service connected to a GitHub, GitLab, Gitea/Forgejo or Bitbucket repository, the repository field opens with its `owner/repo`, and the list shows that repository selected and scrolled into view, with the branch as it is. Opening the tab searches nothing and changes nothing. See [Connect a repository](/guides/github-and-git#connect-a-repository).
- **Wider deploy details.** The dialog with a deploy's steps and log (**Deployments → Logs**) is up to 1280px wide instead of 960px, so build output lines fit without scrolling sideways. On a phone it takes the screen less 16px a side, and the step cards wrap.

## Fixed

- **Builds waiting for a free slot on their node showed as running.** A node runs as many builds at once as its **Builds at once** allows and queues the rest, but the panel marked every build running the moment it sent it to the node. A build now stays queued until its node really starts it. While it waits, its deploy's steps start with a **Queued** step that reads "Waiting for a build slot on `<node>` - 2 ahead" (or "next in line"), and the service header, the deploy list, the build log, the sidebar and the dashboard say **Waiting for a build slot** where they said **Building**. The **Build node** picker says how many builds run and wait on each node. **Built in** times count from the build's real start. A waiting build is no longer failed by the 90-minute build timeout while the builds ahead of it run. Works with nodes on 0.2.11 and later. In the API and MCP, `builds.queue` builds are `queued` until their node starts them, with `position` and `waiting`; deployments have `buildWait` and services `buildWaiting`. See [Builds waiting for a slot](/guides/github-and-git#builds-waiting-for-a-slot).
- **A `NEXT_PUBLIC_..._KEY` variable never reached a Dockerfile build.** A Next.js app whose Dockerfile checks `ARG NEXT_PUBLIC_TURNSTILE_SITE_KEY` failed with "is a required build arg": the name has KEY in it and the value looks like a token, so Seylo took it for a secret, and a Dockerfile build gets secrets only as BuildKit secret files. Variables whose names start with a framework's public prefix (`NEXT_PUBLIC_`, `NUXT_PUBLIC_`, `EXPO_PUBLIC_`, `REACT_APP_`, `VUE_APP_`, `GATSBY_`, `VITE_`, `PUBLIC_`) are now public, unless `# @secret` says otherwise or they hold a password. Redeploy the service for its build to get them. Dockerfile builds also say when an `ARG` names a secret variable, from nodes on 0.2.15. See [Framework public prefixes](/guides/environment-variables#framework-public-prefixes).
- **Saving environment variables offered a Restart that changed nothing.** After a save, the **Environment** tab said "Restart to apply them, or deploy" and offered **Restart**, but a restart starts the same containers again with the values of the last deploy. It now says the new values apply on the next deploy and offers **Deploy** only, and so do the shared variables hint and the descriptions the MCP reads. See [When new values apply](/guides/environment-variables#when-new-values-apply).
- **Typing fast in a code editor could lose keys.** The editor (**Environment**, **Shared variables**, **Notes**, custom CSS and the others) sometimes put back an older text of its own while the page caught up, so what was typed after it was gone. It now keeps every key.
- **A watch path like `apps/docs/..` was saved and then skipped every push.** Patterns start at the repository root and git names changed files without `.` or `..` segments, so such a pattern never matches a file. Saving now refuses it with a hint, such as `apps/docs/.. never matches a file: paths start at the repository root. To watch a folder, write apps/docs/**`. Patterns saved before are not changed: if the **Source** tab shows the message for one, replace it. See [Dot segments are refused](/guides/watch-paths#dot-segments-are-refused).
- **A node next to Wings stayed offline for about 7 minutes after the panel restarted.** It had moved to the panel's domain earlier, its network then began re-signing the domain's certificate, and the agent tried its fallback (the panel's IP and pin) only after 5 minutes of failures. A connect that fails on a certificate the node will never trust now goes to the fallback on the next attempt, and the agent makes the IP and pin its address again and raises one alert, which keeps the node on **Stay**. A timeout, a refused connection or Traefik's own default certificate still waits the 5 minutes. See [When the panel gets a domain](/guides/adding-nodes#when-the-panel-gets-a-domain).
- **Apps behind a node that forwards to another node saw that node, not the visitor.** A request that came in on one node and was served by a copy on another reached the app with the forwarding node's address in `X-Forwarded-For` and `X-Real-Ip`, and `X-Forwarded-Proto: https` even over plain http. The node that serves the copy now keeps the headers the forwarding node set from the visitor's connection. It needs agent 0.2.15 on the node that serves the copy. See [Through another node](/guides/domains-and-https#through-another-node).
- **Visitors over IPv6 reached apps as the address of Docker's bridge.** Docker's userland proxy took IPv6 connections to ports 80 and 443, so every IPv6 visitor arrived as the bridge's gateway. The node's Traefik now also joins `seylo-edge6`, an IPv6-only Docker network, so Docker forwards IPv6 visitors with their own address. It needs Docker 28 or later, and the node does it only when turning on IPv6 forwarding would not stop the server taking its own IPv6 address or route from router advertisements; otherwise the agent logs which interfaces to set `accept_ra=2` on. See [Visitors over IPv6](/guides/domains-and-https#visitors-over-ipv6).
- **A build worker that lost its DNS servers kept failing builds.** A build worker created while Docker had lost its `dns` setting (a `systemctl reload docker` on Docker 29.0 to 29.2) kept failing builds until someone restarted it by hand. Now the agent restarts it itself and the build cache stays: before a build uses it, with one line in the build log, and when the node's **Container DNS** check finds it. It never restarts a worker a build runs on. See [Build workers restart themselves](/guides/node-health#build-workers-restart-themselves).
- **Cloudflare R2 destinations failed their Test with MalformedXML, and Keep newest never deleted old backups there.** With **Use path-style URLs** off, the panel's own requests to the bucket left the bucket out of the address. The panel now addresses the bucket as the nodes' upload links do, and a failed **Test** names the request it made and the provider's error, never the keys. Node uploads were not affected. See [How the bucket is addressed](/guides/backups#how-the-bucket-is-addressed).
- **Backup errors show in their dialog, and a backup whose destination was deleted can be removed.** A failed **Delete** or **Restore** keeps its dialog open with the reason. A backup whose destination was deleted says **Destination deleted**, has no **Restore**, and **Remove from list** marks it deleted (the file stays in the bucket). In the API and MCP, `backups.deleteRun` of such a backup no longer fails with `noDestination`, and `backups.restore` refuses it at once. See [A deleted destination](/guides/backups#a-deleted-destination).
- **A schedule's backup could run twice at once.** When a schedule came due while its previous backup, or one started with **Back up now**, was still running, the scheduler started another. It now skips that time, notes it in the panel's log, and runs the schedule at its next time. See [Schedule backups](/guides/backups#schedule-backups).
- **Reconnect sometimes needed two clicks.** While an app restarted, the panel answered an attach with "ready" right before refusing it, so the terminal wrote "Connected", then the refusal. A try the agent refuses at once now leaves nothing in the terminal: the console tries again by itself, and a shell's **Reconnect** says why. See [The console reconnects by itself](/features/logs-and-terminals#the-console-reconnects-by-itself).
- **A dragged project or service jumped when you dropped it.** In the sidebar, on the dashboard and on a project page, the list showed the old order for a moment after the drop, so the item slid back from a whole drag away. It now stays where you drop it, with the mouse or the keyboard, also while a deploy refreshes the list. See [Project](/concepts#project).
- **With many projects the sidebar squashed its Search box.** Every item of the menu shrank to make room. Now only the projects list scrolls, and the search, the links, the nodes card and your account row keep their size.

## After the update

- Update the nodes too; the update does that. These need only the panel: the **Panel address** setting and the refused connect on an offline node's row, `env.setVariable`, the **References** panel, the **Secret** and **Public** chips, the hints and warnings in the editor, framework public prefixes, `NODE_ENV=production`, **Builds at once** on **Auto** and the build node pick, builds shown as waiting (nodes on 0.2.11 and later), **Back up now** for every schedule, the backup labels, **Download**, the R2 addressing, backups of a deleted destination, the scheduler's skip, the console's reconnects, the watch path check, the sidebar, dragging, the code editors, the deploy details and the repository picker.
- These need the node's agent from 0.2.15, which the update installs: `set-panel` and a join asking for **Stay**, the "Was offline" report, `seylo status` with the panel's name, a failed move kept across restarts and the fallback at once on a certificate the node never trusts, the image's `HEALTHCHECK`, the init process, Traefik's new image pulled before the swap, the "Nothing in the container listens" hint, the visitor's address through another node and over IPv6, build workers restarting themselves, and the note about a Dockerfile `ARG` that names a secret.
- The panel adds what it needs to its database by itself when it starts on 0.2.15 (Builds at once's **Auto**, and when a build reached its node). Nothing to run by hand.
- Updating a node to 0.2.15 replaces its Traefik once (next to Wings, its LB Traefik), for the forwarded headers: sites on the node drop for about half a second, and open connections, event streams and WebSockets included, are cut once.
- `NODE_ENV=production`, the image's `HEALTHCHECK` and the init process apply from each service's next deploy; the update restarts nothing. If an app must run with another `NODE_ENV`, set it in its `.env` before you deploy it. A Dockerfile build gets framework-public variables as build args from its next deploy too.
- Existing nodes keep their **Builds at once** number until you pick **Auto**; new nodes start on it.
- A node that joined over the panel's IP and pin before 0.2.15 follows the panel's domain as before. For a node whose network decrypts HTTPS, choose **Stay on this address** in its **Settings**.
- On a Cloudflare R2 destination with **Use path-style URLs** off, where **Keep newest** never deleted old backups, the first cleanup after the update deletes every backup past its **Keep newest** number at once.
- Open the **Source** tab of services with watch paths: a pattern saved before with a `.` or `..` segment shows the message there. Replace it with the pattern it suggests, or its pushes keep being skipped.
- Scripts that read `builds.queue`: a build is `queued` until its node starts it, not `running` from the moment the panel sends it. Scripts that read `maxParallelBuilds` from `nodes.list` or `nodes.get`: it is the number that applies now, also on **Auto**.
