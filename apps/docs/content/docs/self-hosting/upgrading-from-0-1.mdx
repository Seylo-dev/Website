---
title: Upgrading from 0.1
description: How a 0.1 panel updates to 0.2, what changes for people and nodes afterwards, and what to do about it.
---

A 0.1.x panel updates to 0.2 the same way as to any other release. **Settings → Updates** shows the newest 0.2 release with its changelog, and **Update to `<version>`** updates the panel first, then each node, one at a time. With **Update automatically** on, the panel does it by itself after its next check. Nothing needs to be run on the servers (see [Updates](/self-hosting/updates)). A new install with `curl -fsSL https://install.seylo.dev | sudo sh` gets the newest release directly.

Besides the new features, 0.2 carries the fixes from a [security audit](/security#security-reviews). Most of them change nothing you see. These do.

<Callout title="0.2.1 and 0.2.2">
A 0.1 panel that updates now goes straight to the newest 0.2 release. This page lists what changes from 0.1 to 0.2; [What's new in 0.2.1](/self-hosting/whats-new-in-0-2-1), [What's new in 0.2.2](/self-hosting/whats-new-in-0-2-2) and [What's new in 0.2.3](/self-hosting/whats-new-in-0-2-3) list the rest. Two points below changed again in 0.2.1, and say so: new nodes build by default, and the plain HTTP warning is one calm line.
</Callout>

## What everyone notices

- **One more sign-in.** A browser session now needs a session key that the web app keeps, next to its cookie (see [Sessions](/people/sign-in-and-security#sessions)). Sessions from 0.1 have no key, so everyone signs in again once after the panel updates. API keys, MCP tokens and `seylo login` keep working.
- **Database web UIs and Boxes.** Once a node runs the 0.2 agent, a web UI or Box session opened before shows **Sign-in needed**: open it from the panel again. From then on the node checks with the panel about once a minute, so removing someone's access closes their open session within about a minute (see [Databases](/guides/databases#web-ui-and-shell)).
- **Confirm it's you more often.** In the browser, every invite, member invites too, and every change that gives someone more access needs a sign-in from the last 15 minutes (see [Confirm it's you](/people/sign-in-and-security#confirm-its-you)).
- **A notice on plain HTTP.** Until the panel has a domain, pages on `http://<server-ip>:3000` say so and offer the SSH tunnel command (see [Give the panel a domain](/self-hosting/the-panel#give-the-panel-a-domain)). In 0.2.0 that was an orange **This connection is not encrypted** box on every page; since 0.2.1 it is one line, **HTTPS is off until the panel has a domain.**, which you can dismiss, and none on the setup and sign-in pages.
- **MCP sign-in** always starts on **Read only** and marks the name a client gives itself as not verified (see [MCP and AI](/features/mcp-and-ai#connecting)).

## What may need an owner or admin

- **Git servers on private addresses or on a node.** A **Git** source on a private, loopback or link-local address, or on any address of one of the panel's nodes, public ones included, now works in a project only after an owner or admin saved a source with that host there or allowed the host. 0.2 nodes check every address git connects to. On its first start, 0.2 looks up the hosts of the git sources already saved and allows a host in its projects only when the panel resolves it to an internal address or to its nodes' addresses, or when it is an internal IP address. A host on an address that only a node itself reports, such as one of its network interfaces, is checked again once that node runs the 0.2 agent. So LAN git servers the panel can resolve, and git servers on a node, keep building. LAN-only names the panel cannot resolve are not recorded, even in sources an owner or admin saved: their builds fail after the update until an owner or admin allows that host in each project that uses it. The panel's log names each of them. Hosts that resolve to public addresses at the panel are not recorded either; one that is internal at the nodes (split-horizon DNS) fails its builds with "the node refused to connect to ..." and needs allowing too. So does a git provider connection on such a host. An owner or admin allows a host with **Allow this host for `<project>`** under the failed deployment, under **Internal git hosts** in the project's **Settings** tab, or by saving the source again (see [Allowing a host by hand](/guides/github-and-git#allowing-a-host-by-hand)). A service an owner or admin moves to another project takes its host along; a member's move of such a service is blocked until the host is allowed there. See [After the upgrade from 0.1](/guides/github-and-git#after-the-upgrade-from-01).
- **Nodes behind an HTTP proxy** refuse a git host they cannot resolve themselves, unless the host is allowed or root on the node sets `git_proxy_resolves: true` in `/var/lib/seylo/config.yml` (see [Git servers on private addresses](/guides/github-and-git#git-servers-on-private-addresses)).
- **Git URLs with a token inside.** A source whose URL carries a user name or token keeps deploying, but the panel no longer shows that part, and saving the source again needs a git credential instead.
- **Shared credentials.** A member can use a git credential, registry login, GitHub App installation or git provider connection only for the repository or image a service of the project already uses it with. For another repository, an owner or admin sets up the first service.
- **Build nodes.** `--can-build` on the join command no longer makes a build node: on 0.1, whoever held a join token could. In 0.2.0 every node that joined started with **Build images on this node** off until an owner or admin turned it on. Since 0.2.1 the person who makes the join command chooses, with **Build images on this node** in **Add node**, ticked by default (see [Build nodes](/guides/adding-nodes#build-nodes)). Nodes that already build keep it. A build node gets the source, git credentials and build-time variables of everything it builds, from any project, so keep it on only for nodes you trust like the panel.
- **Creating services with limited actions.** A member who may create services now also needs **Edit variables** to give a new service variables, **Change files** for its config files and **Deploy** to deploy it right away; databases and Boxes always start, so they need **Deploy** (see [Sharing projects and services](/people/users-and-access#sharing-projects-and-services)). The **View**, **Deploy** and **Full access** presets are unaffected.
- **Compose files and cron output.** A pasted compose file holds every member's `environment:` values, so its **Compose file** tab shows it only with **View variables** on the stack and all its members. A cron run's output needs **Read logs and cron output** (called **Read logs** in 0.1); the separate **Read cron output** action does nothing any more, so give people who had only that one **Read logs and cron output** instead.
- **Uptime checks on private addresses.** A node's private address no longer counts just because its agent reported it. Checks aimed at one go **Down** after the update: set that address as the node's **Public address** in its settings, or turn on **Settings → General → Uptime checks → Allow checks of internal addresses**. Checks also refuse a few more ranges, such as the documentation ranges (see [Where checks run from](/features/uptime-checks#where-checks-run-from)). **Check access** on git sources no longer follows these settings (see [Check access](/guides/github-and-git#check-access)).
- **Scripts with limited API keys.** A key limited to some projects or actions now gets `403 FORBIDDEN` with `narrowedKey` for account-wide actions, and sees fewer approvals and activity entries (see [How a key is limited](/people/api-keys#how-a-key-is-limited)). Most request bodies are now limited to 1 MiB (see [Request style](/api-reference#request-style)).
- **The activity log keeps 1 year** by default; older entries are removed once a day, apart from security changes. Pick **Forever** in **Settings → General → Activity log** to keep everything (see [How long entries are kept](/people/users-and-access#how-long-entries-are-kept)).
- **File permissions.** The file browser no longer sets or keeps setuid and setgid bits, and new files in a folder owned by root belong to `nobody` (see [Volumes and files](/features/logs-and-terminals#volumes-and-files)).
- **Custom maintenance and down pages** no longer run scripts: nodes serve them with the strict Content-Security-Policy. Before, scripts on a custom page ran on the service's own domains (see [Maintenance and down pages](/guides/domains-and-https#maintenance-and-down-pages)).
- **Two-factor codes** have a brake per account: from the 10th wrong code within 15 minutes, from any addresses, the panel checks at most one authenticator code every 2.5 seconds, and the owner of the account gets a **Security change** alert (see [Password](/people/sign-in-and-security#password)).

## Nodes

- **The panel's own user.** The panel runs as uid and gid 61000 instead of 1000, and `/var/lib/seylo/panel/` is mode 0700 with `master.key` 0600. On 0.1 it ran as uid 1000, which on most cloud images is the default login user (`ubuntu`, `debian`, `ec2-user`), so that user could read `master.key` and `panel.db` without sudo. Once the panel's node runs the 0.2 agent, the agent gives the folder to the new user and restarts the panel once; if the new container does not start, it puts the old one back. If people you would not trust with the panel's secrets could log in as uid 1000 on that server, treat it as a leaked copy (see [If a copy leaked](/self-hosting/backups#if-a-copy-leaked)).
- **The panel's identity.** At their first connect to 0.2, nodes write down the panel's identity and refuse any other panel from then on. Nothing to do now. Later, a panel installed again from scratch, or a master key rotation with `--new-panel-identity`, needs `seylo join --force` on every node (see [The panel's identity](/guides/adding-nodes#the-panels-identity)).
- **Backups need the 0.2 agent.** Nodes no longer get a backup destination's keys: the panel signs each upload and download for the run's own object, and deletes what **Keep newest** drops itself. Until a node runs the 0.2 agent, its backups and restores fail with "The agent on `<node>` is too old for backups". The panel must reach the bucket too, like **Test** already does (see [Backups](/guides/backups)).
- **Load balancing** on port 5757 only serves with the node's certificate from the panel. A node the panel cannot issue one for raises **Node health check failed**. Certificates are valid for 30 days instead of a year; the panel replaces longer ones by itself (see [Load balancing](/guides/load-balancing)). A request that fails on a replica that died is now sent to the next replica, on any node, and sticky sessions also work on domains without HTTPS (see [When a replica dies](/guides/load-balancing#when-a-replica-dies)).
- **Service folders** on nodes (`/var/lib/seylo/services/` and each service's folder) are mode 0700; the agent closes existing ones when it starts (see [Where things live](/installation#where-things-live)).
- **Join commands** from **Add node** add `--version` with the panel's own release to the installer from install.seylo.dev, so a new node gets the panel's version rather than the latest stable one (see [Join a server](/guides/adding-nodes#join-a-server)).
- **`seylo join --force`** keeps the node's own settings in `config.yml`, such as `no_host_shell` (see [The panel's identity](/guides/adding-nodes#the-panels-identity)).
- **Running the installer again** on a node that runs a newer release than the installer's own stops before it changes anything; re-run with `--version <that release>`, or with `--downgrade` (see [Installer options](/installation#installer-options)).

## Updates

- **A release that was rolled back is held.** On a node, the panel's automatic runs leave that node out for the release until a newer one comes out, and the node's own retries wait an hour, then a day after each further rollback. When the panel's own update was rolled back, automatic runs do not start for that release at all. The **Update failed** alert says so. **Update now** for a node, or **Update to `<version>`** for the panel, installs it right away (see [How a node updates](/self-hosting/updates#how-a-node-updates)).
- **Nodes that were offline** during an update run are updated when they reconnect (see [Nodes that were offline](/self-hosting/updates#nodes-that-were-offline)).
- **A release channel**, **Stable** or **Pre-release**, that only the owner changes. It starts on **Stable**, which offers final releases only (see [Release channel](/self-hosting/updates#release-channel)).
- **`sudo seylo panel rotate-key`** gives the panel a new master key after a leaked copy. With `--new-panel-identity` it also replaces the agents' TLS key, so the pin changes, and prints the exact join command for each node (see [If a copy leaked](/self-hosting/backups#if-a-copy-leaked)).
