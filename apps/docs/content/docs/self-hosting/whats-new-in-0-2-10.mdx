---
title: What's new in 0.2.10
description: Export a service as a .zip and import it on another panel or the same one, and another tag of the version a database runs.
---

0.2.10 updates a 0.2.9 panel like any other release: **Settings → Updates** shows it with its changelog, and **Update to 0.2.10** updates the panel first, then each node. Nothing needs to be run on the servers, and there is no database step to do by hand.

## New

- **Export a service as a .zip.** A service's **Settings** tab has an **Export** card, for owners and admins. **Export…** lists what goes in and what stays out, then downloads one file with the service's settings, its environment variables and file mounts, domains with their certificates and access rules, IP:port access, database listeners, cron jobs, uptime checks, alert rules, backup schedules, the maintenance page, the Cloudflare tunnel settings, and the data of the volumes you tick (an upload app's newest archive too). Secret values (`.env` values, file mounts, database logins, certificates, basic auth hashes, the tunnel token, shared variables) are encrypted with a passphrase you pick, 12 characters or more, and the panel cannot recover it; with a passphrase the settings themselves are inside the encrypted part too. Or leave the values out: the file then has the variable names without values, and basic auth needs new passwords on import. The volume data and the uploaded archive are not encrypted in either mode, and the dialog says so; neither is `manifest.json`, which names the service and its volumes, with their sizes and SHA-256. A service is stopped while its volumes download, so the data is consistent, and starts again by itself when the download ends, breaks off (nothing read for 5 minutes) or the panel restarts; untick **Stop `<name>` while its data is read, so it is consistent** to keep an app running meanwhile. A database is always stopped, and exports all of its data or none, only with a passphrase (the data opens with its logins). At the end the dialog shows the file's SHA-256. See [Export and import](/guides/export-and-import).
- **Import it on another panel or the same one.** **Add a service → Import from a file** reads the .zip in the browser (a damaged or edited file is refused there and again by the panel), asks for the passphrase and shows what would be created before anything is: the name (`<name>-2` when it is taken), the node, what reads the source (the GitHub App installation, connected account, git credential, provider connection or registry login of the same account or host on this panel, or the login from the file when it was included), the first deploy (the exported commit or the branch head, an image source pinned to the digest that ran), each domain (in use here, needs a password, certificate dropped), the shared variables the environment uses, and the volumes with their sizes. Every setting goes through the same checks as when you set it by hand. The service is created stopped, then its volume data goes up in parts straight to the node, with the file's SHA-256 checked by the panel and by the node. With **Deploy when the import is done** (on unless the service was stopped), it deploys once the data is in. A closed page goes on with the same file, and **Discard** deletes the new service while its data is still going up (shared variables and logins the import wrote stay). Through the API: `serviceTransfer.*` (not in MCP). See [Import from a file](/guides/export-and-import#import-from-a-file).
- **What an import leaves out, and why.**
  - Deploy history, logs and built images belong to the old panel: the import builds the service again from its source, or pulls its image.
  - The GitHub App, connected GitHub accounts and git host connections are the old panel's identities at GitHub and the other hosts: the import uses this panel's, matched by account or host.
  - People's access (grants and invites): accounts differ between panels.
  - Automatic domains belong to the old node's wildcard domain: the import offers one on the new node instead, with the same basic auth, allow list and HTTPS choice.
  - The deploy trigger URL: its token is stored hashed, so a new one is made and shown once.
  - Previews and push deploys arrive off, and the Cloudflare tunnel arrives switched off, since two connectors on one token would split the traffic between the panels. Imported on the same panel, cron jobs, uptime checks and backups arrive off, so nothing runs twice. From another panel, cron jobs and uptime checks arrive as in the file: pick **Switched off** while the old service still runs.
  - Database listeners open to anyone are skipped by default, and so are listeners this panel would not open: a MariaDB 10.11 (it has no TLS), or a node whose agent cannot keep the port TLS only yet (update it, then expose the database on its **Connection** tab).
  - The link to the template a service was installed from: a custom template of the old panel may not exist here. The settings come along.
  - Compose stacks and their members cannot be exported yet.
- **Imported databases follow this panel.** An imported database runs this panel's image of its version (the review page says when the file ran another), except when its data comes along from a newer release of the same version, such as a tag set on the **Version** card or a panel that was updated before this one: data cannot go back to an older release, so it keeps that image, or the review page asks you to update this panel or leave the data out. Like every database since 0.2.9, it has one user inside and through the exposed port. For a database from before 0.2.9 whose `external` user the old panel has not retired yet, the copied data still holds that login: the import keeps its name (never its password), and the new node disables it the same way 0.2.9 does, since nothing on the new panel uses it. See [Databases](/guides/export-and-import#databases).
- **Imported domains wait for their DNS.** A custom domain whose records still point at the old server waits before asking Let's Encrypt for its certificate, as a newly added domain does, and gets it once the records point at the new node.

## Improved

- **Another tag of the version a database runs.** The **Version** card on a database's **Settings** tab has **Another tag of `<engine>` `<version>`**, also when the database already runs the newest pinned image of its version and nothing else in the list can be picked. Give another exact release tag of the engine's official image, such as a newer patch release Seylo's catalog does not have yet: it is a patch update (no backup needed, not tested by Seylo). An older release and the image that already runs are refused (after a change that did not finish, the dialog stays on the tag that still runs), Postgres keeps its Alpine (pgvector: Debian trixie) base, and KeyDB and Dragonfly still take the catalog's image only. Through the API and MCP, `databases.versionChoices` returns `customOnCurrent`. See [Another release tag](/guides/databases#another-release-tag).

## After the update

- Update the nodes too; the update does that. Importing volume data onto a node needs its agent from 0.2.10: on an older node the review page says its agent is too old ("Update the node, or leave the data out."), and the settings import without the data. Exporting volume data works from nodes on agents from before 0.2.10 too.
- Keep the passphrase somewhere safe: without it the file's secret values cannot be read, by Seylo or anyone.
- A database is down for its whole download. Export it when that is fine, or leave its data out and back it up instead.
- From now on, a panel update waits while an export downloads or an import uploads volume data, since restarting the panel or an agent would break it.
