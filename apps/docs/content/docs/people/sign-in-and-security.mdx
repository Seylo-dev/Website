Each person manages their own sign-in methods in **Settings → Security** (under **Your account**).

## Password

Passwords need at least 10 characters. Changing yours signs you out everywhere else. If you signed up with GitHub, you can set a password to also sign in with your email; setting that first password needs a recent sign-in (see [Confirm it's you](#confirm-its-you)).

After five wrong passwords or codes in a row from one address, sign-in for that email from that address pauses for 30 seconds, doubling up to 15 minutes; 15 quiet minutes forgive the streak. The pause is per address, so a stranger guessing at your email only locks themselves out, never you. New in 0.2: all addresses of one IPv6 /64 count as one address, so a block of IPv6 addresses buys no extra tries.

Past 50 wrong passwords for one email within 15 minutes, from any addresses, the account's owner gets a **Security change** alert and a brake starts. New in 0.2: while it is on, the panel checks at most one password for that email every 2.5 seconds, one at a time, however many addresses the guesses come from; the others get "Too many failed sign-ins for this email" with the seconds to wait. Addresses (or IPv6 /64s) that signed in to that account with the right password in the last 30 days skip the brake, so a guessing campaign does not keep you out. The brake never locks anyone out. An admin who enables a person again in **Settings → People** clears both.

New in 0.2: wrong two-factor codes have a brake per account too, since whoever guesses codes already has the password. From the 10th wrong code for one account within 15 minutes, from any addresses, the panel checks at most one authenticator code every 2.5 seconds, the wait doubling with every 10 more wrong codes up to one a minute; the others get "Too many wrong codes for this account" with the seconds to wait and do not use up the sign-in attempt. The account's owner gets one **Security change** alert. Addresses (or IPv6 /64s) where the account finished a sign-in in the last 30 days skip the brake, and recovery codes are never braked, so you always have a way in. It covers the sign-in step, [Confirm it's you](#confirm-its-you), turning two-factor sign-in off and making new recovery codes.

## Confirm it's you

Anything that adds a way into your account needs a sign-in from the last 15 minutes, so a browser left signed in somewhere is not enough on its own:

- adding a passkey, linking GitHub for sign-in, setting up an authenticator app or setting a first password,
- creating an API key or an MCP token,
- approving a [command line sign-in](/guides/command-line#sign-in),
- allowing an AI tool through MCP's OAuth sign-in (see [MCP and AI](/features/mcp-and-ai#connecting)).

In the browser, the actions that hand lasting access to someone else need it too: making someone an admin or owner, creating a node join command and inviting people (see [Users and access](/people/users-and-access#invite-someone) and [Adding nodes](/guides/adding-nodes#join-a-server)). New in 0.2:

- every invite needs it, member invites included, not only admin invites,
- so does any change to someone's access that gives them more: a new project or service, a new action, or a wildcard that also covers actions added later. Taking access away and lowering a role never ask,
- and so does saving a GitLab, Gitea or Bitbucket connection's token (see [GitLab, Gitea and Bitbucket](/guides/git-providers#add-the-connection)).

New in 0.2: [host shells](/guides/host-shell) need it every time, and only work in the browser: the owner turning them on for a node, and an owner or admin opening one. API keys and MCP tokens can never do either.

When your last sign-in is older, the panel shows **Confirm it's you** and then makes the change by itself. Confirm with whichever you have:

- your **Password**,
- a code from your **Authenticator** app, or an unused recovery code (it is used up),
- a **Passkey** (needs the panel domain, like passkey sign-in).

The confirmation counts for 15 minutes in that browser only. Five wrong answers in a row from one address pause it for 30 seconds, doubling up to 15 minutes, like wrong sign-ins. An account with none of the three (GitHub sign-in only) gets **Sign in again** instead, and comes back to the same page afterwards. Closing the dialog cancels the change.

API keys and MCP tokens never get this dialog: they cannot change sign-in methods or make keys at all. An API key that holds the actions can still invite people, widen their access, change roles and create join commands without it, because the key itself was made under a recent sign-in. Through the API, a stale browser session gets `403 FORBIDDEN` with `details.reason` set to `reauth`; confirm with `auth.reauth` (see the [API reference](/api-reference)) and repeat the call.

## Security alerts

The **Security change** alert (see [Alerts and notifications](/features/notifications)) is raised when someone approves a [command line sign-in](/guides/command-line#sign-in), creates an API key, adds a passkey, links a GitHub account for sign-in, sets or changes a password or turns off two-factor sign-in, and when many wrong passwords or (new in 0.2) two-factor codes arrive for one account. New in 0.2: it is also raised when the owner allows host shells on a node and when someone opens one. Send it to a channel you read, so a sign-in method you did not add does not go unnoticed.

## Authenticator app (2FA)

**Authenticator app → Set up**: scan the QR code with an app such as 1Password, Authy or Google Authenticator (or type the setup key), then enter the 6-digit code it shows. From then on the panel asks for a code after your password.

You get recovery codes once, right after turning it on. Each signs you in once if you lose your authenticator; save them somewhere safe. The page tells you how many are left and makes new ones on request (the old ones stop working). Turning the authenticator off needs a current code or an unused recovery code, and deletes the recovery codes.

After a sign-in with a recovery code, the panel warns when three or fewer are left. New in 0.2: the sign-in step offers **Use a recovery code** only while the account has an unused one. Once they are used up, or [`seylo panel rotate-key`](/self-hosting/backups#if-a-copy-leaked) deleted them, it takes only a code from the authenticator app and says "This account has no recovery codes left. If you lose your authenticator app, an owner can remove this account and invite you again." Sign in with the app and make new codes here.

## Passkeys

**Passkeys → Add a passkey** lets you sign in with Touch ID, Windows Hello, your phone or a security key instead of a password. Passkey sign-in checks that it is really you on the device, so it does not ask for a 2FA code on top.

Passkeys need the panel to have a domain (**Settings → General**), because browsers tie a passkey to one.

## GitHub

**GitHub → Link GitHub** links your GitHub account so you can sign in with it, through the device flow (like `gh auth login`): you enter a short code on github.com. Tick **Also let the panel clone my private repositories** to also give the panel a token with the `repo` scope; leave it off if the panel's GitHub App already reaches your repositories.

GitHub sign-in needs the panel's GitHub OAuth client to be set up. When it is not, the page says "Sign-in with GitHub is not set up on this panel" and you sign in with email and password instead. Signing in with GitHub only works for accounts that linked it first.

## Sessions

**Sessions** lists the browsers where you are signed in, with their address and when they were last active. **Sign out** ends one, **Sign out everywhere else** ends all but this one.

A browser session lasts 30 days after it was last used, and at most 90 days after you signed in. Only hashes of it are stored. New in 0.2: only the requests a browser makes count as use. On 0.1, the live connection of an open tab counted too, so a tab left open kept its session going, and showed it as recently active, until the 90 days were up.

New in 0.2: a session has two halves, and the panel needs both. One is an HttpOnly cookie. The other is a session key the panel hands to the web app when you sign in; the web app keeps it in the browser's storage for the panel's own address and port and sends it with every request. Browsers send a cookie to every port of an address, but that storage is per address and port, so a copy of the cookie that reaches another service on the same server signs nobody in. Changing your password or your two-factor settings replaces both halves.

Over HTTPS the cookie is `__Host-seylo_session`: `Secure`, sent to the panel's own host only, and the only name the panel reads there, so a cookie that another site under the same parent domain sets is ignored. On `http://<server-ip>:3000` it is `seylo_session`. When a browser sends the session cookie twice (another site on the same address set one too), the panel uses neither, and the sign-in page says "This browser sent two session cookies for this address, so the panel used neither." Clear the browser's cookies for the panel's address and sign in again.

Over HTTPS the panel also sends HSTS. No page of the panel can be shown in a frame, and (new in 0.2) the web app's pages only run the panel's own scripts.

Sessions from before 0.2 have no key, so everyone signs in once after the update (see [Upgrading from 0.1](/self-hosting/upgrading-from-0-1)).

## For admins

- **Settings → People** shows who has 2FA and passkeys. Disabling a person ends all of their sessions and API keys at once; see [Users and access](/people/users-and-access).
- API keys and MCP tokens never change sign-in methods, passwords or other keys: those actions need a browser session.
- New in 0.2: failed sign-ins, refused actions and rate limits also go to the panel's own log as warnings (`sign-in failed`, `op refused`, `op rate limited`), with the action, the address and, when known, the person, never what was typed. See them with `seylo panel logs` on the panel's node. In **Activity**, failed attempts from people who are not signed in are kept up to 200 an hour; past that, one line in the panel's log says the rest were left out.
