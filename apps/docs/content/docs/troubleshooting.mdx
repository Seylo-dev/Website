## Start here

On the node with the problem:

```bash
seylo status
```

It shows the node and agent version, the panel it belongs to and whether it is connected (with the last connection error and when it retries), whether the node is behind on the panel's changes, reports waiting to be sent, every service on the node with its state, and recent errors.

```bash
seylo health
```

runs the [node health checks](/guides/node-health): Docker, disk, clock, ports, DNS, the proxy and the panel connection, each with a fix. The same checks run from the heart icon on **Nodes**.

```bash
seylo logs -f          # the agent's own log
seylo panel logs -f    # the panel's output, on the panel's node
```

## Share a report

```bash
seylo troubleshoot
```

Collects what someone helping you would ask for (versions, health check results, the agent's state and logs, Docker and Seylo's containers, the node's config), removes secrets and uploads it. You get a link like `https://seylo.dev/l/<id>` to paste into an issue or a chat, and when it expires.

- Tokens, keys, passwords (also inside URLs and `KEY=value` lines), setup links, private keys and email addresses are replaced with `[REDACTED]` before anything leaves the node. `--redact-ips` also replaces public IP addresses; `--keep-emails` keeps email addresses.
- `--include-service-logs` adds the last lines of every service's logs.
- `--dry-run` (or `--print`) prints the report instead of uploading it, so you can read it first.
- The upload is refused if the report still contains something that looks like a secret. Nothing is stored in that case.
- The site takes a limited amount of reports per day from everyone together. When that is used up, the upload fails with `HTTP 503` until 00:00 UTC; `--dry-run` still prints the report, so you can paste it instead.
- Anyone with the link can read the report. It is not indexed by search engines and is deleted after 30 days.
- The upload goes to `seylo.dev`, which redirects it to `api.seylo.dev`, so the node needs outbound HTTPS to both. The link opens on `api.seylo.dev` as well.

## Common problems

<Accordions>
<Accordion title="The setup link expired">
The link from the installer is valid for one hour and works once. On the panel's node, `seylo panel setup-link` writes a new one and prints it. Once the owner account exists, sign in instead.
</Accordion>

<Accordion title="A node shows as offline">
Run `seylo status` on the node. If the agent runs but is not connected, the error line says why. Check that the node can reach the panel's address (`curl -I https://panel.example.com/api/health`). The address the node uses is `panel_url` in `/var/lib/seylo/config.yml`. Services on an offline node keep running; only changes wait.
</Accordion>

<Accordion title="The certificate for a domain is not issued">
The domain must point at the node that runs the service, and port 80 must reach the node from the internet, because Let's Encrypt checks over HTTP. Behind Cloudflare's proxy, set SSL/TLS to Full (strict) and turn off Always Use HTTPS, which sends that check to HTTPS. The domain's row on the **Domains** tab shows the DNS status and the last error from Let's Encrypt.
</Accordion>

<Accordion title="A deploy fails its health check">
The deploy log shows the check that failed and the app's last log lines. The usual causes: the app listens on a different port than the one set under **Advanced → Container → Ports**, it listens on `127.0.0.1` instead of `0.0.0.0`, or it needs longer to start than **Health timeout** allows. Your old version keeps serving while you fix it.
</Accordion>

<Accordion title="An app can't reach a database on another node">
Private networks don't span nodes. Expose the database with TLS and use `${{db.EXPOSED_URL}}`, or move the app to the database's node. The environment editor underlines internal addresses that point at another node.
</Accordion>

<Accordion title="Ports 80 or 443 are already in use">
Another web server (nginx, Apache, Caddy) holds them. The installer stops a panel install in that case and names the program; a join only warns. Stop and disable it (for example `systemctl disable --now nginx`), or move its sites into Seylo as services. On a Wings node that runs its own Traefik, Seylo shares it instead; see [Running next to Wings](/guides/running-next-to-wings). If Traefik keeps failing to start, the node raises a **Node health check failed** alert with Docker's error.
</Accordion>

<Accordion title="The join command says the panel is plain HTTP">
The agent refuses to join a panel at `http://` on another server, because its traffic (environment values, registry logins, shells) would be readable on the way. Copy the join command from **Add node** again: without a panel domain it uses `https://<panel IP>:3443` with `--pin`. If the panel was installed with `--agent-tls-port 0`, set a panel domain, or add `--insecure` to join over plain HTTP anyway.
</Accordion>

<Accordion title="A node did not move to the panel domain">
Look at the node's **Connects to** on **Nodes** and at its alerts. A node that joined over plain HTTP (`--insecure`) never moves by itself: run a new join command from **Add node** on it with `--force`. A node that could not move raises **Node health check failed** with the reason and tries again after an hour. When the reason is the certificate, the node does not trust the domain's certificate authority: use a public certificate (Let's Encrypt), or add the authority to the node's trust store and run `systemctl restart seylo`. See [Adding nodes](/guides/adding-nodes#when-the-panel-gets-a-domain).
</Accordion>

<Accordion title="An IP:port address does not answer">
With ufw or firewalld on, open the port: the panel shows the command next to the address, and the node health check lists every closed one. Cloud firewalls need the same port. See [Firewalls](/installation#firewalls).
</Accordion>

<Accordion title="The database web UI or a Box does not open">
Both are opened through the node's wildcard domain. Set a **Wildcard domain** on the node and point the wildcard record at it.
</Accordion>

<Accordion title="Maintenance pages or tool links fail after turning on ufw">
Traefik reaches the agent's edge listener on port 5756 over the `seylo-edge` Docker network. The installer allows it when ufw is active at install time; if you turned ufw on later, run `ufw allow in on seylo-edge to any port 5756 proto tcp`.
</Accordion>

<Accordion title="Pushes to GitHub don't deploy">
Check that **Deploy on push** is on (**Source** tab) and look at **Recent deliveries**. GitHub must reach the panel to deliver webhooks, which needs a panel domain. Without one, the panel still finds new commits by asking GitHub once a minute. New in 0.2: a delivery can also be skipped on purpose: by `[skip ci]` or `[skip cd]` in the head commit message, or by the service's [watch paths](/guides/watch-paths). **Recent deliveries** says which.
</Accordion>

<Accordion title="Pushes to GitLab, Gitea or Bitbucket don't deploy">
New in 0.2. Look at the **Webhook** part of the **Source** tab. When the webhook could not be created, it says why, and the panel polls the branch every minute meanwhile. A GitLab webhook needs the panel domain, because GitLab sends its secret in clear. Once you set the domain, click **Create webhook again**. If deliveries arrive but are refused, **Recent deliveries** shows the reason, for example a signature that did not match. See [GitLab, Gitea and Bitbucket](/guides/git-providers#the-webhook).
</Accordion>

<Accordion title="Docker Hub is rate limiting this panel">
New in 0.2. Docker Hub limits anonymous requests per address. The panel stops asking until the limit lifts, and answers it already has stay cached. Add a Docker Hub login so the panel reads images with that account's limit; see [Deploy from Docker Hub](/guides/docker-hub#pull-limits-and-private-images).
</Accordion>

<Accordion title="Everyone was signed out after the update to 0.2">
Expected, once. Sessions made before 0.2 have no session key, so the panel asks everyone to sign in again. API keys and MCP tokens keep working. See [Upgrading from 0.1](/self-hosting/upgrading-from-0-1).
</Accordion>

<Accordion title="The sign-in page says the browser sent two session cookies">
New in 0.2. Another site on the same address set a second session cookie, so the panel uses neither. Clear the browser's cookies for the panel's address and sign in again. See [Sessions](/people/sign-in-and-security#sessions).
</Accordion>

<Accordion title="Sign-in offers no recovery code">
New in 0.2. The account has no unused recovery codes: they were used up, or `seylo panel rotate-key` deleted them. The sign-in step then takes only a code from the authenticator app and says "This account has no recovery codes left." Sign in with the app and make new codes in **Settings → Security**. Without the app, an owner can remove the account and invite the person again. See [Authenticator app](/people/sign-in-and-security#authenticator-app-2fa).
</Accordion>

<Accordion title="Every node went offline after reinstalling the panel">
New in 0.2. Nodes remember the panel they joined and refuse a panel installed from scratch, a restored `panel.db` of another panel, or a panel after a master key rotation with `--new-panel-identity`. `seylo logs` on a node says "answers as another panel" or "answers with another panel identity key". Join each node again with a new command from **Add node** and `--force` added. After a key rotation, `seylo panel rotate-key` printed the exact command for each node, with the new pin. `--force` keeps the node's own settings in `/var/lib/seylo/config.yml`. See [The panel's identity](/guides/adding-nodes#the-panels-identity).
</Accordion>

<Accordion title="A Git source is refused as an internal address">
New in 0.2. Git servers on private, loopback or link-local addresses, a node's own private address included, and git servers on any of the panel's nodes, public addresses included, work in a project only after an owner or admin saved a source with that host there; then the project's members can use it too. Ask one to save the source once. When the deploy fails with "the node refused to connect to ...", the node found an internal address that the panel did not see, usually a name that resolves to a public address at the panel and to a private one on the nodes, or one of the node's own addresses. When the deploy fails with "does not resolve from the panel" after the update, the source uses a LAN-only name the upgrade did not record. In each case an owner or admin allows the host: **Allow this host for `<project>`** under the failed deployment, **Internal git hosts** in the project's **Settings** tab, or `git.allowInternalHost` (see [Allowing a host by hand](/guides/github-and-git#allowing-a-host-by-hand)). A URL with a user name or token in it is refused as well: add a git credential instead. See [Git servers on private addresses](/guides/github-and-git#git-servers-on-private-addresses).
</Accordion>

<Accordion title='A git clone fails with "the node cannot resolve"'>
New in 0.2. The node clones through its HTTP proxy (`HTTPS_PROXY` in the agent's environment) and its own DNS does not know the git host, so it cannot check where the proxy would connect, and refuses. An owner or admin can allow the host in the project, or, when the node relies on its proxy to resolve names, root on the node sets `git_proxy_resolves: true` in `/var/lib/seylo/config.yml` and runs `systemctl restart seylo`. See [Git servers on private addresses](/guides/github-and-git#git-servers-on-private-addresses).
</Accordion>

<Accordion title="A node was skipped in an update run">
The node was offline when its turn came. Since 0.2 the panel updates it in a run of its own when it reconnects; **History** in **Settings → Updates** shows that run as started by **Node came back**, and hovering the skipped step says what became of the node. A node that had rolled that release back is not retried by itself: **Update now** on **Nodes** installs it. See [Nodes that were offline](/self-hosting/updates#nodes-that-were-offline).
</Accordion>

<Accordion title='Backups fail with "too old for backups"'>
New in 0.2. The panel no longer gives nodes a backup destination's keys, and agents before 0.2 cannot back up or restore without them. Update the node (**Update now** on **Nodes**), then run the backup again. The panel itself must reach the bucket too; **Test** on the destination checks that. See [Backups](/guides/backups).
</Accordion>

<Accordion title="A new node never builds">
New in 0.2. Nodes start with **Build images on this node** off, also when joined with `--can-build`; only the panel's own node from the installer starts with it on. An owner or admin turns it on in the node's settings (see [Node settings](/guides/adding-nodes#node-settings)). Builds that fail with "docker buildx is not installed on this node" need Docker's `docker-buildx-plugin` package on the build node.
</Accordion>

<Accordion title="Running the installer again stops: the node runs a newer release">
New in 0.2. `install.seylo.dev` serves the latest stable release, and the installer refuses to put an older agent on a node that runs a newer one, for example a pre-release or a release the panel updated it to. Update nodes from the panel, or re-run with `--version <that release>` to reinstall it, or with `--downgrade` to install the older one anyway. See [Installer options](/installation#installer-options).
</Accordion>

<Accordion title="An uptime check on a node's private address is down after the update">
New in 0.2. A private address passes only when it is a node's **Public address** as set in the node's settings, or when an admin allows internal targets in **Settings → General → Uptime checks**. The addresses a node detects about itself no longer count. See [Uptime checks](/features/uptime-checks#where-checks-run-from).
</Accordion>
</Accordions>
