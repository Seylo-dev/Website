All of these go through the node's agent over its connection to the panel. Nothing extra is exposed on the node, and each needs its own permission (view logs, console, shell, read or write files), so you can share logs with someone without giving them a shell.

## Logs

A service's **Logs** tab follows its output live: new lines appear as they are written, across restarts and deploys, with a marker where each new generation started. **Pause** holds the view while you read.

The node keeps the logs on disk, not the panel, so they survive deploys and restarts. How much it keeps is set per node: **Logs per service (MB)** and **Keep logs (days)** in the node's settings.

**Search** looks through every deploy's logs on the node, as plain text or, with the regex switch, as a regular expression. On a service that runs on several nodes, pick one node or **All nodes**; lines of an offline node are missing until it is back.

From a terminal, after [`seylo login`](/guides/command-line):

```bash
seylo logs acme-shop/web -f        # follow
seylo logs acme-shop/web -n 1000   # the last 1000 lines
```

Build and deploy logs are on the **Deployments** tab, in each deployment's log.

## Console and shell

Changed in 0.2.2: an app has one **Console** tab, with a **Console | Shell** switch in the terminal's header. Before, console and shell were two tabs.

- **Console** attaches to the container's main process: you see its recent output and then everything it writes, and what you type goes to its standard input, a line at a time. That is what REPLs and game-style servers expect. You can search, pause, clear and download the output.
- **Shell** opens a new shell inside the running container, as `docker exec -it` would, and shows which user and working folder it runs as.

The switch changes the mode in place: the open session closes and the other one opens in the same card. The mode is part of the address (`?mode=shell`), so a link or a reload keeps it, and the old `.../shell` address opens the Console tab in shell mode. The switch offers only the modes you may open: owners and admins both, members what was shared with them. With neither, the tab says so.

Changed in 0.2.9: the console follows its process across a restart. When the process exits (a restart, a crash or a deploy), the console keeps the output with the exit note, says "Waiting for the new process…" and attaches to the new one by itself: first after a second, then up to every 8 seconds, for up to 2 minutes. **Reconnect** next to it tries at once. After 2 minutes without a new process it stops, with **Reconnect**. Before, the console stopped at **Reconnect** right away. A shell that exits stays closed, since that is someone typing `exit`.

### On the Overview

New in 0.2.2: an app's **Overview** shows the same terminal as a card at the top, above **Deploys** (changed in 0.2.3: before, under it and shorter; **Last hour** moved to the right column, under **Domains**), with the switch and **Open full**, which opens the Console tab in the same mode. Changed in 0.2.6: on a wide screen the card is as tall as the cards beside it, at least 480 and at most 600 px. It waits for a running container ("The console opens once the app runs."), takes the keyboard focus only when you click it, and closes its connection when you leave the page. Once it shows, it stays: a restart or a crash keeps the output, with the exit note, and since 0.2.9 the card attaches to the new process by itself as above.

The card only watches until you type. Watching shows the console's output and, like reading logs, is not written to the activity log, so opening a service's page is not console use. The first line you send opens the console itself, which is in the activity log, and the line goes to it once it is ready. A shell opens only when you pick **Shell**, or click **Open shell** if you may open only the shell.

Databases have a **Database shell** instead, already signed in to `psql`, `mysql`, `mongosh` or `redis-cli`, and (new in 0.2) `valkey-cli`, `keydb-cli` or `clickhouse-client` (see [Databases](/guides/databases)).

For a root shell on the node itself rather than in a container, see [Host shell](/guides/host-shell) (new in 0.2, off until the owner turns it on).

Console and shell sessions end after 30 minutes without input or output.

## Volumes and files

The **Storage** tab lists the service's volumes. **Add volume** takes a name, a mount path in the container and an optional **Read only**; volumes are mounted on the next deploy. A volume lives at `/var/lib/seylo/services/<id>/volumes/<name>` on the node and stays across deploys. Removing a volume deletes its data on every node.

**Files** on a volume opens a file browser:

- list folders, open and edit text files, create folders,
- upload (up to 20 GiB per file) and download,
- rename or move, change permissions (octal, like `0644`),
- compress a selection to `.tar.gz` or `.zip`, and extract archives,
- delete files and folders.

Changes are live for the running service. Paths cannot escape the volume: `..` and symlinks pointing outside it are refused. On a service that runs on several nodes, each node keeps its own copy of every volume; pick the node in the file browser.

New in 0.2, so that nobody can leave a root-owned setuid program in a volume through the file browser:

- **Permissions** keep only the permission and sticky bits: setuid and setgid are dropped, so `4755` becomes `0755`. Writing or uploading over a setuid or setgid file drops those bits first. Archives were already extracted without them.
- New files and folders get the owner of their folder, so a volume a non-root container uses stays writable for it. In a folder owned by root they belong to `nobody` (65534) instead; root in the container still reads and writes them. A file you replace keeps its owner.
