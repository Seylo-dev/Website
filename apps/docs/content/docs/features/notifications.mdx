Things that need attention raise an **alert**: a crash, a failed deploy, a node going offline. Every alert is recorded in the panel's alert feed (the dashboard and each service's **Alerts** tab show the recent ones). Rules decide which alerts also go to a **channel**.

## Channels

Create a channel once in **Settings → Notifications**, then pick it in any alert rule:

| Channel | What it needs |
| --- | --- |
| Email | SMTP host, port and security, user name and password, from and to addresses |
| Webhook | A URL and an optional signing secret |
| Discord | A Discord webhook URL |
| Slack | A Slack incoming webhook URL |
| Telegram | A bot token and a chat ID |
| ntfy | Server URL, topic and an optional access token |
| Pushover | User key and app token |
| Gotify | Server URL and app token |

**Send test** sends a test message and says if it did not arrive. Secrets are stored encrypted. **Pick for new alert rules** adds the channel to new rules by default. The email channel is also what the panel uses to send invites.

Deliveries are retried when the receiver is down.

### Webhook format

A webhook channel `POST`s JSON:

```json
{
  "type": "alert",
  "event": "deploy_failed",
  "severity": "error",
  "title": "Deploy of api failed",
  "message": "The new version never became healthy. The previous version is still serving.",
  "link": "https://panel.example.com/p/...",
  "alertId": "...",
  "projectId": "...",
  "serviceId": "...",
  "nodeId": "...",
  "panel": { "name": "Seylo", "url": "https://panel.example.com" },
  "createdAt": "2026-11-05T10:00:00.000Z"
}
```

Every request carries `x-seylo-timestamp` (Unix seconds). With a signing secret it also carries `x-seylo-signature: sha256=<hex>`, the HMAC-SHA256 of `<timestamp>.<body>` with the secret. Check it before you trust the request.

## Events

| Event | When |
| --- | --- |
| Crash | A service crashed: exit code or out of memory, once per crash streak |
| Stopped after repeated crashes | The crash policy gave up |
| Deploy failed | A build error, a failed health check, or a node refused the new settings (see [Zero-downtime deploys](/features/zero-downtime-deploys#how-a-deploy-works)) |
| Deploy succeeded | A new version is live |
| Build failed | The image could not be built |
| Health check failing | A service runs but its health check fails |
| Domain or certificate problem | A certificate could not be issued or renewed |
| Uptime check down | An [uptime check](/features/uptime-checks) failed |
| Backup failed | A scheduled or manual backup did not finish |
| Cron job failed | A cron run exited with an error |
| Node offline | A node lost its connection to the panel for more than a minute |
| Node health check failed | A [node health check](/guides/node-health) found a problem |
| Disk above 85% | The disk that holds a node's data (`/var/lib/seylo`) or Docker's data is more than 85% full. Each node checks every 10 minutes and alerts once until use drops back to 85% or below; the line is fixed. |
| Cleanup ran | New in 0.2: a node cleaned up by itself, on its schedule or a full disk (see [Docker cleanup](/guides/docker-cleanup)). Off by default. |
| Cleanup failed | New in 0.2: a node's scheduled or disk-triggered cleanup did not finish |
| Update available | A new release, when auto-update is off |
| Update failed | The panel or a node could not update |
| Approval requested | An MCP client or the assistant asks to run something |
| Security change | Someone approved a command line sign-in, created an API key, added a passkey, linked GitHub for sign-in, set or changed a password, or turned off two-factor sign-in; or many wrong passwords or (new in 0.2) two-factor codes arrived for one account. See [Sign-in and security](/people/sign-in-and-security#security-alerts). New in 0.2: also when the owner allows [host shells](/guides/host-shell) on a node, and when someone opens one. |

The **Node health check failed** alert also covers what a node reports between checks: Docker not answering, Traefik failing to start (for example because another program holds port 80 or 443), low memory, a clock that drifted from the panel's, and a node that could not move to the panel's domain (see [Adding nodes](/guides/adding-nodes#when-the-panel-gets-a-domain)).

When the problem goes away (the service stays up, the check passes again), the alert is resolved.

The feed keeps an alert for 180 days after it was resolved. New in 0.2: alerts nothing resolves, such as deploy, build, backup, cleanup and update results, go 180 days after they were raised; before, they stayed for good.

## Rules

- **Default alerts** in **Settings → Notifications** set, per event, which channels are told, or **Feed only**. Every service uses these unless it has its own.
- A service's **Alerts** tab: turn off **Use the panel's default rules** to choose events and channels for that service only.

## Mutes

A mute stops notifications for everything, a project, a service or a node, optionally for one event only and until a time. Muted alerts are still recorded in the feed, marked muted. Mutes are set through the API (`alerts.mute`, see the [API reference](/api-reference)) or by an AI assistant you allow to.

## The app and push notifications

New in 0.2.7. The panel can be installed as an app on a phone or computer, and each person can get push notifications from it on their own devices, without a channel or another app in between.

### Turning it on

An owner or admin turns it on in **Settings → Notifications → App and push notifications**. The card says what it is for, and the switch stays disabled, with the reason under it, until all of these hold:

- The panel has a domain in **Settings → General**, and that domain is **Active** (it serves the panel over HTTPS with a trusted certificate).
- The page is open on that domain, `https://<your domain>`. On the panel's IP:port or its tailnet address the switch says to open the domain, with a link. Browsers only install apps and allow notifications on a secure address, and an installed app stays tied to the address it was installed from, so those addresses are not offered, a tailnet with HTTPS included.
- It is a browser signed in to the panel: not an API key, an MCP token or the assistant.

Turning it off works from anywhere and removes everyone's devices; with devices in use the panel asks first. While it is on, pushes pause by themselves when the domain stops working (two failed domain checks in a row) and start again when it works. A new domain removes the old one's devices, since their app and service worker live on the old address.

### Your devices and alerts

Each person sets their own in **Settings → Push notifications** (under Your account):

- **This device**: **Turn on** asks the browser for permission and adds this browser to your devices; **Turn off** removes it. **Send a test** sends a test push to each of your devices and says which ones took it. On iPhone and iPad, push works in the installed app only (iOS 16.4 or later): tap **Share**, then **Add to Home Screen**, open the panel from the Home Screen and turn push on there.
- **Install the app**: **Install** where the browser offers it (Chrome, Edge), otherwise the browser's menu (**Install app** or **Add to Home screen**). The app opens in its own window with the panel's name, colors and icon: an uploaded square PNG favicon of 192 pixels or more, or an SVG one, is used instead of the built-in icon.
- **Your devices**: every device that gets your pushes, with when it was added and last got one. Signing out on a device, or revoking its session in **Security**, removes it; so does a push service saying it is gone, or 5 failed sends in a row.
- **What reaches your devices**: a switch per event. Problems are on to start with; **Deploy succeeded**, **Cron job failed** and the cleanup events are off. **Node back online** is offered here as well.

You only get alerts for what you can see in the panel, checked when each alert is sent: a member gets their services' events, approvals they may decide and changes to their own sign-in methods and keys; owners and admins can also get node, update and panel access alerts. [Mutes](#mutes) silence pushes too. A tap on a notification opens the alert's page, in the app if it is open. A device gets at most 30 pushes in 10 minutes; the rest are in the alert feed.

### Privacy

Pushes go through the push service of the browser's maker: Google (Chrome, Edge on Android, most Android browsers), Mozilla (Firefox), Apple (Safari) or Microsoft (Edge on Windows). Each one is encrypted for its device ([RFC 8291](https://www.rfc-editor.org/rfc/rfc8291)), so the push service sees only when and how much, not what. The panel identifies itself with its own key and its domain, never a person's address, and posts only to those services' hosts: a device whose browser uses another push service cannot be added. The panel needs to reach them over HTTPS (outbound port 443).

Device addresses and keys are sealed with the master key. Rotating the master key with `--new-panel-identity` (a leaked `panel.db`) sets the panel's push key aside: on its next start the panel sends each device one last push, signed with that key, which makes the browser drop its subscription and says push notifications were reset; then it deletes those devices and the old key. Until that push reaches a device, a copy of `panel.db` together with the leaked `master.key` could still push to it, so start the panel again right after the rotation. People turn push on again on each device; push makes a new key by itself.
