title: Zero-downtime deploys
description: A new version only gets traffic after it passes its health check. Until then, the old one keeps serving.
---

## How a deploy works

1. **Clone and build.** For repository and upload sources: Railpack, Nixpacks or your Dockerfile, on a node that can build. Image sources skip this. A build waits for a free slot when its node already runs its **Builds at once** (see [Builds waiting for a slot](/guides/github-and-git#builds-waiting-for-a-slot)).
2. **Ship.** The node that runs the service pulls the image by digest from the panel's registry, through its own connection to the panel.
3. **Start.** The new version starts next to the old one, as a new container.
4. **Health check.** The check runs until it passes or the health timeout runs out.
5. **Switch traffic.** The route moves to the new container in one atomic step, the agent confirms the domain answers through the proxy, then stops the old container.

If the new version never passes within the health timeout, it is removed and the deploy is marked failed with the reason and the last log lines. The previous version stays live; nothing changes for your visitors.

New in 0.2, on nodes with the 0.2 agent:

- Each version of a service's settings gets its own copy of the config files (file mounts), so the previous version keeps its own files when a deploy fails, also after a later restart. Before, a failed deploy's files were already in place for the old version.
- If the agent stops or crashes during the health check (an agent update, `seylo restart`), it rolls the deploy back, and finishes that when it starts again, instead of adopting the unverified version as live and reporting success.

New in 0.2.1: IP:port addresses, such as the one a new app answers on before it has a domain, keep serving through a deploy too. They stay on the old version until the switch, and a connection that arrives during the switch waits up to 5 seconds for the new container instead of being dropped. In 0.2.0, requests to such an address could hang or be reset for about a second around each deploy.

The node also checks the new settings before it starts anything, for example that volume names are valid and that an image from the panel's registry belongs to this service. When it refuses them, the deploy fails at once with the node's reason ("The node refused the new settings: ...") and a **Deploy failed** alert, instead of waiting for the health timeout. The previous version keeps running, and the other services on that node are not affected.

Deploys of one service run one at a time; a deploy started while another runs waits in line. **Cancel deploy** in the service header stops one that has not switched yet.

## Health checks

**Advanced → Health check and deploys → Check**:

| Check | Healthy when |
| --- | --- |
| **Default: the image's HEALTHCHECK, else TCP** | Changed in 0.2.15: when the image declares a `HEALTHCHECK`, Docker calls the container healthy (see [The image's HEALTHCHECK](#the-images-healthcheck)). Otherwise the app accepts connections on its first port. A service without ports counts as healthy once it runs. |
| **TCP port** | A chosen port accepts connections |
| **HTTP request** | A request to a port and path answers with the **Expected status** (0 accepts any 2xx or 3xx). **Host header** is sent when set. |
| **Command in the container** | A command exits with code 0 |

For a custom check, also set **Every (s)**, **Timeout (s)**, **Grace after start (s)** (failures in this time do not count) and **Failures before unhealthy**. The same check keeps running after the deploy: a replica that turns unhealthy leaves the rotation while another replica is healthy, and the **Health checks fail** alert fires.

**Health timeout (s)** (default 300) is how long a new version may take to become healthy before the deploy fails. Since 0.2.15, at the default, a deploy that waits for the image's `HEALTHCHECK` waits longer when the image's start period needs it (see below).

<Callout type="warn">
Both versions run together for a few seconds. If your app migrates the database on start, keep migrations backward compatible, so the old version still works against the new schema until it stops.
</Callout>

### The image's HEALTHCHECK

New in 0.2.15. An app or compose member with no check of its own used to get TCP on its first port, which passes as soon as the app listens: a web image went healthy 1.2 seconds after it started, before it could serve, and an api whose boot migrations wait on a lock got traffic before they ran. Now, when the image declares a `HEALTHCHECK`, the deploy switches traffic only once Docker calls the new container healthy, and fails as soon as Docker calls it unhealthy, with the check's last output in the deploy error. The old version keeps serving.

- Docker runs the image's own command with its interval, timeout, start period and retries. Seylo reads the result; it never runs the command.
- After the deploy, the service's health state, its alerts and load balancing follow the same result.
- Images without a `HEALTHCHECK`, or with `HEALTHCHECK NONE`, keep TCP on the first port. A check you set (**TCP port**, **HTTP request** or **Command in the container**) still replaces the image's.
- At the default **Health timeout** of 300 seconds, the deploy waits at least the start period plus retries times (interval plus timeout), plus a minute, so an image with a 600 second start period gets about 12 minutes. A health timeout you set is used as set, and the deploy log says when it is shorter than the image's start period.

The **Health check and deploys** card says what applies, for example "Image HEALTHCHECK: `curl -f http://localhost:3000/health`, every 10s, start period 600s, 3 retries", or "TCP on port 3000". In the API and MCP, `services.get` returns `imageHealthCheck`.

It applies from each service's next deploy, on nodes with agent 0.2.15; older nodes keep the TCP check. Databases, Boxes and cron services are unchanged, and so are compose members whose file turns health checks off (`healthcheck: disable: true`). Nothing running is restarted by the update.

### Nothing listens on the port

New app services get port 80, and without a check of their own a deploy waits for TCP on that port. A background worker, such as a Dockerfile app with no domain that never serves on a port, used to fail after the whole 5 minute health timeout with only "not healthy after 5m0s: health check never passed: tcp check on port 80: ... connection refused". Changed in 0.2.15, on nodes with agent 0.2.15: when that check was refused on every try, the error goes on:

```text
Nothing in the container listens on port 80. If this service does not serve on a port (a background worker), remove the port under Ports in the Container section of the service's Advanced tab (no domain uses it), or set a check that fits it under Health check and deploys on the same tab. If it does serve, it must listen on port 80 on all addresses (0.0.0.0), not only on 127.0.0.1.
```

A compose member is pointed at its stack's compose file instead, and a service whose domains use the port is told the app must listen there. A check that timed out, an HTTP or command check, and a TCP check you set keep the plain error. Nothing about the defaults or the check changed: the deploy still fails until the port goes or a check that fits is set.

## Stop the old version first

Both versions mount the same volumes while they overlap. Apps that cannot run twice, such as ones holding a file lock (SQLite in rollback-journal mode, some search indexes), should use **Deploy strategy → Stop the old version first**. It trades the zero-downtime switch for a short gap.

## Init process

New in 0.2.15. Apps, compose members and cron jobs ran their program as PID 1, where Linux ignores the signals it has no handler for and nothing reaps the zombie processes it leaves behind. An app started through a wrapper could miss the stop signal and be killed only when the stop timeout ran out. Now their containers run Docker's init (`docker run --init`: Tini as PID 1), which passes SIGTERM and the other signals on to the app and reaps zombies.

**Advanced → Container → Init process** picks:

| Setting | What it does |
| --- | --- |
| **Auto** (default) | Tini runs as PID 1, except for images that run their own init as PID 1 and must stay PID 1 (below) |
| **On** | Tini runs as PID 1, also in front of an image's own init |
| **Off** | No init: the app is PID 1 and handles signals and child processes itself |

**Auto** leaves the init off when the main program is an init of its own: the entrypoint (the service's or the image's) or, without one, the command, is `/init` (s6-overlay, as in linuxserver.io images), another `init` or systemd, tini, dumb-init, docker-init, catatonit or an s6 program. A compose member takes the file's `init:` (`true` or `false`) when it sets one, else **Auto**.

It applies from each service's next deploy, which makes new containers; the update restarts nothing. Nodes before agent 0.2.15 run without an init until they update and the service deploys again. Databases, Boxes and the panel run as before. In the API and MCP, `services.update` takes `container.init` (`auto`, `on` or `off`), and `services.get` returns it.

## Rolling back

The images of the last 5 successful deployments are kept. On the **Deployments** tab, pick one and click **Roll back**: its image runs again with the current settings and environment. Nothing is built, so it takes seconds.

A rollback is a deploy like any other: same health check, same switch. From a script, call `deployments.rollback` (see the [API reference](/api-reference)).
