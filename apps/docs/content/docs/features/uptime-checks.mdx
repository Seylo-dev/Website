---
title: Uptime checks
description: The panel requests a URL on an interval and alerts after several misses in a row.
---

An uptime check watches a service from the outside: the panel requests a URL on an interval, records whether it answered and how fast, and raises the **Uptime check down** alert after a number of misses in a row. When it answers again, the alert is resolved.

## Add a check

On a service's **Alerts** tab, under **Uptime checks**, click **Add check**:

| Field | What it does |
| --- | --- |
| **Name** | Shown in the list and in alerts |
| **URL** | The address to request, usually one of the service's domains |
| **Every (seconds)** | How often to request it, from 30 seconds to a day |
| **Expected status** | The status code that counts as up. 0 accepts any 2xx or 3xx. |
| **Misses before alert** | How many failures in a row raise the alert (1 to 10) |

The first request runs right away. Each check shows its status (**Up**, **Down**, **Pending**, **Paused**), its uptime over 24 hours, its average response time, its incidents and a response-time history. **Pause** stops a check without deleting its history.

The dashboard counts how many checks are up and down across everything you can see.

## Where checks run from

Checks run from the panel, not from the service's node, so they test the whole path a visitor takes. Redirects are not followed: a redirect counts by its own status code.

To keep checks from being used to probe your private network, the panel refuses targets on loopback, private (carrier-grade NAT included), link-local and reserved addresses and cloud metadata endpoints, also written as IPv6 addresses that carry an IPv4 one (IPv4-mapped, NAT64, 6to4), when you save the check and again before every request. Each request goes to the address the panel just checked, so a name server cannot answer one address to the check and another to the request. Public addresses are always allowed; a domain is judged by the address it resolves to, like any other name. An admin can allow internal targets in **Settings → General → Uptime checks → Allow checks of internal addresses**.

A private address also passes when it is a node's **Public address** as set in the node's settings (see [Node settings](/guides/adding-nodes#node-settings)), for clouds with 1:1 NAT where that is how people reach the node. New in 0.2: only that setting counts. The addresses a node's agent detects and reports about itself no longer make a private address pass, since a compromised node could report any address. A check aimed at such an address goes **Down** with the reason, until an admin sets the node's **Public address** to it or allows internal targets. The panel's own node gets its **Public address** from the address the setup link was opened at, when it knows no public one.

New in 0.2: **Check access** on a Git source does not follow these rules. Git servers on private addresses, a node's **Public address** included, and (new in 0.2.0-rc.2) git servers on any of a node's addresses need an owner or admin to allow them per project (see [Git servers on private addresses](/guides/github-and-git#git-servers-on-private-addresses)).

New in 0.2.0-rc.2: the panel's list of ranges is the same as the one nodes use for git connections, so it also refuses the documentation ranges (`192.0.2.0/24`, `198.51.100.0/24`, `203.0.113.0/24`, `2001:db8::/32`), 6to4 addresses that carry an internal IPv4 address, IPv4-compatible (`::/96`) and site-local (`fec0::/10`) IPv6 addresses, local-use NAT64 (`64:ff9b:1::/48`) and `100::/64`. A check aimed at one of them goes **Down** with the reason, like one on any other internal address.

A check on a name that does not resolve yet can be saved. Until the name resolves, the panel sends nothing and the check records "Not checked: the name did not resolve".
