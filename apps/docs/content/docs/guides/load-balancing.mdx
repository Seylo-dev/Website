---
title: Load balancing and replicas
description: Run an app on several nodes with several replicas each, and spread its traffic over all of them.
---

An app runs on one node by default, as one container. On its **Advanced** tab, **Replicas and nodes** lets you add nodes and set **Replicas** per node (1 to 32). The new replicas deploy right away.

The image is built once and shipped to every node, so all replicas run the same image.

## How traffic is spread

Each node's Traefik spreads requests over every healthy replica of the service, on its own node and on the others, so a domain pointed at any of the service's nodes reaches all of them. A replica whose health check fails leaves the rotation while another replica is healthy.

| Setting | What it does |
| --- | --- |
| **Entry node** | The node that takes the public traffic: point the service's domains at it, and its Traefik spreads requests over every node. Without one, each node balances the traffic that reaches it. |
| **Sticky sessions** | A visitor keeps reaching the same replica, with a cookie. New in 0.2: it also works on domains without HTTPS (the cookie is marked Secure only when every domain of the service uses HTTPS) |

Nodes forward traffic to each other over HTTPS on port **5757**, at the other node's **Public address** setting, else its public IPv4 address (else its public IPv6, else its private IPv4 when the nodes share a private network). The connection is mutual TLS: the panel issues each node a certificate from its own CA, and a node only accepts forwarded traffic from another node of the same panel. During an update run, a node whose agent is still on an older version can't present a certificate yet, so its `GET`, `HEAD` and `OPTIONS` requests fall back to the balancing node's own replicas until it updates.

New in 0.2: port 5757 only serves with that mutual TLS. The node's Traefik listens on it on every interface, so a node that has no certificate yet answers 404 there to everyone instead of taking any client. The panel issues each node's certificate when it connects, checks it every hour and renews it when fewer than 20 days are left. When it cannot issue one (for example after a restore with another `master.key`, so the CA's key does not open), the panel raises a **Node health check failed** alert for the node with the reason, and other nodes do not balance traffic to it until it has a certificate. The alert clears once it has one.

Each node has a certificate of its own, valid for 30 days instead of a year, so load balancing keeps working through at least 20 days of panel downtime; a longer one from before is replaced at once. A node checks that the node it forwards to answers with that node's own certificate, and every node gets the list of current nodes from the panel: when you remove a node, or its certificate is replaced, the others stop accepting its certificate as soon as they hear from the panel, instead of when it expires. Until every node runs the 0.2 agent, nodes still accept any certificate the panel's CA issued, as before the update.

Allow 5757 between your nodes only:

```bash
ufw allow from <other node IP> to any port 5757 proto tcp
```

## When a replica dies

New in 0.2: a request that fails on one replica is sent to the next one, up to 4 tries:

- A replica that can't be reached at all (its container just died, so nothing was sent) is skipped for every method, `POST` included.
- A 502, 503 or 504 answer is resent only for `GET`, `HEAD` and `OPTIONS` (with up to 1 MiB of body). Other methods are never replayed, because the app may already have acted on them: a `POST` that a node had already passed to its replica when that replica died fails once.
- With sticky sessions, a visitor whose replica died is served by the balancing node's other replicas, then by the other nodes'.

A replica that crashes leaves the rotation within about a second and comes back after its restart. Connecting to a replica gives up after 2 seconds on the same node and 3 seconds to another node, so a dead one never holds a request for long. Nodes do not yet check each other's health ahead of time.

## What does not spread

- **Volumes.** A service with volumes runs on one node, because each node would keep its own copy of the data. Use **Move** to change which node; see [Moving services](/guides/moving-services).
- **Private networks.** A project's network exists on each node separately. Replicas on several nodes need a database they can all reach: expose it with TLS and use `${{db.EXPOSED_URL}}` (see [Databases](/guides/databases)), not its internal address.
- **Compose stacks** stay on one node.
