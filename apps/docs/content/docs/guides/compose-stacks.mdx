description: Run a docker-compose file as a stack of services, each with its own logs, domains and deploys.

## Create a stack

In a project, click **Add a service → Compose stack** and paste a compose file, or point at one in a repository (GitHub or any Git URL, a branch and the file path). **Preview** shows what the file becomes before anything is created.

A Git URL follows the same rules as a **Git** source: `https://`, `ssh://` or `git@host:path`, with no user name or token inside it, and (new in 0.2) a git server on a private address, or on one of the panel's nodes, only once an owner or admin allowed it in the project (see [Git servers on private addresses](/guides/github-and-git#git-servers-on-private-addresses)). New in 0.2: the file is read by the node the stack runs on, or will run on, and never by another node, so **Preview** needs that node online.

The node's agent reads the file with compose-go, the parser Docker Compose itself uses, and the panel turns every compose service into a **member**: a service of its own with logs, domains, deploys, metrics, a console and a shell. There is no `docker compose` process on the node to look after.

```yaml title="compose.yml"
services:
  umami:
    image: ghcr.io/umami-software/umami:postgresql-v2.15.1
    environment:
      DATABASE_URL: postgres://umami:change-me@db:5432/umami
    depends_on: [db]
    ports:
      - "3000:3000"
  db:
    image: postgres:16
    environment:
      POSTGRES_USER: umami
      POSTGRES_PASSWORD: change-me
    volumes:
      - db:/var/lib/postgresql/data
volumes:
  db:
```

Members are named `<stack>-<service>` in the panel and keep their compose name on the project network, so `db:5432` works as it does in Compose. All members of a stack run on one node, because they can share volumes.

## Changing the file

The stack's **Compose file** tab holds the file. **Preview changes** lists what applying it would do to each member (**New**, **Changed**, **Deleted**, **Same**); **Apply** creates, updates and deletes members to match and deploys the changed ones. Deleting a member deletes its volumes, so the panel asks you to type the stack name first.

A member's environment comes from its `environment:` section. Change it in the file: edits on a member's **Environment** tab are replaced the next time the file is applied.

New in 0.2: since a pasted file holds every member's `environment:` values, the **Compose file** tab shows it only to people who may view variables (**View variables**) on the stack and all of its members; others see why it is hidden. Through the API, `compose.get` then returns the file empty with `fileHidden: true`. Applying a file that changes a member's environment needs **Edit variables** on the stack, and one that adds or changes members needs **Deploy**.

`${VAR}` in the file is filled from the stack's own variables. The panel has no screen for those yet; set them with the API (`env.set` on the stack), or write the values into the file. A variable that is not set becomes empty, with a warning.

## What is different from plain Compose

The preview warns about everything that does not run as written:

- `ports:` are not published on the host. A published TCP port becomes IP:port access that closes once a domain is live; add domains per member on its **Domains** tab. UDP ports are not supported yet.
- `build:` works for stacks from a repository, built like any app on a node that can build. Pasted files need `image:`.
- Named volumes live under `/var/lib/seylo/services/<id>/volumes` with the rest of the node's data, so they show up in **Files** and can be backed up.
- Custom and external networks are replaced by the project's private network.
- Not supported: bind mounts (including the Docker socket), `env_file`, external volumes, secrets and configs read from files, `network_mode: host`, `privileged`, devices and GPUs, `volumes_from`.
- `cap_add`, `sysctls`, volume drivers and host namespaces are ignored.

New in 0.2.15, from each member's next deploy:

- A member with no `healthcheck:` of its own gets traffic once Docker calls its image's `HEALTHCHECK` healthy, on nodes with agent 0.2.15; a `healthcheck:` in the file still replaces it, and `healthcheck: disable: true` keeps the TCP check on the first port, as before. See [The image's HEALTHCHECK](/features/zero-downtime-deploys#the-images-healthcheck).
- Members run with Docker's init (Tini) unless their image runs its own init; `init: true` or `init: false` in the file decides instead. See [Init process](/features/zero-downtime-deploys#init-process).
- Members get `NODE_ENV=production` unless their `environment:` or the project's shared variables set `NODE_ENV`. See [NODE_ENV for apps](/guides/environment-variables#node_env-for-apps).

Moving a stack to another node is coming later, and so is [exporting](/guides/export-and-import) a stack or one of its members (new in 0.2.10 for other services).
