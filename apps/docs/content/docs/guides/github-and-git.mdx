An app's **Source** tab says where its code comes from. Changes there apply on the next deploy.

| Source | What it is |
| --- | --- |
| **GitHub** | A repository through the panel's own GitHub App or (new in 0.2.2) its [connected GitHub account](#the-connected-github-account) |
| **GitLab**, **Gitea**, **Bitbucket** | New in 0.2: a repository through a connection with an access token, see [GitLab, Gitea and Bitbucket](/guides/git-providers). Changed in 0.2.6: their cards show once a connection exists (or the service already uses one) |
| **Git** | Any git URL, with a [git credential](#git-credentials) for private repositories |
| **Docker image** | A ready image from a registry, see [Images and uploads](/guides/images-and-uploads), or (new in 0.2) one found on [Docker Hub](/guides/docker-hub) |
| **Dockerfile** | A Dockerfile typed in the panel, see [Images and uploads](/guides/images-and-uploads) |
| **Upload** | A `.tar.gz` of your code, see [Images and uploads](/guides/images-and-uploads) |

## In the New app dialog

New in 0.2.2. **Add a service → App** (or the **+** next to a project in the sidebar, then **App**) opens **New app** with four source tabs: **Docker image**, **GitHub**, **Git repository** and **Set up later**.

### The GitHub tab

One **Repository** field takes `owner/repo` or a github.com address: `https://`, `ssh://`, `git@github.com:` or `github.com/owner/repo` without a scheme, with or without `.git`. **Browse** lists the repositories of every GitHub App installation that is not suspended and of the connected GitHub account (**Connected account · @login**), by connection, marked **Private** or **Public**, with a search. A page address such as `https://github.com/acme/shop/tree/main/apps/web` gives the repository and the branch, here `main`. **Branch** suggests the repository's branches and follows its default branch until you edit it; a branch you picked for one repository is dropped when you change the repository.

A line under the field says what the app becomes:

| The line | What gets created |
| --- | --- |
| From your GitHub App (acme) - deploys on push | A **GitHub** source through that installation, with **Deploy on push** on |
| From the connected GitHub account (@login) - deploys on push | A **GitHub** source through the [connected account](#the-connected-github-account), with **Deploy on push** on |
| Public GitHub repository github.com/acme/shop | A **Git** source cloned as public, without deploy on push |
| Not in your GitHub App (acme) - cloned as public. Private? Give the App access first. | The same: the App cannot read it |
| Not a repository of the connected GitHub account (@login) - cloned as public. | The same: it is not one of the account's own repositories |
| Could not check your GitHub App (acme). ... | Nothing yet: GitHub did not answer or rate limited the token. **Try again** checks it again. |

A typed repository is looked up by its exact name, through each installation first, then the account. The account only takes its own repositories: private ones, ones it may push to or administer, and ones in its list. Someone else's public repository becomes a plain git URL, so the app never follows that person's pushes.

While nothing on GitHub is connected, the tab shows owners and admins three steps instead of the field: open **Settings → GitHub**, create the GitHub App and install it on your account or organization (or connect a GitHub account, or paste a token), then come back and pick a repository, with **Open Settings > GitHub**. Members are told instead to ask an owner or admin, and that a public repository works from the **Git repository** tab.

Connecting a repository needs the right to change services in the project. A member without it can still type a public repository, which becomes a plain git URL.

### The Git repository tab

A plain **Repository URL** field for any host: `https://`, `ssh://`, `git@host:path`, or a host and path without a scheme such as `gitlab.com/team/app`. It never looks anything up in the App, the connected account or a git provider: the app always gets a **Git** source without a credential and without deploy on push. A github.com URL says "Private? Use the GitHub tab". GitLab, Gitea and Bitbucket repositories are connected on the app's **Source** tab after you create it (see [GitLab, Gitea and Bitbucket](/guides/git-providers#connect-a-repository)), and a credential for a private repository is picked there too.

An SSH URL that becomes a **Git** source (always on the **Git repository** tab, and on the **GitHub** tab when no connection reads the repository) creates the app without the first deploy, and **Deploy right away** is greyed out, since the repository needs a deploy key first: add a [git credential](#git-credentials) on the **Source** tab, then deploy.

### Port

New in 0.2.2: **Port** starts at 80. On the **Docker image** tab it takes the port the image exposes when Docker Hub knows it; a port you typed stays when you change the image or the tab. An app built from a repository gets the port as `PORT` too (see [PORT for built apps](/guides/environment-variables#port-for-built-apps)). **Set up later** creates an empty app with no port; add one under **Advanced → Container** once it has a source.

With **Deploy right away** ticked, **Create** starts the first deploy.

## GitHub

### Create the panel's GitHub App

**Settings → GitHub → Create on GitHub** creates a GitHub App that belongs to you, through GitHub's manifest flow: the panel prepares the App with the permissions it needs and a webhook URL, you confirm it on github.com, and GitHub sends you back with the App's keys. Pick an **Organization** to create the App under an organization you own instead of your personal account.

Then install the App on the accounts and organizations whose repositories you want to deploy (**Install on another account**). The **Installations** list shows where it can read; **Change on GitHub** changes which repositories it sees.

The panel needs an address GitHub can reach: set a panel domain in **Settings → General** first. The App's webhook delivers pushes and pull requests to `https://<panel>/api/hooks/github`; every delivery is signature-checked.

### Connect a repository

Pick the repository in the [New app dialog](#the-github-tab), or on the app's **Source** tab: pick **GitHub**, then the **Account** (an installation, or **@login (connected account)**), the repository and the branch, and click **Connect repository**. New in 0.2.3: the Source tab's repository field also takes a GitHub link or `owner/repo`, like the New app dialog. The repository is looked up by name through the picked account, so one the list does not show (an organization's, or past the first page) works too, and it is offered on top as **Use this repository**; a page address such as `.../tree/v2` picks that branch. Enter picks it. When the account cannot read it, GitHub's answer shows under the field; text that only filters the list (`acme/shop` for `acme/shop-api`) is a search and shows none. With an App installation picked, a repository of another owner is not looked up through it: the field names the **Account** that reads that owner's repositories. Also new in 0.2.3: the App refuses a public repository its installation does not include (`NOT_FOUND`, reason `notOwned`), since the App's webhook would never send its pushes; before, any public repository connected through any installation. **Root directory** in the **Build** section builds a folder inside the repository instead of its root, for monorepos.

### The connected GitHub account

**Settings → GitHub → Private repositories without the App** connects one GitHub account for the whole panel, for repositories the App cannot reach. Changed in 0.2.2: it is a source of its own, like an installation. Its token lists the account's repositories in **Browse** and the Source tab's **Account** picker, reads their branches, clones them and follows their pushes. In 0.2.1 it only cloned, as a credential on a **Git** source. It is opt-in, and the App is still the better choice: it only sees the repositories you pick.

Owners and admins connect it in one of two ways:

- **Connect a GitHub account**: the device flow, like `gh auth login`. It needs the panel's GitHub sign-in to be set up; otherwise the page says so, and a token still works.
- **Use a token** (new in 0.2.2): paste a personal access token from [github.com/settings/tokens](https://github.com/settings/tokens). Either fine-grained, with **Contents: Read** and **Metadata: Read** on the repositories you deploy, plus **Webhooks: Read and write** for push-to-deploy, or classic, with the `repo` scope. **Check and save** asks GitHub first: it must accept the token, a classic one must have `repo`, and a fine-grained one must reach a repository and read its contents. Otherwise it says what is missing and stores nothing.

The card then shows the login, how it was connected (**Device login** or **Personal access token**, and **Fine-grained**) and the scopes. The token is stored encrypted and never shown again. While an account is connected, the page offers only **Disconnect**. Through the API (`github.tokenConnect`, or the device flow), connecting again replaces the account in place, and the services that use it keep it.

**Whose token.** There is one connected account per panel, and every service that reads its repository through it uses that account's token, whoever set the service up. A build sends the token to the build node for that clone only, with the account's login as the git user; nothing is kept on the node. Members use it like an installation: only for a repository that a service of their project already deploys through it (see [below](#any-other-git-host)).

**Push to deploy.** Connecting a repository through the account creates a webhook on that repository with the account's token, for pushes and pull requests, at `https://<panel domain>/api/hooks/github-repo/<id>`, with a secret of its own that every delivery is checked against. That needs a panel domain, an account that administers the repository, and a token that may create webhooks: a device login or classic token with `repo`, or a fine-grained token with **Webhooks: Read and write**. Without them, the panel reads the branch every minute instead, and the Source tab says why, for example "The panel has no domain yet, so GitHub cannot reach it". With a working webhook it still reads the branch every 5 minutes, in case a delivery is lost. Once an hour the panel creates missing webhooks again, so a panel domain set later turns them on within the hour. Pull request previews need the webhook.

**Organizations.** An organization that restricts OAuth app access hides its private repositories from a device login until an organization owner approves the panel's app at `github.com/organizations/<org>/settings/oauth_application_policy`. Organizations can also require approval for fine-grained tokens. Until then, those repositories are missing from the lists. The GitHub App installed on the organization needs neither.

**Disconnect** removes the token and the webhooks it made. Services that read their repository through it fail to deploy until an account is connected again or they get another source; revoke the token on github.com too. An account connected after a Disconnect makes no webhooks by itself: those services poll their branch every minute until you connect their repository again on the **Source** tab. Connecting another GitHub login over the account through the API removes the old login's webhooks first, while the panel still has its token, and creates them again with the new one within the hour. When GitHub rate limits the token, lists and connects say so and ask you to try again, instead of reporting a missing repository.

Compose stacks cannot read their repository through the account yet: they use the App.

## Any other Git host

New in 0.2: GitLab, Gitea, Forgejo and Bitbucket Cloud have their own sources, with a webhook the panel creates, merge request previews and commit statuses: see [GitLab, Gitea and Bitbucket](/guides/git-providers). For any other host, or on 0.1, pick **Git** and enter the repository URL: `https://`, `ssh://` or `git@host:path`. Plain `http://` is not supported. **Check access** lists the branches it can see. For a private repository, pick a **Credential** (see [Git credentials](#git-credentials)):

- an HTTPS access token for the host, or
- an SSH key: the panel can generate an Ed25519 deploy key and give you the public half to add as a read-only deploy key on the repository.

New in 0.2.2: when a deploy of a plain **Git** URL on github.com, gitlab.com or bitbucket.org fails to clone and the source has no credential, the deployment says: "If the repository is private, connect it through GitHub on the Source tab, or pick a git credential there." (GitLab or Bitbucket for those hosts.)

New in 0.2: the URL itself never carries a secret. A user name or token in an `https://` URL (`https://user:token@host/...`), or a password in an `ssh://` URL, is refused when you save, and the form says so before you do: "Take the user name and token out of the URL: add them as a git credential and pick it below." `ssh://git@host/...` and `git@host:path` are fine. A source saved on 0.1 with a token in its URL keeps deploying, but the panel no longer shows that part, and saving the source again needs a credential instead.

A credential is tied to its host. The panel refuses a repository URL on another host for it, when you save the source and again at every deploy, and the build node's git only offers it to that host.

A member can only attach a credential (or a registry login, a GitHub App installation, the connected GitHub account or a git provider connection) to a project when they may manage it, or when a service of that project already uses it. New in 0.2: only for what that service uses it for, the same repository URL, image repository (any tag) or repository. So when an admin sets up one service with a token that reaches every repository of an account, members of the project can use it for that one repository; the repository pickers list only those for them. For another repository, ask an admin to set up the first service with it.

### Git credentials

New in 0.2.2: owners and admins add and manage git credentials in the panel. Before, only the API could create one.

- **Add credential** next to the **Credential** picker on the **Git** source form opens **Add a git credential**, filled in from the repository URL: the host, a name like `acme/shop-api`, and the kind the URL needs (a token for `https://`, an SSH key for `ssh://` and `git@host:path`). The new credential is picked right away.
- **Settings → Git providers → Git credentials** (the **Manage git credentials** link under the picker goes there) lists every credential with its kind, host, user name, when it was added and how many services use it, with **Add credential**, **Edit** and **Delete**. The connected GitHub account is managed on **Settings → GitHub**.

Members see neither; they pick from the credentials they may use (see above).

A **Token** has a name, the **Host** (with its port, if the URL names one), a **User name** (`git` by default; GitHub takes any user name with a token) and the token. The dialog says which token to create: on GitHub a fine-grained token with **Contents: Read-only** on the repository, on GitLab a project access token with `read_repository`, on Bitbucket a repository access token with **Repositories: Read** and the user name `x-token-auth`.

An **SSH key** is either **Generate a key**, which makes an Ed25519 key pair, keeps the private key and shows the public key with where to add it as a read-only deploy key, or **Paste a private key** (OpenSSH or PEM, without a passphrase). The panel trusts GitHub's host keys by itself. Any other host needs its host keys, so builds can trust it:

- **Read host keys** reads them from the host and shows their fingerprints. Compare them with the ones the host publishes before you save.
- Or **Paste known_hosts lines instead**. Each line must start with the host as ssh names it: the plain name on port 22, `[host]:port` on any other port. For `ssh://git@gitea.lan:2222/team/app.git` that is `[gitea.lan]:2222`, which `ssh-keyscan -p 2222 gitea.lan` prints. Hashed lines (`|1|...`) cannot be matched, and the panel refuses text that holds one. **Save** (or **Generate key**) waits until a line names the host.

The panel checks the same for API clients (`git.createCredential`, `git.generateSshKey`, `git.updateCredential`) and MCP clients (`git.generateSshKey`): known_hosts text with hashed lines, or with no line for the credential's host, is refused, so no credential is saved whose every clone over SSH would fail its host key check.

**Edit** renames a credential, replaces a token (left empty, the current one stays) and its user name, or sets an SSH key's host keys, and shows an SSH key's public key to add it to another repository. An SSH key for a host other than github.com with no line for that host shows **Host keys missing**. **Delete** is refused while a service clones with the credential: the dialog says how many do, so point their source at another credential first. On a **Git** source form, a credential deleted elsewhere shows as **Deleted credential**, and **Check access** and **Save** wait until you pick another.

The secret is stored encrypted, never shown again, and only ever sent to its own host.

### Git servers on private addresses

New in 0.2. Nodes clone as root inside their own network, so a git URL could reach machines only that network should see. A **Git** source, and a compose stack's git URL, must point at a public address. A host on a private, loopback, link-local or reserved address, or a name the panel cannot resolve, works in a project once an owner or admin has saved a source with that host in that project; from then on the project's members may use it too. A node's own private address counts as internal here, also when it is set as the node's **Public address**: a git server there needs an owner or admin like any other, although [uptime checks](/features/uptime-checks#where-checks-run-from) may reach it. Cloud metadata addresses never work. The panel checks when the source is saved and again right before each build, since a name can resolve somewhere else by then.

A host on one of the panel's nodes counts as internal too, public addresses included. That is a name set as a node's **Public address**, or a host whose every address is a node's: its **Public address**, the public IPv4 or IPv6 address it reports, or an address on its network interfaces. So a git server that runs on a node, reached by its public name, needs an owner or admin to save or allow it once per project, like one on a private network. A name that also resolves to an address of another server stays public.

The node checks too, since it looks the name up again. Every connection git makes on a 0.2 node, for a build or for a compose stack's file, goes through an address check in the agent on the address it really connects to, redirects included. Internal addresses pass only for the source's own host and port, and only when that host is allowed in the project; a redirect to another internal address is refused, and a cloud metadata address always is. The node also refuses its own addresses, public ones included, unless the host is allowed: a connection to them stays on the node, past a firewall that hides a service from the internet. A refused connection fails the deploy with the address and the reason, for example "the node refused to connect to gitea.lan:443: gitea.lan resolves to 10.0.0.7, a private address" or "... resolves to 203.0.113.10, an address of this node". For the source's own host the message ends with how an admin allows it, and the deploy log has a line `Refused a git connection to ...`.

A node that reaches the internet through an HTTP proxy (`HTTPS_PROXY`, `HTTP_PROXY` and `NO_PROXY` in the agent's environment) keeps cloning through it over https. The node checks what a name resolves to on the node before it asks the proxy, and the proxy's own rules decide the rest. Git goes only through `http://` and `https://` proxies, not SOCKS; ssh connects directly, as before.

A name the node itself cannot resolve (the name is not found, its name server fails, or nothing answers within 10 seconds) is refused before it goes to the proxy, since the node cannot check where the proxy would connect. The deploy fails with "the node cannot resolve `<name>`, so it cannot check where the agent's HTTP proxy would connect". There are two ways to let it through. An owner or admin allows the host in the project (see [Allowing a host by hand](#allowing-a-host-by-hand)), which covers the source's own host and port only. Or, on a node whose DNS knows no outside names and relies on its proxy to resolve them, root on the node sets this and restarts the agent (`systemctl restart seylo`):

```yaml title="/var/lib/seylo/config.yml"
git_proxy_resolves: true
```

With it, every name the node cannot resolve goes on to the proxy unchecked, for any host, redirects and submodules included, and the proxy's own rules decide where it connects. Only someone with root on the node can set it; the panel cannot. A re-join with `seylo join --force` keeps it.

#### Allowing a host by hand

Saving a source allows a host only when the panel itself sees it as internal. These hosts need an owner or admin to allow them by hand:

- A name that resolves to a public address at the panel and to a private one on the nodes (split-horizon DNS), for a **Git** source or a git provider connection. It looks public to the panel, so the nodes refuse it.
- A LAN-only name the panel cannot resolve, in a source saved before 0.2 (see [After the upgrade from 0.1](#after-the-upgrade-from-01)).
- A name a node behind an HTTP proxy cannot resolve itself, unless that node sets `git_proxy_resolves` (see above).

Owners and admins can do it from the web app:

- Under a failed deployment the node refused for its git host, on the **Deployments** tab: **Allow this host for `<project>`**, then **Allow host** to confirm, then deploy again. Saves by owners and admins are not refused for an internal host, so a split-horizon name or a name a proxied node cannot resolve shows up here.
- In the project's **Settings** tab, **Internal git hosts** lists every host allowed in the project, who allowed it (**Recorded on upgrade or by a removed account** when no account is named) and how many of the project's sources use it. GitHub sources count for `github.com` and GitLab, Gitea and Bitbucket sources for their connection's host, so **Remove** warns about their builds too. **Allow a host** takes a repository URL and allows its host and port. **Remove** stops allowing a host: the project's nodes then clone it from public addresses only, so builds of the sources on it fail until an admin allows it again.

When a member's save or **Check access** of a **Git** source is refused for its host, the form says that only an owner or admin can allow it, in the project's settings or by saving the source once. A host the panel cannot resolve gets its own note: check the address, and if only your network knows the name, an owner or admin can allow it. Owners and admins never see these notes, since their saves are not refused for an internal host.

From the API or an MCP client, [`git.allowInternalHost`](/api-reference/git/git.allowInternalHost) allows a host, [`git.listInternalHosts`](/api-reference/git/git.listInternalHosts) lists them and [`git.removeInternalHost`](/api-reference/git/git.removeInternalHost) takes one off:

```bash
curl -X POST https://panel.example.com/api/v1/git.allowInternalHost \
  -H "Authorization: Bearer $SEYLO_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"projectId": "<project id>", "url": "https://git.example.com/team/app.git"}'
```

It answers with the host as recorded for the project, for example `{"host": "git.example.com"}`, with the port when the URL names one (`10.0.0.7:3000`). Any host works except a cloud metadata address. From then on the project's nodes may clone that host from internal addresses, their own included, and its members may use it in their sources. Allowing and removing a host are in the activity log.

#### After the upgrade from 0.1

On its first start, 0.2 looks up the host of every git source that was already saved (services and compose stacks) and allows it in their projects only when the panel resolves it to an internal address (private, loopback, link-local or reserved) or to the addresses of its nodes, or when it is such an IP address. So an existing LAN git server with a name the panel resolves, a git server on a node, or an IP address, keeps building. A host on an address that only a node itself reports, such as one of its network interfaces, is checked again once that node runs the 0.2 agent, and allowed then for the sources that were saved before the update. Nothing else is recorded:

- Hosts that resolve to public addresses at the panel. They keep building from public addresses; a split-horizon one needs allowing by hand.
- Names the panel cannot resolve, LAN-only names included, whether its DNS said the name does not exist or did not answer within 20 seconds. Their builds fail after the update, also for sources an owner or admin saved, until an owner or admin allows the host in each project that uses it (see [Allowing a host by hand](#allowing-a-host-by-hand); saving the source again as an owner or admin works too). The panel's log (`seylo panel logs`) names each one: "a git host of an existing source does not resolve at the panel, so it was not recorded as an internal host".

Builds and **Check access** wait for these lookups after that first start. A service [moved to another project](/guides/clone-and-move#move-a-service-to-another-project) by an owner or admin takes its host along: the move allows it in the new project. A member's move of such a service is blocked until the host is allowed in the new project.

#### Check access

**Check access** is a request the panel makes itself, to the address it just checked. It follows the rule for saving a source: a public address, or a host allowed in the project, and owners and admins may check any internal host. A host on one of the panel's nodes counts as internal here too. A name the panel cannot resolve works only for owners and admins, and a cloud metadata address never works. The uptime setting **Allow checks of internal addresses** plays no part, and a node's **Public address** never opens a host up here.

## Builders

New in 0.2.6: the [New app dialog](#the-github-tab) asks **Build with** for a GitHub or Git repository, so the first deploy already builds the way you want; a GitHub repository with a Dockerfile at its root starts on **Dockerfile**. After that, the **Build** section on the Source tab picks how the image is built:

| Builder | What it does |
| --- | --- |
| **Railpack** | Detects the language and builds a small image. The default. |
| **Nixpacks** | The older detector, in maintenance mode upstream. |
| **Dockerfile** | Builds the Dockerfile in the repository. Set **Dockerfile path** and, for a multi-stage file, the **Target stage**. |

With Railpack and Nixpacks you can override the detected **Install command**, **Build command** and **Start command**; empty keeps the detected one.

The service's variables are available while it builds. Railpack and Dockerfile builds get every variable as a BuildKit secret (`RUN --mount=type=secret,id=NAME` in a Dockerfile), so no value ends up in the image; Dockerfile builds also get the variables that are not secret as build args (`ARG NAME`). Nixpacks writes the variables it builds with into the image, so it only gets the ones that are not secret. See [Secret variables](/guides/environment-variables#secret-variables) for how a variable counts as secret.

### Where builds run

Images are built once, on a node that can build, and pushed to a registry that runs on the panel's node. Every node pulls through its own connection to the panel, so the registry is never published on a port. The deploy log says where each image was built and where it was shipped.

**Build node** picks the node. **Automatic** uses the service's own node when it can build, otherwise the least busy one that can. Allow builds per node with **Build images on this node** in the node's settings, and limit **Builds at once** there; extra builds wait in a queue. Builds need Docker's buildx plugin on the build node: without it they fail with "docker buildx is not installed on this node", and the node's **Docker buildx** health check says so. New in 0.2.1: **Automatic** skips a node whose agent reports no docker buildx, and a **Build node** without it is refused with "`<node>` has no docker buildx. Install docker-buildx-plugin on it." When no online node has it, the deploy says which nodes lack it.

A build node gets the source, git credentials and build-time variables of every service it builds, from any project, and the images it pushes run on every node. Keep builds on only for nodes you trust like the panel. Changed in 0.2.1: whoever makes a join command chooses whether the new node builds, with **Build images on this node** in **Add node**, ticked by default (see [Build nodes](/guides/adding-nodes#build-nodes)). Since services build on their own node first, services on a node that joined with the default build there, not on the panel's node. In 0.2, new nodes started with builds off, except the panel's own node from the installer, until an owner or admin turned them on.

From the **Deployments** tab, a deployment's menu has **Redeploy this commit** and **Deploy without build cache**.

Changed in 0.2.2: a deployment without a commit message is titled from what it built, **Deploy from `<branch>`** or, for an upload, **Deploy from `<archive name>`**. A clone that failed keeps the branch it tried, also after you fix the branch. Titles never show the address of the panel's internal registry (`127.0.0.1:5755/...`) any more.

## Deploy on push

Turn on **Deploy on push** on the Source tab and every push to the branch deploys. With the GitHub App this comes from the App's webhook, and through the connected account from a webhook on the repository (see [Push to deploy](#the-connected-github-account)). When nothing delivers the pushes (no panel domain, or no working webhook on the repository), the panel asks GitHub for the head of each followed branch once a minute instead. Changed in 0.2.2: with a webhook it still asks every 5 minutes, in case a delivery was lost; before, every minute. **Recent deliveries** on the Source tab lists what GitHub sent, and for the App **Retry failed** asks GitHub to send failed ones again.

Deploys of one service run one at a time: a push while a deploy is running waits in line and starts when it is done. New in 0.2.3: a deploy you start waits for none. While one is in progress, **Deploy** in the service header says **Deploying**, and **Roll back** and the **Redeploy** items on the **Deployments** tab are off until it ends; **Cancel deploy** stops the one in progress. The API, the CLI and MCP get `409 CONFLICT` with reason `deployRunning` and the id of the deploy in progress. Before, each click queued another deploy behind the running one.

New in 0.2:

- A push whose head commit message contains `[skip ci]`, `[ci skip]`, `[skip cd]` or `[cd skip]` (any case) does not deploy. A pull request whose title contains one of them gets no preview deploy.
- **Watch paths** on the Source tab make a service deploy only when a push changes files it cares about, for monorepos. See [Watch paths](/guides/watch-paths).

### Deploy trigger URL

For other Git hosts and CI, **Deploy trigger** creates a secret URL that deploys the service on `POST`:

```bash
curl -X POST "https://panel.example.com/api/hooks/deploy/<token>?commit=<sha>"
```

`commit` is optional. The URL is shown once; **New URL** replaces it and the old one stops working.

New in 0.2: a call while a deploy from an earlier call still waits in line joins it, and that deploy builds the newer commit. Any other waiting deploy (a manual one, a rollback, a move) is left as it is, and the call queues its own deploy behind it. On 0.1, the call joined whatever waited, so its commit could go unbuilt.

New in 0.2: a call whose JSON body says what changed (a push payload in GitHub's, GitLab's or Gitea's shape, or `{"changedFiles": [...]}`) goes through the service's watch paths and the `[skip ci]` markers first; see [Watch paths](/guides/watch-paths#the-deploy-trigger-url).

## Pull request previews

On the **Previews** tab, turn on **Previews** and every open pull request against the deployed branch gets its own copy of the service, deployed on each push to the pull request and removed when it closes. Previews are for services that deploy from GitHub, and (new in 0.2) from GitLab (merge requests), Gitea and Bitbucket (see [GitLab, Gitea and Bitbucket](/guides/git-providers#merge-and-pull-request-previews)).

| Setting | What it does |
| --- | --- |
| **Domain pattern** | The preview's host name. `{pr}` and `{service}` are replaced. Empty uses the node's wildcard domain. |
| **Most at once** | How many previews may exist (default 5). The oldest goes first. |

Turning previews off removes the open ones.

<Callout type="warn" title="Same environment, same database">
Previews use the service's environment, so they talk to the same database, cache and APIs. Point them at test data before you turn previews on; the panel asks you to confirm this.
</Callout>
