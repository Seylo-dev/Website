An app's **Source** tab says where its code comes from. Changes there apply on the next deploy.

| Source | What it is |
| --- | --- |
| **GitHub** | A repository through the panel's own GitHub App |
| **GitLab**, **Gitea**, **Bitbucket** | New in 0.2: a repository through a connection with an access token, see [GitLab, Gitea and Bitbucket](/guides/git-providers) |
| **Git** | Any git URL, with a credential for private repositories |
| **Docker image** | A ready image from a registry, see [Images and uploads](/guides/images-and-uploads), or (new in 0.2) one found on [Docker Hub](/guides/docker-hub) |
| **Dockerfile** | A Dockerfile typed in the panel, see [Images and uploads](/guides/images-and-uploads) |
| **Upload** | A `.tar.gz` of your code, see [Images and uploads](/guides/images-and-uploads) |

## GitHub

### Create the panel's GitHub App

**Settings → GitHub → Create on GitHub** creates a GitHub App that belongs to you, through GitHub's manifest flow: the panel prepares the App with the permissions it needs and a webhook URL, you confirm it on github.com, and GitHub sends you back with the App's keys. Pick an **Organization** to create the App under an organization you own instead of your personal account.

Then install the App on the accounts and organizations whose repositories you want to deploy (**Install on another account**). The **Installations** list shows where it can read; **Change on GitHub** changes which repositories it sees.

The panel needs an address GitHub can reach: set a panel domain in **Settings → General** first. The App's webhook delivers pushes and pull requests to `https://<panel>/api/hooks/github`; every delivery is signature-checked.

### Connect a repository

On the app's **Source** tab pick **GitHub**, then the account, the repository and the branch, and click **Connect repository**. **Root directory** builds a folder inside the repository instead of its root, for monorepos.

### Private repositories without the App

**Settings → GitHub → Private repositories without the App** connects a GitHub account whose token clones private repositories, through the same device flow as `gh auth login`. It is opt-in, and the App is the better choice: it only sees the repositories you pick. This option needs the panel's GitHub sign-in to be set up; otherwise the page says so.

## Any other Git host

New in 0.2: GitLab, Gitea, Forgejo and Bitbucket Cloud have their own sources, with a webhook the panel creates, merge request previews and commit statuses: see [GitLab, Gitea and Bitbucket](/guides/git-providers). For any other host, or on 0.1, pick **Git** and enter the repository URL: `https://`, `ssh://` or `git@host:path`. Plain `http://` is not supported. **Check access** lists the branches it can see. For a private repository, pick a **Credential**:

- an HTTPS access token for the host, or
- an SSH key: the panel can generate an Ed25519 deploy key and give you the public half to add as a read-only deploy key on the repository.

New in 0.2: the URL itself never carries a secret. A user name or token in an `https://` URL (`https://user:token@host/...`), or a password in an `ssh://` URL, is refused when you save, and the form says so before you do: "Take the user name and token out of the URL: add them as a git credential and pick it below." `ssh://git@host/...` and `git@host:path` are fine. A source saved on 0.1 with a token in its URL keeps deploying, but the panel no longer shows that part, and saving the source again needs a credential instead.

A credential is tied to its host. The panel refuses a repository URL on another host for it, when you save the source and again at every deploy, and the build node's git only offers it to that host.

A member can only attach a credential (or a registry login, a GitHub App installation or a git provider connection) to a project when they may manage it, or when a service of that project already uses it. New in 0.2: only for what that service uses it for, the same repository URL, image repository (any tag) or repository. So when an admin sets up one service with a token that reaches every repository of an account, members of the project can use it for that one repository; the repository pickers list only those for them. For another repository, ask an admin to set up the first service with it.

<Callout title="Adding credentials">
The Source tab lets you pick stored credentials. Adding one is done through the API for now (`git.createCredential`, `git.generateSshKey`, see the [API reference](/api-reference)); a screen for it in Settings is coming later.
</Callout>

### Git servers on private addresses

New in 0.2. Nodes clone as root inside their own network, so a git URL could reach machines only that network should see. A **Git** source, and a compose stack's git URL, must point at a public address. A host on a private, loopback, link-local or reserved address, or a name the panel cannot resolve, works in a project once an owner or admin has saved a source with that host in that project; from then on the project's members may use it too. A node's own private address counts as internal here, also when it is set as the node's **Public address**: a git server there needs an owner or admin like any other, although [uptime checks](/features/uptime-checks#where-checks-run-from) may reach it. Cloud metadata addresses never work. The panel checks when the source is saved and again right before each build, since a name can resolve somewhere else by then.

The node checks too, since it looks the name up again. Every connection git makes on a 0.2 node, for a build or for a compose stack's file, goes through an address check in the agent on the address it really connects to, redirects included. Internal addresses pass only for the source's own host and port, and only when that host is allowed in the project; a redirect to another internal address is refused, and a cloud metadata address always is. A refused connection fails the deploy with the address and the reason, for example "the node refused to connect to gitea.lan:443: gitea.lan resolves to 10.0.0.7, a private address", and the deploy log has a line `Refused a git connection to ...`.

A node that reaches the internet through an HTTP proxy (`HTTPS_PROXY`, `HTTP_PROXY` and `NO_PROXY` in the agent's environment) keeps cloning through it over https. The node checks what a name resolves to on the node before it asks the proxy, and the proxy's own rules decide the rest. Git goes only through `http://` and `https://` proxies, not SOCKS; ssh connects directly, as before.

#### Split-horizon DNS

Saving a source allows a host only when the panel itself sees it as internal. A name that resolves to a public address at the panel and to a private one on the nodes looks public to the panel, so the nodes refuse it. An owner or admin allows such a host for a project with [`git.allowInternalHost`](/api-reference/git/git.allowInternalHost) (there is no button for it yet; it is also an MCP tool):

```bash
curl -X POST https://panel.example.com/api/v1/git.allowInternalHost \
  -H "Authorization: Bearer $SEYLO_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"projectId": "<project id>", "url": "https://git.example.com/team/app.git"}'
```

It answers with the host as recorded for the project, for example `{"host": "git.example.com"}`, with the port when the URL names one (`10.0.0.7:3000`). Any host works except a cloud metadata address. From then on the project's nodes may clone that host from internal addresses, and its members may use it in their sources. The call is in the activity log.

#### After the upgrade from 0.1

On its first start, 0.2 looks up the host of every git source that was already saved (services and compose stacks) and allows it in their projects when the panel sees it as internal: a private, loopback, link-local or reserved address, or a name the panel's DNS says does not exist (a LAN-only name). So an existing LAN git server keeps building. These are not recorded:

- Hosts that resolve to public addresses at the panel. They keep building from public addresses; a split-horizon one needs `git.allowInternalHost`.
- Hosts whose lookup failed in another way, for example a name server that did not answer within 20 seconds. The panel's log (`seylo panel logs`) names each one: "could not look up a git host while recording the internal hosts of existing sources". Allow them with `git.allowInternalHost`.

Builds and **Check access** wait for these lookups after that first start. A service [moved to another project](/guides/clone-and-move#move-a-service-to-another-project) does not take its host along: its next build needs the host allowed in the new project.

#### Check access

**Check access** is a request the panel makes itself, to the address it just checked. It follows the rule for saving a source: a public address, or a host allowed in the project, and owners and admins may check any internal host. A name the panel cannot resolve and a cloud metadata address never work. The uptime setting **Allow checks of internal addresses** and a node's **Public address** play no part.

## Builders

The **Build** section on the Source tab picks how the image is built:

| Builder | What it does |
| --- | --- |
| **Railpack** | Detects the language and builds a small image. The default. |
| **Nixpacks** | The older detector, in maintenance mode upstream. |
| **Dockerfile** | Builds the Dockerfile in the repository. Set **Dockerfile path** and, for a multi-stage file, the **Target stage**. |

With Railpack and Nixpacks you can override the detected **Install command**, **Build command** and **Start command**; empty keeps the detected one.

The service's variables are available while it builds. Railpack and Dockerfile builds get every variable as a BuildKit secret (`RUN --mount=type=secret,id=NAME` in a Dockerfile), so no value ends up in the image; Dockerfile builds also get the variables that are not secret as build args (`ARG NAME`). Nixpacks writes the variables it builds with into the image, so it only gets the ones that are not secret. See [Secret variables](/guides/environment-variables#secret-variables) for how a variable counts as secret.

### Where builds run

Images are built once, on a node that can build, and pushed to a registry that runs on the panel's node. Every node pulls through its own connection to the panel, so the registry is never published on a port. The deploy log says where each image was built and where it was shipped.

**Build node** picks the node. **Automatic** uses the service's own node when it can build, otherwise the least busy one that can. Allow builds per node with **Build images on this node** in the node's settings, and limit **Builds at once** there; extra builds wait in a queue.

From the **Deployments** tab, a deployment's menu has **Redeploy this commit** and **Deploy without build cache**.

## Deploy on push

Turn on **Deploy on push** on the Source tab and every push to the branch deploys. With the GitHub App this comes from the webhook. When GitHub cannot reach the panel (no domain, or a missed delivery), the panel also asks GitHub for the head of each followed branch once a minute. **Recent deliveries** on the Source tab lists what GitHub sent, and **Retry failed** asks GitHub to send failed ones again.

Deploys of one service run one at a time: a push while a deploy is running waits in line and starts when it is done.

New in 0.2:

- A push whose head commit message contains `[skip ci]`, `[ci skip]`, `[skip cd]` or `[cd skip]` (any case) does not deploy. A pull request whose title contains one of them gets no preview deploy.
- **Watch paths** on the Source tab make a service deploy only when a push changes files it cares about, for monorepos. See [Watch paths](/guides/watch-paths).

### Deploy trigger URL

For other Git hosts and CI, **Deploy trigger** creates a secret URL that deploys the service on `POST`:

```bash
curl -X POST "https://panel.example.com/api/hooks/deploy/<token>?commit=<sha>"
```

`commit` is optional. The URL is shown once; **New URL** replaces it and the old one stops working.

New in 0.2: a call whose JSON body says what changed (a push payload in GitHub's, GitLab's or Gitea's shape, or `{"changedFiles": [...]}`) goes through the service's watch paths and the `[skip ci]` markers first; see [Watch paths](/guides/watch-paths#the-deploy-trigger-url).

## Pull request previews

On the **Previews** tab, turn on **Previews** and every open pull request against the deployed branch gets its own copy of the service, deployed on each push to the pull request and removed when it closes. Previews are for services that deploy from GitHub, and (new in 0.2) from GitLab (merge requests), Gitea and Bitbucket (see [GitLab, Gitea and Bitbucket](/guides/git-providers#merge-and-pull-request-previews)).

| Setting | What it does |
| --- | --- |
| **Domain pattern** | The preview's host name. `{pr}` and `{service}` are replaced. Empty uses the node's wildcard domain. |
| **Most at once** | How many previews may exist (default 5). The oldest goes first. |

Turning previews off removes the open ones.

<Callout type="warn" title="Same environment, same database">
Previews use the service's environment, so they talk to the same database, cache and APIs. Point them at test data before you turn previews on; the panel asks you to confirm this.
</Callout>
