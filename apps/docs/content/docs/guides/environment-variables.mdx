## The editor

A service's **Environment** tab is a `.env` file in an editor: one `KEY=value` per line, `#` for comments, quotes for values with spaces or newlines. Values of variables that count as secrets (see [Secret variables](#secret-variables)), and the password in a URL, are hidden until you click **Show values**. Changed in 0.2.15: a variable with a framework's public prefix, such as `NEXT_PUBLIC_`, or a `# @public` comment shows its value, since every browser gets it, and a `# @secret` one is hidden. A **Secret** or **Public** chip after a line says how it counts (see [Secret and Public chips](#secret-and-public-chips)).

The editor checks the file as you type and underlines problems:

- syntax: a line without `=`, an invalid name, a quote that is never closed,
- a key set twice (the last value wins),
- a reference to a service or variable that does not exist, to the service itself, or one that loops back on itself,
- an internal address of a service that runs on another node, or that is not exposed (see below),
- new in 0.2.15: a service's address written out instead of its reference, and a reference the app would get as text (see [Hints for references](#hints-for-references)).
- new in 0.2.16: an index on a variable that is no list, or past the last domain of `DOMAINS` (see [DOMAINS](#domains)).

Syntax problems block saving; the others are saved and shown as warnings, or as a blue hint for an address written out.

The environment is stored encrypted. When two people edit at once, the second save is refused with **Someone else saved meanwhile** instead of silently overwriting the first.

## When new values apply

An app's deployment keeps the environment it started with. Saving new values does not touch the running version: they apply on the next deploy. That way a half-finished edit, or a failed deploy, never reaches the running app. Databases and Boxes take the new values on their next restart.

Changed in 0.2.15: after a save, the tab says the running instances keep the old values until the next deploy, and offers **Deploy**. Before, it said "Restart to apply them, or deploy" and offered **Restart**, but a restart starts the same containers again with the values of the last deploy, so nothing changed. Shared variables work the same way: services get new values on their next deploy, not on a restart.

From the command line, `seylo env set` and `seylo env unset` save and deploy in one step (`--no-deploy` only saves). See [Command line](/guides/command-line).

## PORT for built apps

New in 0.2.2. An app built from a repository (a GitHub, GitLab, Gitea, Bitbucket or Git source) gets `PORT=<its first port>` in the environment its deploy starts with. Changed in 0.2.3: one with no port gets the port its domains point at (its primary domain's), else `PORT=80`, so an app whose domain was added on 3000 keeps listening there. New domains, Cloudflare tunnels, previews, clones and the panel's port fields start from the same port, and the Overview shows it as **80/tcp, as PORT**. Railpack and Nixpacks start commands and most frameworks listen on `$PORT`, so the app listens where its domains and health check look. A `PORT` of your own wins, in the service's `.env` or in the project's shared variables. Images, Dockerfiles typed in the panel, uploads, compose members and cron services get none.

Changed in 0.2.3: every built app gets it, also apps created before 0.2.2. On 0.2.2 only apps created on 0.2.2 or later did, so an older Next.js app with no port kept listening on 3000 while its domain pointed at 80. Like every environment change, it applies on the next deploy. An app that must listen elsewhere sets its own `PORT` in its `.env`.

## GIT_SHA for builds from git

New in 0.2.14. A build from a repository (a GitHub, GitLab, Gitea, Bitbucket or Git source) gets `GIT_SHA`, the full 40-character commit the node checked out, whether the deploy came from a push, a branch head or a commit you picked:

- **Dockerfile:** `--build-arg GIT_SHA=<sha>`, read with `ARG GIT_SHA`. Easypanel passes the same build argument, so images written for it keep working. A Dockerfile without the `ARG` builds as before.
- **Railpack and Nixpacks:** `GIT_SHA` in the build environment.
- **The containers** of that deployment get `GIT_SHA=<sha>` in their environment. A restart keeps it, and a rollback or a move to another project runs with the commit of the image it runs again.

The build log shows `--> GIT_SHA=<sha>` before the build. A `GIT_SHA` of your own wins, at build and at runtime, in the service's `.env` or in the project's shared variables, also an empty one, and the build log says it came from your variables. A commit id there counts as a plain variable, not a secret (see [Secret variables](#secret-variables)), so a Dockerfile build gets it as a build argument; a `# @secret` comment above it makes it a secret, and then a Dockerfile's `ARG GIT_SHA` stays empty. Images, uploads and Dockerfiles typed in the panel have no commit, so they get none.

```dockerfile
ARG GIT_SHA
ENV APP_VERSION=$GIT_SHA
```

A service gets `GIT_SHA` from its next deploy after the update to 0.2.14. The build argument needs the node's agent from 0.2.14; a node on an older agent still gives the containers the environment variable.

## NODE_ENV for apps

New in 0.2.15. Every app gets `NODE_ENV=production` in its containers, the way an app built from a repository gets `PORT`: built from a repository, a Dockerfile or an upload, run from an image, a compose stack member or a pull request preview. A `NODE_ENV` of your own wins, whatever its value, also an empty one: in the service's `.env` (for a compose member, its `environment:` block) or in the project's shared variables. It also replaces a `NODE_ENV` the image sets itself (`ENV NODE_ENV=...`).

- **Builds** do not get it, so `npm ci` in a Dockerfile still installs devDependencies. A `NODE_ENV` you set reaches the build as before.
- **Databases, Boxes and cron services** get none.

Like every environment change, it applies on the next deploy. Apps that are running get it then, not on a restart, which keeps the environment the app was deployed with. An app that must run with another value sets `NODE_ENV` in its `.env` before its next deploy:

```bash
NODE_ENV=development
```

## References

Point at another service's values instead of copying them:

```bash
DATABASE_URL=${{db.INTERNAL_URL}}
API_BASE=${{api.URL}}
STRIPE_KEY=${{project.STRIPE_KEY}}
```

A reference is `${{<service>.<VARIABLE>}}`, where `<service>` is a service name in the same project and `<VARIABLE>` is one of its built-in variables or a key from its own `.env`. References are resolved on every deploy, so when a database password is reset or a domain changes, the next deploy picks it up. `${{project.<NAME>}}` reads the project's shared variables.

Hover a reference to see the value it becomes. The **References** panel lists everything this service can reference; click an entry to insert it. Internal addresses of services on other nodes are struck through there (see [In the References panel](#in-the-references-panel)).

A reference hands its value to your container, so you can only save one whose value you may see yourself: a member with access to one service can't read a sibling's API key or a database password by referencing it. The same rule applies to compose files and templates; a stack's or template's own services count as yours. A push to a compose stack's repository has no person behind it, so outside the stack it can only add references to other services' addresses, never to their secrets.

### The References panel

New in 0.2.15: the panel starts with the service you edit, marked **this service**, and its own built-in variables (see [Built-in variables](#built-in-variables)): `URL`, `DOMAIN`, `INTERNAL_URL`, `INTERNAL_HOST` and `INTERNAL_PORT` for an app, the connection set (`INTERNAL_URL`, `EXPOSED_URL`, `USER`, `PASSWORD`, ...) for a database. A click inserts `${{<its name>.DOMAIN}}` like any other reference, and the tip shows the value. Before, the panel listed the other services and the shared variables only, so a service's own domain could not be inserted from there. Its own `.env` keys are not listed: a reference to another line of the same file is refused, since it could loop back on itself, so write that value instead.

Also new in 0.2.15: a variable that is empty right now gets no chip. That is `URL` and `DOMAIN` of a service without a domain (the service you edit included), a database's `EXPOSED_*` while it is not exposed, and an empty shared variable. A service, or the shared variables, with nothing left is not listed. A value you may not see keeps its chip, such as another service's variables or a database password without access to its credentials. A reference typed by hand, such as `${{web.DOMAIN}}`, still works, and gets its value once the service has a domain.

The panel is never taller than the editor: its list scrolls inside it, by mouse wheel, keys or Tab, and its title and hint stay at the top. Each group (the service you edit, every other service, the shared variables) collapses and expands with a click on its header row, or Enter or Space. A group with more than 12 variables starts collapsed and shows how many it holds ("34 variables"); the service you edit and the other groups start expanded. **Expand all** and **Collapse all** in the header do every group. What you expand or collapse is remembered in this browser, per project. The panel is up to 440px wide (about 320px before) once the editor has 600px next to it; on a narrow screen it goes under the editor.

### Built-in variables

Every service offers these besides its own keys:

| Service | Variables |
| --- | --- |
| Apps, compose members and Boxes | `URL` (public URL of the primary domain), `DOMAIN` (its host), `DOMAINS` (new in 0.2.16: every domain's host, primary first, comma separated; see [DOMAINS](#domains)), `INTERNAL_URL` (`http://<service>:<port>` on the project network), `INTERNAL_HOST`, `INTERNAL_PORT` |
| Databases | `INTERNAL_URL` (connection URL on the project network), `INTERNAL_HOST`, `INTERNAL_PORT`, `EXPOSED_URL` (connection URL from anywhere, with TLS), `EXPOSED_HOST`, `EXPOSED_PORT`, `USER`, `PASSWORD`, `DATABASE`. ClickHouse (new in 0.2) also has `INTERNAL_HTTP_URL` (its HTTP interface, with the password) and `INTERNAL_HTTP_PORT`. |

`URL`, `DOMAIN` and `DOMAINS` are empty until the service has a domain; the `EXPOSED_*` variables until the database is exposed, and since 0.2.9 while an exposed Postgres, MySQL or MariaDB waits for its node's update (see [Closed until the node updates](/guides/databases#closed-until-the-node-updates)). The exposed URL has the database's own user and password.

New in 0.2.8: a service can reference its own built-in variables by its own name, for an app that must know its public address. n8n, for example:

```bash
N8N_HOST=${{automations.DOMAIN}}
WEBHOOK_URL=${{automations.URL}}
```

Its own `.env` keys stay out of reach that way (they are the lines of the same file): the editor marks `${{automations.SOME_KEY}}` as an error and says to write the value instead. Before 0.2.8 every reference to the service itself was an error and stayed unresolved. Since 0.2.15 the **References** panel lists the service's own built-in variables under **this service** (see [The References panel](#the-references-panel)).

### Every domain of a service: DOMAINS [#domains]

New in 0.2.16. `${{api.DOMAINS}}` lists every host the api service answers on, comma separated with no spaces: the primary domain first, then the others in the order the **Domains** tab lists them.

```bash
ALLOWED_HOSTS=${{api.DOMAINS}}          # api.example.com,www.example.com
WWW_HOST=${{api.DOMAINS[1]}}            # www.example.com
CALLBACK=https://${{api.DOMAINS[1]}}/v1 # https://www.example.com/v1
```

Redirect-only domains are left out, a host with several paths counts once, and a wildcard host is listed as written. It is empty while the service has no domain. Apps, compose members and Boxes have it, like `DOMAIN`.

`[n]` after the name picks one domain, counting from 0, so `DOMAINS[0]` is the primary domain, the same host as `DOMAIN`. It works inside a longer value too. In the editor:

- completions offer `DOMAINS[0]`, `DOMAINS[1]`, ... with their hosts when the service has two or more domains, the hover shows the host ("Item 2 of 2 in DOMAINS"), and the **References** panel has a `DOMAINS` chip,
- an index past the last domain gets an amber warning that says how many the service has, such as "api has 2 domains: DOMAINS[0] and DOMAINS[1]", and the value stays empty until it has that many,
- an index on a variable that is no list, such as `${{api.URL[1]}}`, is a red error, with a fix to `DOMAINS[1]` for `DOMAIN[1]`; the reference then stays as written,
- a broken index (`DOMAINS[-1]`, `DOMAINS[ 1 ]`, `DOMAINS[]`, `DOMAINS[1.5]`) is a syntax error and blocks the save.

The **Secret** and **Public** chips judge an indexed reference by its one item, as the panel does on save. As with `DOMAIN`, adding, removing or changing a domain shows in the **References** panel right away and reaches running containers on their next deploy; a restart keeps the old values. Shared variables take no references, so `${{api.DOMAINS[1]}}` is refused there like any other reference. When the service's own `.env` has a key named `DOMAINS`, other services that reference `${{api.DOMAINS}}` get the built-in list, as with every built-in name.

In the API and MCP, `env.references` marks the variable `list: true`, and `env.set`, `env.setVariable` and `env.analyze` return the diagnostics `not-a-list` (error) and `index-out-of-range` (warning); a broken index is `malformed-reference`.

## Hints for references

### An address written out

New in 0.2.15. A value that spells out a service's address gets a blue hint in the editor, with a quick fix to the reference that gives the same value and follows the address when it changes. With `api.example.com` as the api service's domain:

```bash
NEXT_PUBLIC_API=https://api.example.com/v1
```

gets "NEXT_PUBLIC_API can use `${{api.URL}}`", and **Use `${{api.URL}}`** makes it `NEXT_PUBLIC_API=${{api.URL}}/v1`. The hint covers:

- a service's `URL`, `INTERNAL_URL` or `EXPOSED_URL`, also followed by a path or a query,
- the service's own address, such as `${{web.URL}}` for `NEXTAUTH_URL` on the web service,
- a bare `DOMAIN` or `INTERNAL_HOST` as the whole value of a variable named for a host or a domain (`API_HOST`, `COOKIE_DOMAIN`, `ALLOWED_HOSTS`),
- new in 0.2.16: a service's domains written out in a variable named for hosts or domains, in the order of `DOMAINS` (`ALLOWED_HOSTS=api.example.com,www.example.com` can use `${{api.DOMAINS}}`; another order or a space after a comma is no match), and one of its other domains on its own (`WWW_HOST=www.example.com` can use `${{api.DOMAINS[1]}}`). The primary domain alone still gets `DOMAIN`.

A database's `EXPOSED_HOST` on its own is left alone, since it is often just the node's address. So are addresses many services share (`localhost`, an IP address), mail settings such as `MAIL_DOMAIN`, an address two services share, and plain words that happen to be a service's name.

Browser variables (`NEXT_PUBLIC_`, `VITE_`, `PUBLIC_`, `REACT_APP_`, `NUXT_PUBLIC_`, `EXPO_PUBLIC_`, `GATSBY_`, `VUE_APP_`) end up in code that runs in the visitor's browser, which cannot reach the project network, so `INTERNAL_URL` never works in them. For these the fix uses the public URL, also when the value was the internal address, and the hint says that a server-side variable can use `INTERNAL_URL` instead when both services share a node. When the service has no public address yet, the hint says the browser cannot reach it and has no fix.

The hint is not counted as a problem and does not block saving. In the API and MCP, `env.set`, `env.analyze` and `env.setVariable` return it as the diagnostic `hardcoded-reference` (severity `info`) with its fix. It names the key and the reference, never the value, so an AI tool can apply it with [`env.setVariable`](#set-one-variable-through-the-api) without seeing the value. A database URL with its password gets the hint only for people who may see the database's credentials, in the editor and in the API.

### References the app gets as text

New in 0.2.15. Two ways of writing a reference hand the app the text instead of the value, and get an amber warning with a quick fix:

| Written as | The app gets | Fix |
| --- | --- | --- |
| `API='${{api.URL}}'` | The text `${{api.URL}}`: single quotes keep a value as written | **Use double quotes** |
| `API=api.DOMAIN` | The text `api.DOMAIN` | **Use `${{api.DOMAIN}}`** |

For a name that is no service, such as `blabla.DOMAIN`, there is no wrap fix, only the closest service names when one is a typo away. A token counts only when the part after the dot is an exact variable name in capitals, so `example.com`, `api.domain`, `api.DOMAIN.com` and `https://api.DOMAIN` are left alone. Saving is never blocked, and the **Shared variables** sheet, which takes no references, shows neither warning. In the API and MCP, `env.set`, `env.analyze` and `env.setVariable` return them as `single-quoted-reference` and `bare-reference` (severity `warning`) with their fixes; they name the key, the token and the reference, never the rest of the value.

## Secret variables

Every value reaches the container the same way. Whether a variable is a secret matters where a value could be kept: crash reports and troubleshoot uploads strip secret values, Dockerfile builds never pass them as build args, and Nixpacks builds (which write their variables into the image) do not get them at all. A variable is a secret when its name contains `SECRET`, `TOKEN`, `PASS`, `KEY`, `PRIVATE`, `CREDENTIAL` or `DSN`, when its value is a URL with a password or a long random token, or when it references a secret (a database's `PASSWORD`, `INTERNAL_URL`, `INTERNAL_HTTP_URL` or `EXPOSED_URL`, or another service's secret). New in 0.2.14: the value of `GIT_SHA` is a commit id, so it never makes that variable a secret. A comment on the line above, or after the value, overrides the guess:

```bash
# @public
STRIPE_PUBLISHABLE_KEY=pk_live_51Hx...
SIGNUP_CODE=spring-2026 # @secret
```

### Framework public prefixes

New in 0.2.15. A variable whose name starts with a framework's public prefix is public, whatever its name or value says, since the framework ships its value to every browser:

| Prefix | Framework |
| --- | --- |
| `NEXT_PUBLIC_` | Next.js |
| `NUXT_PUBLIC_` | Nuxt |
| `EXPO_PUBLIC_` | Expo |
| `REACT_APP_` | Create React App |
| `VUE_APP_` | Vue CLI |
| `GATSBY_` | Gatsby |
| `VITE_` | Vite |
| `PUBLIC_` | SvelteKit, Astro |

Such a variable is a Dockerfile build argument, Nixpacks builds get it, and crash reports keep its value. Before, a name like `NEXT_PUBLIC_TURNSTILE_SITE_KEY` (KEY in it, a value that looks like a token) counted as a secret, so a Dockerfile's `ARG NEXT_PUBLIC_TURNSTILE_SITE_KEY` stayed empty and the build failed with "is a required build arg". Redeploy a service for its build to get them.

Two things still make one a secret: `# @secret` on the line above, and a password. A URL with a password (`PUBLIC_DATABASE_URL=postgres://user:pass@...`, as written or once its references resolve), or a reference to a database's `PASSWORD` or connection URL, also through another variable, keeps a variable a secret under any of these prefixes. Its **Secret** chip says why the prefix did not decide; `# @public` makes it public if the browser should get it.

### Secret and Public chips

New in 0.2.15. In the editor, a **Secret** chip follows each variable that builds and crash reports treat as a secret, and a **Public** chip follows one whose name or value looks secret but is public, by a framework prefix or a `# @public` comment. Hovering the chip or the name says why (its name, its value, a reference to another secret, a comment, the prefix), what it changes (a Dockerfile or Railpack build gets a secret only as a build secret, `RUN --mount=type=secret,id=NAME`, not as `ARG NAME`; Nixpacks does not get it; crash reports and troubleshoot uploads hide its value) and which comment changes it. In the API and MCP, `env.references` says `secret` for every variable of other services and every shared variable.

Changed in 0.2.16: an indexed reference such as `${{api.DOMAINS[1]}}` is judged by that one domain, not by the whole list, so the chip agrees with what the panel decides on save.

### A secret named by a Dockerfile ARG

New in 0.2.15, on nodes with agent 0.2.15. A Dockerfile build says when an `ARG` of the Dockerfile, in any stage, names a secret variable, since that `ARG` stays empty. The line comes before the build output, and again as the last line when a failed build's output mentions the name:

```text
--> TURNSTILE_SECRET is a secret, so the build gets it as a BuildKit secret (RUN --mount=type=secret,id=TURNSTILE_SECRET), not as ARG TURNSTILE_SECRET. If it is not secret, add "# @public" above it in the service's environment.
```

Read a real secret in the Dockerfile with `RUN --mount=type=secret,id=NAME` instead of `ARG`. The build log names variables, never their values.

## Set one variable through the API

New in 0.2.15. `env.setVariable` changes one variable of a service's environment and keeps the rest of the file as it is. It is for scripts and AI tools: `env.get` hides every value from models (MCP and the assistant), and `env.set` replaces the whole file, so changing one line with it meant wiping the values the tool could not see.

```bash
curl -X POST https://panel.example.com/api/v1/env.setVariable \
  -H "Authorization: Bearer $SEYLO_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"serviceId": "<service id>", "key": "LOG_LEVEL", "value": "debug"}'
```

- The last line with the key, the one that wins, gets the new value. It keeps its quotes when the value fits them, its `export`, its comment and the comment lines above it, `# @public` included.
- A new key goes at the end of the file, as `KEY=value`.
- A `null` value removes the key: every line with it, and a `# @public` or `# @secret` line right above. A key that is not there is `NOT_FOUND`.
- Give the value without quotes. It can hold references; a value with spaces or a line break is written in double quotes.

The value goes through the same checks as a save from the editor: a reference to something the caller may not read is refused, as before, but only for the line being written. A change that would make the file longer than 256 KiB is refused, so the **Environment** tab always loads. The call returns the diagnostics of the whole file, the [hints](#hints-for-references) included, and like `env.set` takes `expectedUpdatedAt` from `env.get` to refuse a change when someone saved in between. The new value applies on the next deploy. The activity log shows the key, never the value.

`env.setSharedVariable` does the same for a project's shared variables. Both run right away for MCP tokens that may make changes, like `env.set`, and `env.get` and `env.set` point models to them.

## Shared variables

A project's **Shared environment** tab holds variables every service of the project gets, in the same `.env` format. A service's own keys win over shared ones with the same name. Databases do not get shared variables. Shared variables cannot reference services, but services can reference them as `${{project.NAME}}`.

## Addresses on other nodes

A project's private network exists on each node separately. An `INTERNAL_*` address only works for services on the same node. When a reference or a typed address points at a service on another node, the editor underlines it in red and offers fixes:

- **Use** the exposed address instead (`${{db.EXPOSED_URL}}`), when the target is exposed,
- **Expose** the target, for databases with TLS (see [Databases](/guides/databases)),
- **Move** this service to the target's node (see [Moving services](/guides/moving-services)).

### In the References panel

The **References** panel marks the same addresses. Its header names the nodes this service runs on ("Click to insert. Internal addresses only work for services on `<this service's nodes>`."). For a service on another node, its internal variables (`INTERNAL_URL`, `INTERNAL_HOST`, and ClickHouse's `INTERNAL_HTTP_URL`) are struck through, clicking one inserts nothing, and its tip names the nodes that other service runs on: "Only for services on `<its nodes>`". Its other variables, such as `INTERNAL_PORT`, `USER` or its own `.env` keys, insert as usual.

Changed in 0.2.12: that includes services with a way in from other nodes, an exposed database or an app with a domain, and their tip names the variable to use instead: `EXPOSED_URL` (`EXPOSED_HOST` for `INTERNAL_HOST`) for a database, `URL` for an app. For example: "Only for services on de-fsn-1. worker runs on us-ash-1, so use EXPOSED_URL." Before, the panel left the internal variables of such a service out, so they looked missing. Listed or not, they do not connect from another node: the project network does not reach across nodes. Use the exposed address, or move one of the two services to the other's node.
