---
title: Backups
description: Database dumps and volume archives on a schedule to S3, R2 or MinIO, and how to restore them.
---

Backups run on the node the service is on and upload straight to an S3-compatible bucket; they never pass through the panel. To back up the panel itself, see [Backing up the panel](/self-hosting/backups).

New in 0.2: nodes never get the bucket's keys. For each upload, download or delete of a running backup or restore, the node asks the panel, which signs a link for that run's own object only, so a node that is taken over cannot read or delete other backups. The panel starts and finishes multipart uploads and deletes old backups itself, so it must reach the bucket too. Nodes need the 0.2 agent for this: on an older one, backups and restores fail with "The agent on `<node>` is too old for backups" until the node is updated.

## Add a destination

**Settings → Backups → Add destination**:

| Field | What it is |
| --- | --- |
| Provider | AWS S3, Cloudflare R2, MinIO or Other S3 |
| Endpoint, Region | Where the bucket lives |
| Bucket | The bucket name |
| Folder | Optional folder inside the bucket |
| Access key ID, Secret access key | Keys that can list, write, read and delete in the bucket. Stored encrypted, and used only by the panel. |
| Use path-style URLs | MinIO and some other providers need this |

**Test** writes, reads and deletes a small object, and says which step failed if one does. Add destinations once; every service can use them.

## Schedule backups

On a service's **Backups** tab, **Add schedule**:

| Setting | What it does |
| --- | --- |
| **What** | **Database** (a dump) for databases, or **Volume** for one of the service's volumes |
| **Destination** | One of the buckets from Settings |
| **When** | A preset, or **Custom (cron expression)**. Times are UTC. |
| **Keep newest** | How many backups this schedule keeps. The panel deletes older ones from the bucket after each successful backup and when you change the number. |
| **Stop the service while copying** | For files that change while being copied, like SQLite databases. The service is down for the length of the backup. |

**Back up now** runs the service's first schedule at once, and each schedule's menu has a **Back up now** of its own. Such a run counts toward that schedule's **Keep newest**, so it can push the schedule's oldest backup out. On a database without a schedule, **Back up now** on the **Backups** tab makes a one-off dump to the first destination instead, which is kept until you delete it. The **Back up now** on a database's **Connection** tab needs a schedule.

### What a backup contains

| Service | Backup |
| --- | --- |
| PostgreSQL | `pg_dump` of the database (or `pg_dumpall`) |
| MySQL, MariaDB | `mysqldump` or `mariadb-dump` |
| MongoDB | `mongodump` |
| Redis | An RDB snapshot (`redis-cli --rdb`) |
| Valkey, KeyDB (new in 0.2) | An RDB snapshot (`valkey-cli --rdb` or `keydb-cli --rdb`) |
| Dragonfly (new in 0.2) | An RDB snapshot it saves into its data folder (`SAVE RDB`) |
| ClickHouse (new in 0.2) | A `BACKUP` of every database except the system ones, as a zip |
| Volume | A `.tar.gz` of the volume's folder |

Dumps run in a helper container from the database's own image, so the dump tool always matches the server version. Dragonfly and ClickHouse write their backup into their own data folder first; the helper streams it to the bucket and deletes it, so the node needs room for one backup there. How each engine restores, including ClickHouse's rename-aside restore, is in [Database engines](/guides/database-engines#backups-and-restores).

## Restore

In **Backups and restores**, pick a backup and click **Restore**. It replaces the service's current data: databases are restored with their engine's own tool, volumes are unpacked into a fresh folder and swapped in. Tick **Back up the current data first** to keep a copy of what is there now. You type the service name to confirm. New in 0.2: a volume restore, like a volume copied by a move or a clone, keeps the sticky and setgid bits of folders; setuid and setgid on files are dropped, like on uploads. Before, folders came back without them.

<Callout type="warn" title="A restore replaces the current data">
Without **Back up the current data first**, the data in the service before the restore cannot be recovered.
</Callout>

## Alerts

A failed backup raises the **Backup failed** alert. Pick where it goes in **Settings → Notifications** or on the service's **Alerts** tab; see [Alerts and notifications](/features/notifications).
