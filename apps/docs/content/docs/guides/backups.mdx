---
title: Backups
description: Database dumps and volume archives on a schedule to S3, R2 or MinIO, and how to restore them.
---

Backups run on the node the service is on and upload straight to an S3-compatible bucket; they never pass through the panel. To back up the panel itself, see [Backing up the panel](/self-hosting/backups).

New in 0.2: nodes never get the bucket's keys. For each upload, download or delete of a running backup or restore, the node asks the panel, which signs a link for that run's own object only, so a node that is taken over cannot read or delete other backups. The panel starts and finishes multipart uploads and deletes old backups itself, so it must reach the bucket too. Nodes need the 0.2 agent for this: on an older one, backups and restores fail with "The agent on `<node>` is too old for backups" until the node is updated.

## Add a destination

**Settings → Backups → Add destination**:

| Field | What it is |
| --- | --- |
| Provider | AWS S3, Cloudflare R2, MinIO or Other S3 |
| Endpoint, Region | Where the bucket lives |
| Bucket | The bucket name |
| Folder | Optional folder inside the bucket |
| Access key ID, Secret access key | Keys that can list, write, read and delete in the bucket. Stored encrypted, and used only by the panel. |
| Use path-style URLs | MinIO and some other providers need this. On, every request puts the bucket in the path (see [How the bucket is addressed](#how-the-bucket-is-addressed)) |

**Test** writes, reads and deletes a small object, and says which step failed if one does. Since 0.2.15 a failed **Test** also names the request it made, whether the bucket was in the host or the path, and the provider's error, never the keys. Add destinations once; every service can use them.

### How the bucket is addressed

Changed in 0.2.15. The panel's own requests to the bucket (the **Test**, the cleanup of old backups and its listing) address the bucket exactly as the nodes' upload links do: path-style (`<endpoint>/<bucket>/<file>`), unless the endpoint is AWS, Google or Aliyun, which get the bucket in the host, or the endpoint is already the bucket's own host at a known provider (Cloudflare R2, DigitalOcean Spaces, Backblaze, Wasabi and others), which is used as it is instead of getting the bucket twice. With **Use path-style URLs** on, every request is path-style.

Before, with **Use path-style URLs** off, the panel's own requests left the bucket out of the address. On Cloudflare R2 the **Test** then failed at the write step with MalformedXML, since R2 read the test write as "create a bucket", and **Keep newest** never deleted old backups there. Node uploads were not affected. After the update, the first cleanup on such a destination deletes every backup past its **Keep newest** number at once.

When the endpoint is already a bucket's own host, backups made before the panel was on 0.2.15 were uploaded with the bucket's name in front of each file again, so they sit in a `<bucket>/` folder inside the bucket. Restores, downloads, deletes and the cleanup find them there. The nodes upload to links the panel signs, so new backups use the new address as soon as the panel is on 0.2.15, also from a node whose agent is older.

## Schedule backups

On a service's **Backups** tab, **Add schedule**:

| Setting | What it does |
| --- | --- |
| **What** | **Database** (a dump) for databases, or **Volume** for one of the service's volumes. New in 0.2.16: for a PostgreSQL, MySQL, MariaDB or MongoDB database, **Everything on this server** or **Chosen databases** (see [Choose what a database backup holds](#choose-what-a-database-backup-holds)) |
| **Destination** | One of the buckets from Settings |
| **When** | A preset, or **Custom (cron expression)**. Times are UTC. |
| **Keep newest** | How many backups this schedule keeps. The panel deletes older ones from the bucket after each successful backup and when you change the number. |
| **Stop the service while copying** | For files that change while being copied, like SQLite databases. The service is down while its volume is archived. Changed in 0.2.17, on nodes with agent 0.2.17: it starts again as soon as the archive is written, while the upload goes on (see [When the bucket is slow](#slow-buckets)); before, it stayed down until the upload ended. |

Changed in 0.2.15: **Back up now** on a service's **Backups** tab starts every schedule that is on at once. Each backup goes to its own destination and counts toward its own **Keep newest**, and the toast says how many started. Schedules that are off, and one whose backup is still running, are skipped. Before, it ran only the first schedule, so a service with a schedule per volume got one backup. Each schedule's menu still has a **Back up now** of its own that backs up just that schedule. Such a run counts toward that schedule's **Keep newest**, so it can push the schedule's oldest backup out.

**Back up now** on a database's **Connection** tab does the same as on the **Backups** tab. A database without a schedule gets a one-off dump to the first destination instead, from either tab, which is kept until you delete it. In the API and MCP: `backups.runAll` for every schedule, `backups.runNow` with a `policyId` for one.

New in 0.2.15: when a schedule comes due while its previous backup, or one started with **Back up now**, is still running, the scheduler skips that time, notes it in the panel's log, and runs the schedule at its next time. Before, it started another backup of the same schedule.

Fixed in 0.2.16: a schedule's own **Back up now** is refused while that schedule's backup still runs, and the toast says "This schedule is still backing up."; before, it started a second backup of it. One-off backups are not checked. In the API and MCP, `backups.runNow` with a `policyId` returns CONFLICT with reason `running` and the `runId` of the backup that runs.

New in 0.2.16: while a service moves to another node, **Back up now** and **Restore** are refused ("`<service>` is moving to another node. Back it up once the move ends."). A schedule that comes due during the move stays due and runs in the first minute after the move ends, on the new node (see [Moving services](/guides/moving-services#databases)).

### What a backup contains

| Service | Backup |
| --- | --- |
| PostgreSQL | `pg_dump` of the database (or `pg_dumpall`) |
| MySQL, MariaDB | `mysqldump` or `mariadb-dump` |
| MongoDB | `mongodump` |
| Redis | An RDB snapshot (`redis-cli --rdb`) |
| Valkey, KeyDB (new in 0.2) | An RDB snapshot (`valkey-cli --rdb` or `keydb-cli --rdb`) |
| Dragonfly (new in 0.2) | An RDB snapshot it saves into its data folder (`SAVE RDB`) |
| ClickHouse (new in 0.2) | A `BACKUP` of every database except the system ones, as a zip |
| Volume | A `.tar.gz` of the volume's folder |

Dumps run in a helper container from the database's own image, so the dump tool always matches the server version. Dragonfly and ClickHouse write their backup into their own data folder first; the helper streams it to the bucket and deletes it, so the node needs room for one backup there. How each engine restores, including ClickHouse's rename-aside restore, is in [Database engines](/guides/database-engines#backups-and-restores).

### Choose what a database backup holds

New in 0.2.16, on nodes with agent 0.2.16. A PostgreSQL, MySQL, MariaDB or MongoDB schedule backs up one of:

| Choice | What it holds |
| --- | --- |
| **Everything on this server** (the default, as before) | Every database, with the users and roles for PostgreSQL, the users and privileges for MySQL and MariaDB, the users for MongoDB. The dialog shows how many databases the server has and their size now. |
| **Chosen databases** | The databases you pick from the server's live list, with their sizes. With one database picked, **Only these tables** (MongoDB: **Only these collections**) takes some of its tables; empty is **The whole database**. Users and roles are not in such a backup. |

A schedule takes 1 to 50 databases, or one database with up to 200 tables; system databases cannot be picked. The list needs the database running and its node connected: while it cannot answer (the database is stopped, the node is away, its agent is older than 0.2.16 and the dialog says "Update `<node>` to choose databases", or Seylo's sign-in is refused), **Everything on this server** still works, and names saved before stay as chips you can remove. Names that are gone from the server are marked **missing**. Redis, Valkey, KeyDB, Dragonfly and ClickHouse always back up everything.

The node lists the server right before each backup. A chosen database or table that no longer exists is skipped, and the run shows how many were skipped and which; when none of them is left, the backup fails and says so. A schedule of chosen databases on a node whose agent is older than 0.2.16 fails with "Update `<node>` to back up chosen databases".

Each database backup in **Backups and restores** shows what it holds: its databases as chips with their size inside the database, the size of the compressed file and how long it took. The arrow opens its tables or collections with their size and approximate rows (the biggest 500 per database). A backup of everything that could not be measured says **Contents not measured**; it is still a whole backup. Backups made before 0.2.16, or by older nodes, show **Everything on this server**. Several PostgreSQL or MongoDB databases in one backup are one object in the bucket (`.bundle`), so **Keep newest**, **Download** and **Delete** work as for any other backup.

**Back up now** on the **Connection** tab or the **Backups** tab of a database without a schedule makes a one-off backup of everything. A service export keeps a schedule's chosen databases; a panel before 0.2.16 backs up everything with such a schedule. In the API and MCP, `backups.listDatabases` lists the server (with `database`, that database's tables), `backups.createPolicy` and `backups.updatePolicy` take `selection`, runs carry `scope`, `contents` and `warnings`, and `backups.runContents` returns one backup's tables. Listing the databases needs the permission to see the database's credentials, like the **Users** tab.

## Restore

In **Backups and restores**, pick a backup and click **Restore**. It replaces the service's current data: databases are restored with their engine's own tool, volumes are unpacked into a fresh folder and swapped in. Tick **Back up the current data first** to keep a copy of what is there now. You type the service name to confirm. Changed in 0.2.15: a failed **Restore** or **Delete** keeps its dialog open with the reason; before, the message showed under the last row and stayed after the dialog closed. New in 0.2: a volume restore, like a volume copied by a move or a clone, keeps the sticky and setgid bits of folders; setuid and setgid on files are dropped, like on uploads. Before, folders came back without them.

<Callout type="warn" title="A restore replaces the current data">
Without **Back up the current data first**, the data in the service before the restore cannot be recovered.
</Callout>

New in 0.2.15: each row of **Backups and restores** names what it holds next to its date: **Database**, the volume (such as **Volume data**), **Deleted volume** for a volume removed since, and for a restore "Restore of the Nov 12 03:00 backup of Volume data". In the API and MCP, runs have `volumeName`, and restores `sourceStartedAt`.

### Restore chosen databases

New in 0.2.16. A backup of chosen databases, tables or collections restores only what it holds and leaves everything else on the server, users included, as it is. The restore dialog names it, for example "This replaces the database shop on db with its state from ...", or "This replaces 2 tables in shop: public.orders, public.items". PostgreSQL restores each database in one transaction (creating it when it is missing), MySQL and MariaDB run the dump, and MongoDB replaces only those namespaces.

**Back up the current data first** backs up the same selection. When none of it is on the server any more (a dropped database or table you want back), the restore goes on without that backup and its row says so; when the backup first fails, the restore's error says why and to untick the box.

A PostgreSQL table that another table references cannot be restored alone: the restore fails and changes nothing, and the schedule dialog says so when you choose tables. Choose both tables, or the whole database. Restoring a backup of chosen databases, or any `.bundle`, needs the node's agent 0.2.16, and fails at once on an older node. Backups of everything, and every backup made before 0.2.16, restore exactly as before.

### Download a backup

New in 0.2.15. A backup's menu in **Backups and restores** has **Download**. The browser saves the file straight from the bucket, so nothing passes through the panel and the bucket needs no CORS settings; the browser must be able to reach the bucket. The file is named after the service, what it holds and when it started (UTC), for example `vault-warden-data-2026-11-13_0300.tar.gz`. The link the panel signs is for that one file and works for 5 minutes, and the bucket's keys are never in it.

It needs the permission to restore the service's backups, and on a database also the permission to see its credentials, since a dump holds its logins. Each download is in the activity log. Deleted backups, backups that failed or still run, and backups whose destination was deleted have no **Download**. In the API and MCP: `backups.downloadUrl`. An AI tool or an MCP token waits for a person's approval first, like a delete, unless **Ask before destructive actions** is off (see [Approvals](/features/mcp-and-ai#approvals)).

### A deleted destination

New in 0.2.15. A backup whose destination was deleted in **Settings → Backups** can no longer be restored or downloaded, since the panel has no keys for its bucket. Its row says **Destination deleted** and has no **Restore**, and **Remove from list** marks it deleted. The file stays in the bucket: delete it there by hand if you want it gone. Before, such a backup could never leave the list. In the API and MCP, `backups.deleteRun` of such a backup no longer fails with `noDestination`, and `backups.restore` refuses it at once.

### Postgres backups and missing users

Changed in 0.2.13: a PostgreSQL backup made with `pg_dump` restores in one transaction (`pg_restore --single-transaction`). A backup names the users that own its tables and have rights on them. When one of them is gone from the database, renamed or deleted since the backup on the [Users](/guides/databases#users) tab or in the shell, the restore fails with nothing changed, and its error names the user (`role "<user>" does not exist`). Before, it stopped part way, after the tables it replaces had been dropped.

To restore such a backup, make a user with that name on the database's **Users** tab (**New user**, any access), then **Restore** again.

One transaction takes a lock on every table it replaces, so a database with a very large number of tables may need Postgres's `max_locks_per_transaction` raised for the restore to run.

## When the bucket is slow [#slow-buckets]

Changed in 0.2.17, on nodes with agent 0.2.17.

The node uploads a backup in parts of 32 MiB. Before 0.2.17 the dump waited while each part uploaded, and some databases close a client that stops reading: on a slow uplink MariaDB and MySQL dumps failed with "mariadb-dump: Error 2026: TLS/SSL error: unexpected eof" or "Error 2013: Lost connection", and Redis, Valkey and KeyDB dumps with "I/O Error reading RDB payload".

### The node holds what the upload has not taken yet

The agent now keeps reading the dump or the archive while a part uploads, and holds what the upload has not taken yet:

- in memory, up to 16 MiB per backup, for every backup,
- then on disk, for dumps of MySQL, MariaDB, Redis, Valkey and KeyDB, whose servers drop a dump that stops reading, and for volume backups with **Stop the service while copying**, so the service starts again sooner. These go into files of 32 MiB in `/var/lib/seylo/backup-spool`.

| Limit | What it means |
| --- | --- |
| 4 GiB per backup | The most one backup holds on the node's disk. |
| 15% of the disk and 10 GiB free | No file is written that would leave less free on the disk that holds `/var/lib/seylo`. That is where the **Disk space** health check starts to warn, so a backup never sets it off. |

Each file is removed from the folder as soon as it is made, so the folder looks empty while `df` shows the space in use. The space comes back as the upload takes each file, and at the latest when the backup ends or the agent stops; the agent also empties the folder when it starts. Other dumps (PostgreSQL, MongoDB, ClickHouse and Dragonfly) and other volume backups keep to memory: their database does not drop them while they wait, and their bytes are not written to the node's disk once more.

When there is no room left, the dump waits for the upload, as before: the node never fails a backup for want of room by itself. The progress of a run counts what the upload took. A volume backup that stopped its service starts the service again once the whole archive is written; an archive larger than the room the node has keeps the service down until the rest fits.

### "The database closed the connection" [#connection-closed]

A dump or a restore whose tool's last line says the database closed the connection gets a sentence after that line with what usually causes it:

```text
the dump exited with code 2: mariadb-dump: Error 2026: TLS/SSL error: unexpected eof while reading when dumping table `orders` at row: 81234. The database closed the connection in the middle of the dump. Usually it restarted or ran out of memory: look in its Logs for a restart or "Aborted connection". Before Seylo 0.2.17 a slow upload to the bucket caused this too.
```

A restore says "in the middle of the restore" and "a slow download from the bucket". What to look for in the database's **Logs** around that time:

| Engine | The tool's line | In the database's Logs |
| --- | --- | --- |
| MySQL, MariaDB | Errors 2006 (server has gone away), 2013 (lost connection), 4031 (disconnected for inactivity), or 2026 with "unexpected eof" | A restart, or "Aborted connection" |
| Redis, Valkey, KeyDB | "I/O Error reading RDB payload", or "while SYNCing" | A restart, or "Disconnecting timedout replica" |
| PostgreSQL | "server closed the connection unexpectedly", "connection to server was lost", "terminating connection due to ..." | A restart, or "terminating connection" |

When a MySQL, MariaDB, Redis, Valkey or KeyDB dump had just waited a second or more for the upload because the node had no more room, the message says so instead, and what to change:

```text
... The database closed the connection after the dump waited 1m15s for the upload: the upload fell behind the dump by more than 4.3 GB, the most one backup holds on the node. Use a bucket the node reaches faster or raise the database's net_write_timeout and wait_timeout.
```

When the disk was the limit it reads "... and the node has no room to hold it (backups leave 15% of its disk and 10 GiB free). Free space on the node, use a bucket it reaches faster or raise ...". For Redis, Valkey and KeyDB the setting to raise is `repl-timeout`. A mysqldump that exits without a word after such a wait (MySQL closed its idle session) gets "The dump stopped without a message right after it waited ... for the upload: ..., so the database most likely closed its connection meanwhile."

### Timeouts of the backup's own session

The dump and restore tools raise the database's idle timeouts for their own session only. The database's settings are never changed:

- MySQL and MariaDB restores set `wait_timeout`, `net_read_timeout` and `net_write_timeout` to 86400 seconds for their session. Before, a restore from a slow bucket ended with "Server has gone away" (2006) or "disconnected by the server because of inactivity" (4031).
- mysqldump 8.4 and later does the same for its dump. mysqldump 8.0 and 5.7 and mariadb-dump cannot, and the node's room for the upload covers them.
- A PostgreSQL restore of a whole-server backup, which runs `psql`, turns `idle_session_timeout` off for its sessions on PostgreSQL 14 and later.

## Alerts

A failed backup raises the **Backup failed** alert. Pick where it goes in **Settings → Notifications** or on the service's **Alerts** tab; see [Alerts and notifications](/features/notifications).
