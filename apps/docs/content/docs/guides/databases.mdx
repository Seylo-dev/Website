## Create a database

In a project, click **Add a service**, pick **Database**, then the engine and the version (the newest is preselected):

| Engine | Versions |
| --- | --- |
| PostgreSQL | 18 (new in 0.2), 17, 16, 15, each also with pgvector (new in 0.2) |
| MySQL | 8.4, 8.0 |
| MariaDB | 11.8, 11.4, 10.11 |
| MongoDB | 9.0 (new in 0.2.9), 8.0, 7.0 |
| Redis | 8.2, 7.4 |
| Valkey (new in 0.2) | 9.1, 9.0, 8.1 |

Changed in 0.2.9: **New database** does not offer KeyDB, Dragonfly and ClickHouse for now; existing ones keep working, and templates and the API still create them.

For Postgres, **Include pgvector** picks an image with the vector extension. Valkey, KeyDB, Dragonfly and ClickHouse need a 0.2 agent on the node. [Database engines](/guides/database-engines) has the connection strings, backups and limits of each.

New in 0.2.11: tick **Use another image** under **Version** to run another tag or digest of the engine's own image instead of the pinned one, such as `mongo:8.2.12`, `postgres:17-alpine` or `redis:latest`. The **Image** field starts from the picked version's image (`pgvector/pgvector` with **Include pgvector**). It is not tested by Seylo, and for a floating tag the form says that what it points at can change on the next deploy. The database is recorded as the version its tag names (`mongo:8.2.12` is MongoDB 8.2); when the tag names none, the page shows the image instead, as in "MongoDB (mongo:latest)". A Postgres image whose tag names no release, such as `postgres:latest` or a digest, also gets `PGDATA=/var/lib/postgresql/docker` in the database's variables, so its data stays on the data volume whatever release the tag pulls (see [Postgres and PGDATA](#postgres-and-pgdata)). An image of another repository is refused: Seylo's settings for a database (its environment, data folder, health check and command) are made for its engine's image.

Seylo generates the credentials and keeps them encrypted. The database is only reachable from services of the same project on the same node, by its service name, until you [expose it](#expose-with-tls) or open a [timed expose](#timed-expose). New in 0.2.13: the **Users** tab makes more users and changes the main one (see [Users](#users)).

## Connect from an app

The database's **Connection** tab shows the **Internal connection**: URL, host, port, database, user and password, for services on the same node in this project.

Reference it from the app's environment instead of copying it, so a new password or a new main user reaches the app on its next deploy:

```bash
DATABASE_URL=${{db.INTERNAL_URL}}
```

See [Environment variables](/guides/environment-variables) for the other variables a database offers.

## Web UI and shell

The **Tools** section on the Connection tab has:

- **Web UI**: pgweb for Postgres, phpMyAdmin for MySQL and MariaDB, mongo-express for MongoDB, Redis Commander for Redis, Valkey, KeyDB and Dragonfly, and ClickHouse's own Play page for ClickHouse. It starts when you open it, already signed in, and sleeps again after a few idle minutes, so it costs nothing while unused. It is opened through the node's wildcard domain with a one-time ticket from the panel and never gets a port of its own, so the node needs a wildcard domain.

  New in 0.2, on nodes with a 0.2 agent: while a web UI is open, the node asks the panel about once a minute whether you may still use it. Removing your access, disabling you, or revoking the API key that opened it closes it within about a minute, open connections included. While the panel cannot answer (it is down, or older than 0.2), a session lasts an hour past the last answer, and 12 hours at most in any case. Web UI sessions from before the update are not accepted: open the web UI from the panel once more (the old one shows **Sign-in needed**). Boxes work the same way.

  New in 0.2, on nodes with a 0.2 agent: each web UI also has a login of its own, made anew on every agent start, which only the node's edge holds and adds to your requests. So other containers on the project network, such as code a member deployed there, cannot open the web UI and act as the database admin without the right to see the credentials.
- **Database shell**: `psql`, `mysql`/`mariadb`, `mongosh`, `redis-cli`, `valkey-cli`, `keydb-cli` or `clickhouse-client`, already signed in, in the browser.

## Expose with TLS

To reach the database from your laptop or from another node, turn on **Exposed**. Since 0.2.8 it asks first for the port the node opens (1024 to 65535; empty picks a free one) and who may connect, and opens it when you click **Expose**; **Port and access** changes them later.

Exposing only opens a port on the node to the database, with TLS. Clients sign in with the database's own user and password, the same as in the **Internal connection**, for every engine, and the internal URL does not change. The exposed card on the **Connection** tab shows that user and password, and **Copy** copies the URL. Changed in 0.2.9: before, Postgres, MySQL, MariaDB, MongoDB and ClickHouse got a second user for the exposed port; [What's new in 0.2.9](/self-hosting/whats-new-in-0-2-9#after-the-update) says what happens to it.

**Exposure settings**:

| Setting | What it does |
| --- | --- |
| **Allowed IPs** | Only these IPs or CIDRs may connect. Empty allows anywhere, except for KeyDB, which gets no security fixes and is only exposed to listed addresses. |
| **TLS host name** | A name that points at the node gets a Let's Encrypt certificate. Empty uses a self-signed certificate (see [Self-signed certificates](#self-signed-certificates)). |
| **Port** | The public port. Empty keeps the current one or picks a free port. |

Changed in 0.2.12, on nodes with the 0.2.12 agent: a **TLS host name** set or changed while the database runs gets its Let's Encrypt certificate right away. Before, the node asked for it only on the database's next deploy or the agent's next restart, and until then the port kept the self-signed certificate.

The port only takes TLS. Postgres, MySQL and MariaDB serve TLS themselves, and the node refuses their clients that do not ask for it with the database's own kind of error: Postgres clients get "this port only accepts TLS connections: connect with sslmode=require", MySQL and MariaDB clients get error 3159. For MongoDB, the Redis-like engines and ClickHouse's native port the agent terminates TLS on the exposed port; ClickHouse's HTTP port is never exposed. MariaDB always uses its own self-signed certificate, even with a TLS host name. Since 0.2.16 the port can also let clients without TLS through, when you allow it (see [Connections without TLS](#connections-without-tls)).

MariaDB 10.11 has no TLS, so since 0.2.9 it cannot be exposed: **Expose** refuses it. MariaDB 11.4 and later can; to expose a 10.11 database, [change its version](#change-the-version) to 11.4 first. A MariaDB version before 11.4 that Seylo does not offer, such as 10.6 or 11.2 run with **Use another image**, cannot be exposed either.

The **Exposed connection URL** (`${{db.EXPOSED_URL}}`) is what services on other nodes use. Without a Let's Encrypt certificate the port serves a self-signed one, which clients that check certificates refuse: see [Self-signed certificates](#self-signed-certificates) for the settings that connect.

The card's **Certificate** line says what the port serves: **self-signed**, **being issued** (the node has no Let's Encrypt certificate for the **TLS host name** yet), **valid** with its issuer and end date, or, new in 0.2.13, **failed** (the node serves the self-signed one and has an error from Let's Encrypt for the name). Changed in 0.2.13: the line follows what the port serves. Before, an exposed Postgres or MySQL database with a TLS host name stayed on **being issued** after it had its Let's Encrypt certificate, because the node did not report the certificate those databases serve, and a MongoDB, ClickHouse or Redis-like database with a TLS host name whose certificate was never issued said **valid** while it served the self-signed one.

### Connections without TLS

New in 0.2.16, on nodes with agent 0.2.16. **Allow connections without TLS** on the **Exposed connection** card lets clients that do not ask for TLS through to the database, instead of refusing them. It works for every engine that can be exposed: Postgres, MySQL, MariaDB, MongoDB, Redis, Valkey, KeyDB, Dragonfly and ClickHouse's native port. It is off by default, also on every database exposed before 0.2.16. TLS clients connect as before, the **Allowed IPs** still apply, and the exposed URL and `${{db.EXPOSED_URL}}` keep asking for TLS. While it is on, the card's chip says **TLS optional**.

Turning it on asks you to confirm. Clients without TLS send their queries, get their data back and, with some sign-in methods, send the password unencrypted; the Redis-like engines and ClickHouse send the password itself unencrypted. With no **Allowed IPs**, or ones that cover every address (`0.0.0.0/0`, `::/0`, or ranges that add up to every address, such as `0.0.0.0/1` with `128.0.0.0/1`), the warning says, in stronger words, that the port is open to every IP address. While it is on, saving allowed IPs under **Port and access** that let every IP in this way asks again, unless the saved ones already did. Prefer TLS, or a [timed expose](#timed-expose) for a one-off connection.

Turning it off asks nothing: the node refuses new clients without TLS at once and closes the ones connected without TLS, and TLS sessions stay. Turning **Exposed** off turns it off too, so exposing again starts TLS only. Each change is in the activity log, and it takes the same permission as the rest of the exposure.

MySQL clients without TLS need the server's public key to send the password, as the card says: `--get-server-public-key` (for example `mysql --ssl-mode=DISABLED --get-server-public-key`), or `allowPublicKeyRetrieval=true` in JDBC.

On a node with an older agent the switch says it needs the node's agent 0.2.16, and the port stays TLS only. In the API and MCP, `databases.setExposure` takes `allowPlain` (it needs exposure on, and turning it on is refused with `agentTooOld` on an older node); `databases.get` returns `exposure.allowPlain` and `exposure.plainNeedsNodeUpdate`, and `databases.connection` returns `exposed.allowPlain`, true only while clients without TLS get through. An AI tool waits for a person's approval before it turns it on, or, while it is on, empties the allowed IPs or adds addresses they did not cover (see [Approvals](/features/mcp-and-ai#approvals)). Its request shows a **Without TLS** chip and says what approving allows and to whom, and approving it asks first. A call the panel would refuse anyway, such as on a node with an older agent or while the database is not exposed, is refused at once instead of waiting for approval.

### Closed until the node updates

Exposed Postgres, MySQL and MariaDB need the node's agent from 0.2.9, which keeps the port TLS only. On an older node **Expose** refuses them ("Update the node first"), and one exposed before the update stays closed: the **Connection** tab says "Closed until `<node>` updates to 0.2.9", with **Exposed** still on, and `${{db.EXPOSED_URL}}` is empty for services deployed meanwhile. The port opens by itself once the node is updated. MongoDB, ClickHouse and the Redis-like engines stay exposed on older nodes.

### Self-signed certificates

New in 0.2.13. While the exposed port serves a self-signed certificate, the **Exposed connection** card on the **Connection** tab has a **Self-signed certificate** note: "Connections are encrypted, but clients that check certificates refuse this one." It says why:

| Reason | What the note says |
| --- | --- |
| No **TLS host name** | "No TLS host name is set, so the node uses a certificate of its own." |
| No Let's Encrypt certificate for the host name yet | "The node has no Let's Encrypt certificate for `<host>` yet", with "Last attempt:" and the certificate authority's last error when the node has one, for example that it could not reach port 80 on the node. The **Certificate** line says **failed** with an error, **being issued** without one. |
| MariaDB | "MariaDB always serves the certificate it makes itself, with or without a TLS host name." |

To get a trusted certificate (not for MariaDB):

1. Set a **TLS host name** under **Port and access**.
2. Give that name an A record to the node's address, set to DNS only (not proxied, for example the grey cloud on Cloudflare).
3. Let port 80 reach the node: Let's Encrypt checks the name over port 80.

Until then, these client settings connect with the self-signed certificate. They encrypt the connection without checking the certificate:

| Engine | Setting |
| --- | --- |
| PostgreSQL | psql and other libpq clients connect with `sslmode=require`, as in the exposed URL. node-postgres (the `pg` package) reads `sslmode=require` as "check the certificate", so it needs `sslmode=no-verify`, or `uselibpqcompat=true&sslmode=require`. |
| MySQL | `ssl-mode=REQUIRED`, as in the exposed URL. `VERIFY_CA` and `VERIFY_IDENTITY` need the certificate. |
| MariaDB | `ssl-mode=REQUIRED` (`mariadb --ssl --skip-ssl-verify-server-cert`). |
| MongoDB | `tlsAllowInvalidCertificates=true`. The exposed URL of a database without a TLS host name already carries it; with a host name, add it while the certificate is self-signed. |
| ClickHouse | `skip_verify=true`, the same way. |
| Redis, Valkey, KeyDB, Dragonfly | `redis-cli --tls --insecure`, or `--cacert` with the downloaded certificate. |

For example, an app on another node that connects with node-postgres to an exposed Postgres database without a TLS host name:

```bash
DATABASE_URL="postgresql://postgres:<password>@<node address>:<port>/<database>?sslmode=no-verify"
```

#### Trust the certificate file

**Download certificate** in the note saves the certificate the port serves as `<service>.crt`, so a client can trust that file instead of skipping the check. MariaDB has none to download.

- **With a TLS host name**, the file names that host. Any client that checks certificates connects by that name with the file as its CA: `sslrootcert` (Postgres), `ssl-ca` (MySQL), `tlsCAFile` (MongoDB), `--cacert` (redis-cli).
- **Without one**, the certificate names no host, so a client that checks the host name refuses it. Use the setting that checks the certificate but not the name:

| Engine | Trusting the file without a TLS host name |
| --- | --- |
| PostgreSQL | `sslmode=verify-ca` with `sslrootcert=<file>`; node-postgres also needs `uselibpqcompat=true`. `verify-full` refuses it. |
| MySQL | `ssl-mode=VERIFY_CA` with `ssl-ca`. `VERIFY_IDENTITY` refuses it. |
| MongoDB | `tlsCAFile` with `tlsAllowInvalidHostnames=true`. `tlsCAFile` alone refuses it. |
| ClickHouse, Redis-like engines | A client that does not check the host name. |

```bash
DATABASE_URL="postgresql://postgres:<password>@<node address>:<port>/<database>?uselibpqcompat=true&sslmode=verify-ca&sslrootcert=/app/db.crt"
```

The certificate only vouches for its own host name and the names under it, and for no IP address (without a TLS host name, for no name at all). So a copy trusted for a whole process (`NODE_EXTRA_CA_CERTS`, the system's certificate store) cannot be used to vouch for any other site. Once the node has a Let's Encrypt certificate for the TLS host name, the port serves that one instead, and a client that trusts only the downloaded file refuses it: let the client use the system's certificate authorities again then.

Changed in 0.2.13: the self-signed certificate is now made as a self-signed certificate. Before, some clients described it wrongly: node-postgres on Bun, and other clients built on BoringSSL or OpenSSL 1.1, said "unable to verify the first certificate" instead of "self-signed certificate", and some, such as LibreSSL, did not accept it even when told to trust that file. A node on 0.2.13 makes the certificate again, once, and again when a TLS host name is set while the database still has no Let's Encrypt certificate, so the file names the host. The database serves the new one by itself, without a restart; open connections keep the old one until they reconnect. A client that pinned the old certificate needs the new one: **Download certificate** again.

The reason for a TLS host name ("no Let's Encrypt certificate yet"), the last error and **Download certificate** need the node on 0.2.13. On an older node the note only shows for a database without a TLS host name and for MariaDB, without the download.

## Timed expose

New in 0.2.16. The **Timed expose** card on the **Connection** tab, under the exposed connection, opens the database's port to your IP for a while, for a desktop client or a one-off script, without exposing it for good. Pick how long (**For**: 15 minutes, 1 hour, which is the default, 2, 8 or 24 hours) and who may connect (**Only from**: IPs or CIDRs; empty uses your own address), then **Open for 1 hour from my IP**. For ClickHouse, **Port** picks the native port 9000 or the HTTP port 8123 (for JDBC and DBeaver). Before, timed exposes were only offered on the **Domains** tab, which databases do not have.

Each open expose shows:

- the address (`<node IP>:<port>`) once the node has opened the port, and the IPs it is open to,
- the connection URL: with the password for people who may see the database's credentials, without it for everyone else,
- a command for the engine's own client: `psql`, `mysql`, `mariadb`, `mongosh`, `redis-cli` (also for Valkey, KeyDB and Dragonfly), `clickhouse-client`, or `curl` for ClickHouse's HTTP port. Each asks for the password at its prompt, so the password never lands in your shell history,
- whether the connection is encrypted, when it closes and who opened it, with **+1 hour**, which adds an hour to the time left, and **Close now**. **Open another** opens one more.

A timed expose relays the database's own port and adds no TLS. MySQL and MariaDB 11.4 and later serve TLS themselves, so the URL and command ask for it (`ssl-mode=REQUIRED`, `mariadb --ssl`), and so does a Postgres while it is also exposed, since TLS is on inside it then: its URL and command use `sslmode=require` once the node reports TLS on. MongoDB, ClickHouse, the Redis-like engines and a Postgres that is not exposed are reached without encryption, and the card says so: the connection crosses the network in the clear, only the allowed IPs can connect, and the port closes on time. For TLS on those, use the [exposed connection](#expose-with-tls).

The node closes the port on time even while the panel is down. Idle connections stay open for 2 hours, like on the exposed port, on nodes with agent 0.2.16; older agents cut them after 15 idle minutes, which drops a SQL client's pooled connections. A timed expose and the exposed connection never share a port on the node. Opening, extending and closing take the same permission as on the **Domains** tab and are in the activity log; the card is hidden from people who may not see the service's exposures.

From a terminal, `seylo tunnel expose acme-shop/db --port 5432 --for 2h` opens one too (see [Dev access and tunnels](/features/dev-access-and-tunnels#timed-expose)). In the API and MCP, `exposures.openTimed`'s `targetPort` is optional and defaults to the database's port, which is the only one a database takes (ClickHouse: 9000 or 8123); `exposures.get` returns each timed expose of a database with `database` (its client command and URL, without the password), and `databases.connection` returns `timed`, the URL of each with the password.

## Users

New in 0.2.13. A database's **Users** tab, next to **Connection**, lists the users that can sign in, read from the database itself each time it opens (Seylo keeps no list of them), with the main user first. The main user is the one Seylo signs in with: the shell, the web UI, backups, the connection URLs and the `${{db.*}}` references all use it. Seylo keeps only the main user's password. The password of any other user shows once, when it is set, and Seylo does not keep it.

PostgreSQL, MySQL, MariaDB, MongoDB and ClickHouse list all their users. Redis, Valkey, KeyDB and Dragonfly have one user, `default`, and the tab shows only that one, with a note on why only its password changes there: users made with `ACL SETUSER` live in memory only, since Seylo starts these engines without an ACL file, so the next restart or deploy would remove them.

Each row shows the user's name (`name@host` on MySQL and MariaDB) and what it may do (see [Access levels](#access-levels)), with these marks:

- **Main**: the main user, "Seylo signs in with this one".
- **Used inside the container**: MySQL's and MariaDB's root and Postgres's first user (the one the image made), when they are not the main user, and ClickHouse users defined in the server's configuration files.
- **Locked**: it cannot sign in now (a locked MySQL account, an expired Postgres role).
- `auth: <database>`: a MongoDB user of another authentication database than `admin`.
- Postgres rows say how many tables and other objects a user owns ("owns 3 objects", in every database of the server), and MySQL and MariaDB rows how many views, routines, triggers and events run as it (DEFINER).

Each row but the main user's has a **...** menu with **Change password**, **Rename**, **Make this the main user** and **Delete**, which says why when one of them is not offered. The tab lists 500 users at most ("Only the first 500 users are listed. Manage the others from the shell."), and a name with control characters or backslashes is listed but only managed from the shell.

While the database is stopped, is not placed on a node or its node is not connected, the tab lists only the main user, from what Seylo stores, and says why, for example "The database is stopped. Start it to see and change its users." While a deploy of the database runs, new users, other users' passwords, renames, deletes and a switch of the main user are refused until it finishes. The main user's password can still be changed.

### Access levels

| Access | What it may do |
| --- | --- |
| **Read only** | Reads every table of the database; cannot change anything. |
| **Read and write** | Reads, writes and changes tables of the database: what an app needs, migrations included. |
| **Admin of `<database>`** | Everything in the database, and may give those rights to others. Not on Postgres. |
| **Full admin** | Everything on the server, like the main user: other databases and users too. |
| **Custom** | Any other set of rights. The row shows the first grants or roles, and all of them on hover. |
| **No rights here** | Nothing on this database. |

On Postgres, **Read only** and **Read and write** use `pg_read_all_data` and `pg_write_all_data`, so they cover every database of the server, and **Read and write** also makes tables in the database. A Postgres before 14 (run with **Use another image**) offers **Full admin** only. What each level grants on each engine is in [Database engines](/guides/database-engines#users).

### Make a user

**New user** (PostgreSQL, MySQL, MariaDB, MongoDB and ClickHouse) takes:

- **Name**: letters, digits and `_`, starting with a letter or `_`; 32 characters at most on MySQL and MariaDB. Names the engine or Seylo keeps for itself are refused, such as `root` on MySQL and MariaDB, names that start with `pg_` on Postgres and `default` on ClickHouse.
- **Access**: one of the [access levels](#access-levels), on the database's own database (the whole server for **Full admin**).
- The password: **Generate one** (32 characters) or **Set my own** (12 to 128 letters, digits and `. _ ~ -`).
- MySQL and MariaDB, under **Advanced**: the **Host** it may sign in from. `%`, the default, is anywhere: services of the project and the exposed port both need it.

**Create user** makes it and shows "`<user>` is ready" with its password, its **Connection URL** and, while the database is exposed, its **Exposed connection URL**. Copy them then: Seylo does not keep the password. MongoDB users are made in the `admin` database.

### Change, rename or delete a user

For any user but the main one:

- **Change password** sets a generated or typed password, shown once. Anything signed in with the old one stops connecting.
- **Rename** gives it a new name (and on MySQL and MariaDB, another **Host**). Anything signed in with the old name stops connecting. A rename keeps the user's rights, and on Postgres the tables it owns. A Postgres user with an md5 password gets a new password with the rename, since Postgres clears an md5 password when it renames the user. MongoDB has no rename: a new user with the same rights and a new password takes its place, and the old one goes.
- **Delete** removes the user and keeps the data. Anything signed in as it stops connecting.

What runs as the user or belongs to it:

- **Postgres, a user that owns tables or other objects**: **Delete** needs "Give its `<count>` tables and other objects to `<main user>` first (REASSIGN OWNED)" ticked. Seylo first stops the user from signing in and ends its sessions, and waits for them to be gone (5 seconds at most), so nothing it makes meanwhile is lost. Then, in every database, it gives what the user owns to the main user (`REASSIGN OWNED`), drops its remaining grants (`DROP OWNED`) and drops the user. This visits one database after another, so it is not one transaction: if a step fails, the error says the user may no longer sign in and some of what it owned may already belong to the main user. Delete it again, or finish in the shell.
- **MySQL and MariaDB, views, routines, triggers and events that run as the user** (DEFINER): they stop working once it is renamed or deleted, until they are made again with another definer. **Rename** asks you to tick **Rename it anyway**, **Delete** to tick "... Delete it anyway".

These are not offered, and the row says why: deleting the main user (make another user the main one first), Postgres's first user, which Postgres never lets go, MySQL's `root@localhost`, which the image and Seylo's own steps sign in with, and MongoDB's last user with `root`. ClickHouse users defined in the server's configuration files take no changes. MySQL's and MariaDB's root always has the main user's password, so its password changes with the main user's.

A Postgres backup made before a user was renamed or deleted still names that user. Restoring it fails with nothing changed until a user of that name exists again (see [Restore](/guides/backups#restore)).

### The main user

Unless a template or the API named another one, the main user is `postgres` on PostgreSQL, `root` on MySQL, MariaDB and MongoDB, a generated `ch_` name on ClickHouse and `default` on the Redis-like engines. Its row on the **Users** tab has **Change password** and, except on the Redis-like engines, **Change name**. On the **Connection** tab, a **Change** link next to **User** and next to **Password**, on the internal card and on the exposed one, opens the **Users** tab with that change (the Redis-like engines have only the one next to **Password**). Changed in 0.2.13: these replace **Reset password**, with the same step of typing the service name. People who cannot see the credentials do not get the links, and while the database cannot be changed (stopped, its node away) the **Users** tab says why instead of opening the change.

### The main user's password [#reset-a-password]

**Change password** (or **Change** next to **Password**) opens **Change the main user's password?**: a generated or typed password, and the service name typed to confirm. It is one password, inside and through the exposed port. Postgres, MySQL, MariaDB and MongoDB change it inside the running database, and Seylo stores it once the database took it.

Changed in 0.2.13: ClickHouse, Dragonfly, Redis, Valkey and KeyDB restart with the new password right after the change, a short outage, and the dialog says so. Before, ClickHouse and Dragonfly stored the new password but kept running with the old one until something else redeployed them, so the shell, the web UI, backups and services with the new URL could not sign in, and Redis, Valkey and KeyDB took it at once but went back to the old one on their next restart. That restart needs the right to deploy the database. A stopped database is refused for every engine: start it first, since the restart would start it.

Changed in 0.2.13: a second password change of a MongoDB database before its next deploy no longer fails ("the database refused"). It signed in with the password the database first started with, and now signs in with the one Seylo stores. Postgres changes also sign in as the stored user, and send the new password to Postgres only as its SCRAM hash, so a failed statement in the database's log shows no password.

Changed in 0.2.11: for MySQL and MariaDB, root gets the new password too, also when the database's main user is not root (a database made by a template or the API with its own user). The database's container gives root the main user's password (`MYSQL_ROOT_PASSWORD`, `MARIADB_ROOT_PASSWORD`), but before, a reset changed the main user's password only, so signing in as root with it failed (ERROR 1045) after the next deploy, and so did the panel's own steps that sign in as root, such as the next reset and the [MySQL 8.4 check](#mysql-84-and-mysql_native_password).

A database an older reset left that way still takes a new password: the main user's password changes, and the dialog after the change says that root kept an older password, which the panel does not know, and how to set it: sign in as root with that older password and run `ALTER USER 'root'@'%' IDENTIFIED BY '<new password>'`, and the same for `'root'@'localhost'`. Later changes then change both. Until then the **Users** tab lists only the main user and changes nothing else. Through the API, `databases.resetPassword` and `databases.setUserPassword` return that as `warning`.

When Seylo's stored login no longer signs in (a restored backup, or a change made in the shell), the tab says so and lists only the main user. **Set the password again** sets a new one. On MongoDB it is **Enter the password that works** instead: Seylo signs in with the password you give, stores it only when that works, and changes nothing in the database. For ClickHouse the tab says to deploy the database again, so it takes the stored user and password.

### The main user's name

**Change name** (or **Change** next to **User**) depends on the engine:

| Engine | What happens |
| --- | --- |
| PostgreSQL | **Rename the main user?** renames it in place, also when it is the first user the image made. The database then restarts so its health check uses the new name: **Restart the database now, so its health check uses the new name (a short outage)** is ticked. Untick it to restart later; until then the health check's failed sign-ins show in the database's log. |
| MySQL, MariaDB | A main user other than root is renamed in place. Root stays, since the image, its health check and Seylo's own steps need it: **Change name** opens [Use another user as the main one](#use-another-user-as-the-main-one). |
| MongoDB | No rename: **Change name** opens [Use another user as the main one](#use-another-user-as-the-main-one). |
| ClickHouse | It restarts with the new name, since ClickHouse makes this user from its environment at every start. Refused while a SQL user has that name, or while the database is stopped. |

**Rename the main user?** takes the new name, **Also set a new password**, and the service name to confirm. A Postgres main user with an md5 password gets a new password with the rename. On MySQL and MariaDB it asks first when views, routines, triggers or events run as the main user. A rename that restarts the database needs the right to deploy it.

### Use another user as the main one

On PostgreSQL, MySQL, MariaDB and MongoDB, **Use another user as the main one** at the top of the tab, or **Make this the main user** in a row's menu, opens a dialog:

- **A new user**: a name, and Seylo makes it with full rights.
- **An existing user**, picked from the list. Seylo does not know its password, so it gets a new one. A user without full rights needs **Give it full rights: the main user needs them for backups and the Users tab** ticked. A locked user cannot be picked, nor a MySQL or MariaDB account with another host than `%`, nor a MongoDB user of another authentication database than `admin`.
- The password, generated or typed.
- On MySQL, MariaDB and MongoDB, whether to delete the old main user. With MySQL's or MariaDB's root as the main user, it is **Remove root@%: root@localhost stays inside the container**: the image, its health check and Seylo's own steps need root. MySQL and MariaDB ask first when views, routines, triggers or events run as the old main user. On Postgres the old main user stays; delete it from its row later if Postgres lets it go (never its first user).

**Switch**, after the service name, makes the change. Seylo signs in as the user the way its tools do before it gives it full rights or stores anything. When that fails nothing is stored: a user made for the switch is removed again, and an existing one keeps the new password, which the error says. MySQL and MariaDB then give root the new main user's password, since root always has the main user's.

ClickHouse's main user is the one its container is started with, so it takes no switch: rename it instead. Redis-like engines have only `default`.

### After a change to the main user

The dialog after the change shows:

- The new password, when there is one: copy it then ("Copy it now.").
- "The database restarts with it now." with **See the restart**, when the change restarts the database.
- The services of the project that reference the database's user, password or URLs, each with **Redeploy**: they get the new values on their next deploy. Anything else signed in with the old name or password stops connecting, wherever it connects from.
- A warning, when the change happened but a step after it did not, such as root's password on MySQL or removing the old main user.

The shell, the web UI and backups use the new main user at once. If the node stops answering in the middle of a change to the main user, Seylo signs in with the new name or password and stores it only when that works; otherwise the main user stays as it was, and the error says so.

### Permissions, API and MCP

Seeing and changing a database's users needs **See credentials** (`databases.credentials`) on the service, the same action that shows its password on the **Connection** tab. A change that restarts the database also needs **Deploy**.

Through the API and MCP: `databases.users`, `databases.createUser`, `databases.setUserPassword`, `databases.renameUser`, `databases.deleteUser` and `databases.switchMainUser`, all with `databases.credentials`. The four that change or remove a user (`setUserPassword`, `renameUser`, `deleteUser` and `switchMainUser`) wait for a person's approval when an AI tool calls them (see [Approvals](/features/mcp-and-ai#approvals)). `databases.resetPassword` still works, and since 0.2.13 returns `deploymentId` when the database restarts.

In Seylo's test setup, the commands the panel runs for each step of the Users tab ran on the real images of PostgreSQL 18, MySQL 8.4, MariaDB 11.8, MongoDB 9.0 and ClickHouse 26.8: users of each access level checked with the database's own client for what they may and may not do, new passwords, renames and deletes, the main user's password twice before a deploy, its new name in place, by a switch or with a restart, and then, after a redeploy, the shell, a backup and its restore signed in as the new main user. The panel's side of the tab was tested against a stand-in node, not yet through a real panel.

## Backups

On the database's **Backups** tab, schedule dumps to an S3-compatible bucket. Each run uses the engine's own dump tool. See [Backups](/guides/backups), and [Database engines](/guides/database-engines#backups-and-restores) for what each engine's backup and restore do.

New in 0.2.16: a PostgreSQL, MySQL, MariaDB or MongoDB schedule can back up chosen databases, or some tables or collections of one, and each backup shows what it holds (see [Choose what a database backup holds](/guides/backups#choose-what-a-database-backup-holds)).

## Advanced tab

New in 0.2.16. A database's **Advanced** tab, between **Alerts** and **Notes**, has the parts of an app's **Advanced** tab that a database takes. Its engine sets the rest (health check, nodes and replicas, container settings and ports).

- **Move to another node** copies the database to another node while it is stopped and starts it there with the same data, users and passwords. Before you click **Move**, the card says what happens on the node you pick, and while the move runs it shows the move with its log. Meanwhile the header says **Moving to `<node>`...**, with **Cancel move** while the data is copied (see [While it moves](/guides/moving-services#while-it-moves)). **Move to another node** is in the database's menus too. See [Moving a database](/guides/moving-services#databases).
- **Resource limits**: memory limit and reservation, CPU weight and process limit. A database has no **Deploy** button, so **Save and restart** saves them and, after a confirm, restarts the database with them. It is offline for a few seconds and its data stays. A memory limit below what it uses stops it, so leave room for its caches.
- **Restart after a crash**, the crash policy (see [Crash policy and alerts](/features/crash-policy-and-alerts)).

## Change the version

New in 0.2.9. A database's **Settings** tab has a **Version** card: the version and image it runs, the versions of Seylo's catalog it can change to under **Change to**, and, new in 0.2.11, **Use another image** for any other tag or digest of its engine's image. The version in the page header links to it. Pick a version and click **Change version**, or give another image: the database deploys on the same data, with a short outage while it restarts. Changing the version takes the right to deploy the database.

The card and the header show the version the image's tag names, such as "MongoDB 8.2" for `mongo:8.2.12`, or the image when the tag names none, such as "MongoDB (mongo:latest)".

A newer image of the version that runs is a patch update: no backup needed, and the dialog's button is **Update**. Between the catalog's versions, these changes take no risk, since the engine upgrades its own data files in place:

| Engine | Changes without a risk |
| --- | --- |
| PostgreSQL, with or without pgvector | Patch updates only. A major upgrade needs a dump and restore into a new database. |
| MySQL | 8.0 to 8.4 |
| MariaDB | One version at a time: 10.11 to 11.4, then 11.4 to 11.8. The container upgrades its system tables on the first start of the new version. |
| MongoDB | One version at a time: 7.0 to 8.0, then 8.0 to 9.0 |
| Redis, Valkey, ClickHouse | Any newer version |
| KeyDB, Dragonfly | Patch updates only |

Each of them ran on the real images in Seylo's test setup; see [Tested version changes](/guides/database-engines#tested-version-changes). The **Change to** list leaves out the image that runs, and a version that takes a risk has a short note under it, such as "Skips a version".

<Callout type="warn" title="A new version cannot be undone">
Older versions cannot read the upgraded data files. Going back means restoring a backup into a new database.
</Callout>

### What can go wrong

Changed in 0.2.11: every other change used to be refused. Now the confirm dialog lists under **What can go wrong** one line for each risk the change takes, and the change goes ahead once you tick **I understand**:

| Risk | What can go wrong |
| --- | --- |
| An older version, or an older release of the version that runs | Data files a newer version or release wrote may not open on it. MongoDB 8.0, for one, refuses 9.0 data whose feature compatibility version is 9.0. |
| A Postgres major, up or down | Postgres does not open another major's data files without pg_upgrade or a dump and restore, which do not run here, so it will most likely not start. |
| A version that keeps its data in another folder, such as Postgres 17 to 18 | Seylo runs it on the folder of the data that runs, so it will most likely not start. |
| A newer version of KeyDB or Dragonfly | They take patch updates only: another version may not read the data files. |
| A skipped MongoDB, MariaDB or MySQL version | They upgrade one version at a time, so it may refuse the data files. |
| A version Seylo does not offer, as the target or as what runs | Not tested by Seylo, for example: `mongo:8.2.12` is MongoDB 8.2, which Seylo does not offer. |
| A floating tag such as `mongo:8.2` or `latest`, as the target or as what runs | It is not an exact release: it moves to each new release, so the release behind it can change on the next deploy, and Seylo cannot check it against what runs. An earlier deployment of the tag that pulled an older release is not offered as a rollback (see [Rollbacks](#rollbacks)). |
| A digest as the target, or a database that runs an image known by its digest only | It does not show which release it is, so Seylo cannot check the change. |
| Another Postgres base system, such as Debian's `postgres:17.6` on an Alpine database | Its C library may sort text in another order, so indexes on text columns may need `REINDEX`. The database starts as usual, so the old container does not come back for this one. |

For a MongoDB move to another version or image, the list also says that MongoDB may refuse data whose feature compatibility version it does not support (see [MongoDB](#mongodb)). It ends with "If the new version never gets healthy, the old container comes back on the same data."

For a version in the list, the dialog shows the risks when it opens. For another image it learns them from the panel: the first click on the dialog's button changes nothing and shows them, and the next one, after **I understand**, makes the change. The deploy's log says `Risk accepted:` with the risks.

### What protects the data

- **The old container comes back.** A database deploys by replacing its container on the same data. If the new one does not become healthy within 5 minutes, the old container comes back on the same data, and the card says "The change to `<image>` did not finish, so the database still runs `<image>`." Pick it again to retry, or stay on the image that runs (see [Use another image](#use-another-image)). That catches a version that refuses the data files and does not start. It does not undo what a new version already wrote: MongoDB data stays readable by the old version after one of the upgrades in the table above, but MySQL and MariaDB may already have upgraded their files, which the old version can refuse: then restore the backup into a new database. A change that starts healthy also stays, such as another Postgres base system.
- **A backup first.** Every change but a newer patch of the version that runs asks for a successful backup from the last 24 hours, a change that takes a risk included. If there is one, the confirm dialog shows when it finished. Without one, **Back up now** runs the database's backup schedule right there (**Set up backups** when it has none), or tick **Change without a backup**.
- **`PGDATA` for Postgres.** Before a Postgres move that could start on an empty database, Seylo pins the folder of the data; see [Postgres and PGDATA](#postgres-and-pgdata).

While the change deploys, the card shows **Deploying `<image>`** with **View log**.

### Postgres and PGDATA

New in 0.2.11. Postgres images from 18 on keep each major's data in a folder of its own, such as `/var/lib/postgresql/18/docker`, so an 18 database's volume is at `/var/lib/postgresql`. Older images look in `/var/lib/postgresql/data` and declare that folder a volume of its own, so on an 18 database's volume Docker gives it an anonymous volume: a 17 image there would start healthy on an empty database, the old container would not come back, and whatever was written there would go with the container on the next deploy.

So before a Postgres database whose volume is at `/var/lib/postgresql` moves to another version, or from or to a tag that names no release, Seylo sets `PGDATA` in the database's own variables to the folder of the data that runs, with a comment that says why. For a database on 18 that is `/var/lib/postgresql/18/docker`; otherwise Seylo reads it from the running container, and when it cannot, nothing changes. The deploy's log says `PGDATA set to <folder>, the folder of the data that ran.` Every image of the database then runs on that folder, so a version that cannot read the data fails to start, and the old container comes back with the data. In Seylo's test setup, a Postgres 18 database set to 17 this way never got healthy and came back on 18.

For a Postgres 18 database that means:

- Its first change to another version, or to a tag without a release, leaves `PGDATA=/var/lib/postgresql/18/docker` in its variables, also when the change did not finish, and every later image runs on that folder. Through the API, `env.get` shows it.
- A `PGDATA` you set in its variables yourself stays, and Seylo sets none.

A database on 15, 16 or 17 has its volume at `/var/lib/postgresql/data` and gets no pin: an older image looks there and refuses another major's data, and Postgres 18 refuses a volume at that old folder. In the test setup, a 17 database set to 18 never got healthy and came back on 17.

A database made from a Postgres tag that names no release, such as `postgres:latest` or a digest, gets `PGDATA=/var/lib/postgresql/docker` when it is created, so its data stays on the data volume whatever release the tag pulls.

### What is still refused

These changes stay refused, whatever you accept, and nothing changes:

- An image of another repository. A database takes its engine's own image only: `postgres` (`pgvector/pgvector` with pgvector), `mysql`, `mariadb`, `mongo`, `redis`, `valkey/valkey`, `clickhouse/clickhouse-server`, `eqalpha/keydb` or `ghcr.io/dragonflydb/dragonfly`, with or without `docker.io/`. Seylo's settings for it (its environment, data folder, health check and command) are made for that image. So a Postgres database also stays with or without pgvector.
- A database that is not placed on a node.
- A stopped database: the deploy would start it. Start it first.
- A database with a deploy running: wait for it to finish.
- The image that already runs: nothing to change. The one exception is turning MySQL 8.4's old logins on or off (see [MySQL 8.4 and mysql_native_password](#mysql-84-and-mysql_native_password)).

While the database is stopped, deploying or not placed on a node, **Change to** is disabled and **Use another image** is not there. A step that runs before the change refuses it too when it fails, with nothing changed: MongoDB's compatibility step, MySQL's account check, and reading where Postgres keeps its data.

### Use another image

New in 0.2.11, in place of 0.2.10's **Another tag of `<engine>` `<version>`**. **Use another image** opens **Run another image of `<engine>`?** on an **Image** field, filled in with the image that runs ("The database runs `<image>`. Give the image to run instead."). Type any tag or digest of the engine's own image:

- A newer release of the version that runs, such as `mongo:8.0.40` on a MongoDB 8.0 database before the catalog has it: a patch update, with **Update** and no backup.
- Another version, such as `mongo:9.0.8` or `mongo:8.2.12`: the same rules as the list, with the backup step, and a risk for a version Seylo does not offer.
- A floating tag (`mongo:8.0`, `mongo:latest`), a digest (`mongo@sha256:...`) or an old release: a risk.

The rules judge from what runs, read from the tags: the version a tag names (major.minor, a Postgres major, 26.8 for ClickHouse's 26.8.36.3), and whether it names an exact release. Until the panel answers, the dialog reads the version from the tag the same way, so a change of version shows the backup step at once. KeyDB and Dragonfly take it too: a newer version of them is a risk. Images other than the catalog's are not tested by Seylo.

After a change that did not finish, the field starts from the image that still runs, and the dialog is **Stay on `<image>`?**: **Update** sets it again, the database restarts on it, and the card no longer says the change did not finish. On an image newer than the catalog's image of its version, the list shows that catalog image as **older**, with its risk.

### MongoDB

Before a one-step upgrade between the catalog's MongoDB versions (7.0 to 8.0, 8.0 to 9.0), Seylo sets the feature compatibility version (`featureCompatibilityVersion`) of the running database to the version it runs, and the dialog says so. If that fails, nothing changes. Since 0.2.11 that is the only MongoDB move that gets the step: for any other, such as a version Seylo does not offer, a skipped or older version, a floating tag or a digest, **What can go wrong** says that MongoDB may refuse data whose feature compatibility version it does not support. In Seylo's test setup, a MongoDB 8.0 database moved to `mongo:8.2.12` kept its data with no step, and a 9.0 database set to the 8.0 image never got healthy and came back on 9.0.

### MySQL 8.4 and mysql_native_password

New in 0.2.11. MySQL 8.4 turns the old `mysql_native_password` sign-in method off. Accounts made with it, common for older apps and users made by hand, cannot sign in to 8.4, while the data is fine. So before a change from 8.0 to 8.4 the panel lists the running database's accounts that use it (MySQL's own `mysql.sys`, `mysql.session` and `mysql.infoschema` left out), and the dialog says so first. If it finds any, nothing changes, and the dialog names them (10 at most, then "and N more"), with two ways out:

- Switch them to `caching_sha2_password`, then change the version again: `ALTER USER 'user'@'host' IDENTIFIED WITH caching_sha2_password BY '…'`, which needs each account's password.
- Tick **Keep mysql_native_password logins working in 8.4** and click **Change version** again. 8.4 then starts with `--mysql-native-password=ON`, and later deploys, rollbacks, clones and 8.4 patch updates keep it. The card shows **Logins**: **Old mysql_native_password logins are on**. Switching the accounts is still the lasting fix: MySQL 9 has no `mysql_native_password`.

When the panel cannot list the accounts, nothing changes either, and the dialog shows the same checkbox, which needs no list. The check signs in as MySQL's root user, so it works for a database whose admin user is not root too, also right after a password reset, before the next deploy.

The same check runs before a move to a MySQL image from 8.4 on that Seylo does not offer, such as `mysql:9.1.0`, or to a tag that names no release, when such accounts can sign in to what runs. For both, the only way out is switching the accounts, and the dialog has no checkbox: MySQL 9 removed that sign-in method, and the MySQL a tag that names no release runs may not have it.

A MySQL 8.4 database can also turn those logins on or off without changing its image: the card has a **Keep old mysql_native_password logins working** switch with **Apply**. **Turn old mysql_native_password logins on?** (or **off?**) and **Update** restart the database on the image it runs, also a tag such as `mysql:8.4`, with nothing to accept and no backup step. Turning them off checks for such accounts first, as above. The switch is disabled while the database is stopped or deploying, and after a change that did not finish.

An exported MySQL 8.4 that ran with these logins on keeps them when it is imported (see [Export and import](/guides/export-and-import#databases)).

### Rollbacks

A rollback on the **Deployments** tab only takes a deployment of the same image the database runs: the same tag and the same release it pulled. So it never goes back across a version change or a patch update, and with a floating tag such as `mongo:8.0` or `latest`, an earlier deployment that pulled an older release behind the same tag is not offered either (a rollback runs the release that deployment pulled). What you accept on the **Version** card is for that change only. Changed in 0.2.11: the tab no longer offers **Roll back** on a database's deployments of another image, which the rollback then refused.

### Through the API and MCP

`databases.versionChoices` lists the catalog's versions, each with its `kind`, `risk` and `risks` (what `databases.setVersion` needs `acceptRisk` for) and `message`, and says `anyImage`, `repository`, `release`, `blocked` and, for MySQL, `nativePassword`. `customOnCurrent` is deprecated: it is `anyImage` while nothing blocks a change.

`databases.setVersion` takes a `version` or any `image` (then no `version` is needed), with `acceptRisk`, `confirmNoBackup` and, for MySQL 8.4, `keepNativePassword`, also alone on the image that runs. It refuses, with nothing changed: `riskNotAccepted` (`details.risk`, `details.risks`, `details.message`, `details.backupRequired`), `backupRequired`, `nativePasswordUsers` (`details.accounts`, `details.count`), `nativePasswordCheckFailed`, `fcvFailed`, `pgdataFailed`, `customImage` (another repository), `customCommand` (a MySQL database that runs its own command, not mysqld's, so `--mysql-native-password=ON` has nowhere to go), `noNode`, `stopped`, `deployRunning` and `current`. `keepNativePassword: true` on a MySQL line without that option (8.0, MySQL 9 or a tag that names no release) is a `BAD_REQUEST` with `details.field` `keepNativePassword`. `databases.create` takes `image` too. AI tools need an approval for a change (see [Approvals](/features/mcp-and-ai#approvals)).

## Clone or export a database

New in 0.2: **Clone** in the service's **More actions** menu copies a database into any project and node, empty with new passwords or with a copy of its data. See [Clone and move between projects](/guides/clone-and-move).

New in 0.2.10: to take a database to another panel, **Export…** on its **Settings** tab downloads it as a .zip, and **Add a service → Import from a file** creates it there. Its data only goes in an encrypted file, since it opens with the database's logins, and the database is stopped for the whole download. The import runs the new panel's image of its version, unless that image could read its data differently: then, with its data, the database keeps the image it ran (a newer release, a floating tag or digest, another Postgres base system). See [Export and import](/guides/export-and-import#databases).
