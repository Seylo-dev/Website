## Join a server

On **Nodes**, click **Add node**. Leave **Build images on this node** ticked, or untick it for a server that should only run services (see [Build nodes](#build-nodes)). Then click **Create join command** (if you signed in more than 15 minutes ago, the panel asks you to [confirm it's you](/people/sign-in-and-security#confirm-its-you) first). The command has a single-use token that is valid for one hour. Run it as root on the new server:

```bash
curl -fsSL https://install.seylo.dev | sudo sh -s -- join --panel 'https://panel.example.com' --token '<token>' --version '<version>'
```

New in 0.2.6: on the new server you can also run `curl -fsSL https://install.seylo.dev | sudo sh`, pick **2) Join this server to a Seylo panel you already have**, and paste the command there.

The command pipes the installer from `install.seylo.dev`, which serves it only after checking it against the signed release (see [What the installer checks](/security#what-the-installer-checks)). `--version` is the panel's own release: the installer takes the agent from that release's signed manifest, so the node gets the agent of the panel's version. A panel built without a release (a development build) leaves `--version` out, and the node gets the latest stable release. New in 0.2: on 0.1, the command had no `--version`, so a new node got the latest stable agent, whatever release the panel ran.

The installer checks the server, installs Docker when it is missing (without asking since 0.2.1, see [Docker](/installation#docker)), installs the agent as the `seylo.service` systemd unit and joins the panel. The agent creates its own Ed25519 key pair; the panel stores the public key, and every later connection is a signed challenge, so the token is useless after the first use. The node shows up on **Nodes** a few seconds later.

New in 0.2.1: the installer then waits up to a minute for the agent's first connection and ends with a block that says how it went:

- **This server is a node of the panel now.** It connected.
- **Installed, but not connected to the panel yet.** The block names the address the server could not reach and what to check: the panel server must accept connections on that port (3443 is the agents' port of a panel without a domain), and no firewall or cloud security group on the way may block it. The agent keeps trying in the background, and `seylo status` shows where it stands. The installer exits with status 0.
- **Installed, but the panel refused this node.** The token was used or expired, the pin is wrong, or the node was removed or disabled. That command never works: make a new one in **Add node** and run it. The installer exits with status 3 (see [Exit status](/installation#exit-status)).

New in 0.2.8: when the agent refuses the panel's certificate, the block says so instead of pointing at ports, and the error names who issued the certificate it got. A certificate from a CA the server does not trust (for example "Fortinet, FG800D...") means a firewall or proxy on the server's network decrypts HTTPS (TLS inspection) and re-signs every site with its own CA. The agent refuses that on purpose. Either exempt the panel's domain from the inspection in that firewall, or join over the panel's IP instead: **Add node** shows **Network decrypts HTTPS? Join over the panel's IP instead** next to a domain command, the same token over `https://<panel IP>:3443` with `--pin`. Use one of the two commands: the token works once.

New in 0.2.13: a node that already joined over the domain and went offline this way does not need to join again. Under the same link, **Already joined? Point it here** has a `seylo set-panel` command that moves it to the panel's IP and pin and keeps the node; see [Point a joined node at another address](#point-a-joined-node-at-another-address).

Also new in 0.2.8: running a join command on a node that is already joined to the same address joins again when the earlier join is dead for that address: another panel answers there (a new panel that took over an old panel's domain), the node was removed from it, or the command's `--pin` names another key. Before, the installer said "Already joined" and kept the old panel's identity. A disabled node, the same pin, a used token or an unreachable panel keep the earlier join, and the installer says what to do (enable the node, or re-run with `--force`). A node joined over the panel's IP and pin that cannot use the panel domain tries it again once a day instead of every hour, and stays connected meanwhile.

A node only needs outbound access to the panel, plus inbound ports 80 and 443 for the sites it serves. The panel never connects to a node, so a node behind NAT works. Load balancing between nodes adds port 5757, and the IP:port addresses the panel hands out need their own ports; see [Firewalls](/installation#firewalls).

<Callout title="The agent's connection is always encrypted">
With a panel domain, the join command uses `https://<panel domain>` and its public certificate. Without one, it uses the panel's agent port, `https://<panel IP>:3443`, with `--pin sha256:...`: the panel's own key, made once at install, which the agent then trusts and nothing else. The panel server needs port 3443 open to your nodes (the installer opens it in ufw or firewalld). The agent refuses a plain `http://` panel on another server unless you add `--insecure`.

A command made on the panel's tailnet URL still uses the domain or the agents' port: nodes don't connect over the tailnet in 0.2.1. Once every node connects over the domain, the panel can close the agents' port (see [Serve on IP address](/self-hosting/the-panel#serve-on-ip-address)).
</Callout>

Then add a wildcard DNS record for the node so its services get automatic domains:

```text
*.de2.example.com   A   <node IP>
```

and set `de2.example.com` as the node's **Wildcard domain** in its settings.

### Build nodes

New in 0.2.1: whether a new node builds images is chosen in **Add node**, with **Build images on this node**, which is ticked by default. The choice is part of the join command, and once a command is on screen the dialog says which it makes. To change it, click **Change**: that revokes the command on screen, so only one stays valid, and you create a new one. A command that was already used can't be changed; set **Can build** for its node in the list instead.

- The node itself can't change it: `--can-build` on the node only sets `can_build` in its `config.yml`.
- A node that joins again (`--force`, or after a master key rotation) keeps its own **Can build**, on or off.
- Join commands made before the panel's update to 0.2.1 still make nodes that don't build.
- Nodes that joined before 0.2.1 keep their setting. Turn on **Can build** on **Nodes** for the ones that should build.

A build node gets the source, git credentials and build-time variables of everything it builds, from any project, and the images it builds run on every node (see [Where builds run](/guides/github-and-git#where-builds-run)). Untick the box for servers you do not fully trust. Services build on their own node first, so with the default, services on a joined node build there instead of on the panel's node. Nodes that are a poor fit show a warning next to **Can build**: **Less than 2 GB of memory**, **Only one CPU core** or **docker buildx is missing**. A node whose agent reports no docker buildx gets no automatic builds; install `docker-buildx-plugin` on it (Docker from get.docker.com has it).

In 0.2, a new node never built until an owner or admin turned it on. On 0.1, `--can-build` on the join command turned it on.

## When the panel gets a domain

Nodes that joined over `https://<panel IP>:3443` move to the [panel domain](/self-hosting/the-panel#give-the-panel-a-domain) by themselves once it is active. The panel asks each of them to reconnect; the agent connects to `https://<panel domain>`, checks the certificate against the server's trusted certificate authorities and that the same panel answers there, and only then saves the new address in `/var/lib/seylo/config.yml`. The old pinned address stays as a fallback: if the domain stops answering for 5 minutes (removed, or its DNS changed), the node reconnects through it and moves on to the next domain by itself. Changed in 0.2.15: a connect that fails on a certificate the node will never trust (an issuer it does not trust, or a key that is not the pinned one, as when the node's network starts decrypting HTTPS) goes to the fallback on the next attempt, not after 5 minutes. The agent then makes the IP and pin its address again, raises one alert and stays there (see [Panel address](#panel-address)). A timeout or a refused connection still waits the 5 minutes, so a short panel restart does not move a node off its address, and so does Traefik's own default certificate, which the panel's server answers with while it has no certificate for the name (its proxy just restarted, or a certificate is being issued again). The node's sheet on **Nodes** shows the address it uses under **Connects to**. The panel's own node keeps connecting over the server's loopback.

A move that fails (for example because the node does not trust the domain's certificate) keeps the old address, raises a **Node health check failed** alert with the reason, and is tried again after an hour or when the agent restarts. Changed in 0.2.15: a move that failed because the domain's certificate came from an issuer the node does not trust, or did not match the pin, is remembered on the node, in `/var/lib/seylo/state/panel.json`. Before, the wait lived only in memory, so every agent restart, an update included, tried the move again, dropped the first session the panel accepted and raised the same alert again. The wait ends when the panel stops naming that address or names another, or when the move works. After adding a certificate authority to a node's trust store, move the node by hand with `sudo seylo set-panel '<panel URL>'` (see [Point a joined node at another address](#point-a-joined-node-at-another-address)); for other failures, `systemctl restart seylo` reloads the trust store and tries again.

Two kinds of node do not move by themselves:

- Nodes that joined over plain HTTP (`--insecure`) never move: nothing on a plain connection proves the new address comes from your panel. Run a new join command from **Add node** on them with `--force` added. The node keeps its key, so the panel keeps the same node and its services.
- Nodes that joined with a panel domain have no pinned address to fall back on. If you remove or change the domain, run a new join command with `--force` on them too, or, new in 0.2.13, point them at the panel's IP with `seylo set-panel`, which needs no token (see [Point a joined node at another address](#point-a-joined-node-at-another-address)). New in 0.2.1: while nodes connect over the domain, **Settings → General** asks before it removes or changes it, and names them.

While the agents' port is closed (see [Serve on IP address](/self-hosting/the-panel#serve-on-ip-address)), nodes have no fallback either, and the panel makes no join command until the port is open again or the domain is active.

## Panel address

New in 0.2.15. A node's **Settings** has a **Panel address** choice:

- **Follow the panel's domain**, the default and how every node worked before: the node moves to the panel's domain once it is live (see [When the panel gets a domain](#when-the-panel-gets-a-domain)), so it finds the panel if its IP address changes.
- **Stay on this address**: the node keeps the address it connects to now, usually the panel's IP and pin, and the panel never names its domain to it.

**Stay** is for a server whose network decrypts HTTPS: a firewall doing TLS inspection re-signs the domain's certificate, the agent refuses it, and moving to the domain only cuts the node off. The choice saves at once. Choosing **Follow** on a connected node reconnects it, so it moves at once. The panel's own node has no choice: it reaches the panel on its own server.

Besides your own choice, three things put a node on **Stay**, and **Settings** then says which:

- `sudo seylo set-panel` on the node sets it (see [Point a joined node at another address](#point-a-joined-node-at-another-address)), also when `config.yml` already points at that address because someone edited it by hand.
- A join with `--pin` at the panel's IP address while the panel has a domain sets it: that is the second command of the **Add node** dialog, **Network decrypts HTTPS? Join over the panel's IP instead**. The request goes with the join only, so a node that joined a panel before 0.2.15 that way follows a domain added later.
- While a node has an open "could not move to the panel address" alert because its network re-signed the domain's certificate, the panel keeps it on **Stay** until you choose. **Settings** says why: "Kept here because the node's network re-signed the panel domain's certificate (TLS inspection), see the node's alert. Choose Follow to try the domain again." An alert about Traefik's own default certificate does not count: the panel's server answers with it while it has no certificate for the name, which passes on its own.

The setting works for every node. `set-panel` and the join ask for **Stay** from agent 0.2.15: the agent writes `stay_on_address: true` to `config.yml`, sends it on its next connect, and removes it once a panel answered.

In the API and MCP, `nodes.updateSettings` takes `panelAddressChoice` (`follow` or `stay`, in the activity log), and `nodes.get` returns `panelAddressChoice`, `panelAddressChoiceBy` (`owner`, `node`, `join`, `inspectedCertificate` or `default`) and `panelAddressChoiceAt`. The panel's own node has none of them.

## Why a node is offline

New in 0.2.15. An offline node's row on **Nodes** says why when the panel knows: the connect it refused since the node was last seen, for example "Refused 4 min ago: This agent (0.2.1) is too old for this panel..." or a signature that does not match the node's key, else when it was last seen ("Last seen ...").

Once a node is back, its agent tells the panel the last connect error it had while away, which the panel could not see: a certificate it refused, a name it could not look up, a connection that timed out. The node's page shows it for a week:

```text
Was offline from 17:39 to 17:46: dial panel: x509: certificate signed by unknown authority ...
```

The agent keeps that error across a restart while it is away, in `/var/lib/seylo/state/panel.json`. The report comes from nodes on agent 0.2.15. In the API, `nodes.list` and `nodes.get` have `rejectedHello` for an offline node, and `nodes.get` has `lastOffline` (`from`, `to`, `reason`, `failedAttempts`).

## Point a joined node at another address

New in 0.2.13. `seylo set-panel` changes the address a joined node connects to and keeps the node: its id, its services and its own settings in `/var/lib/seylo/config.yml` stay (only the panel address settings change, see [What it does](#what-it-does)), and it needs no join token. Use it on a node that joined over the panel's domain and went offline because:

- its network began decrypting HTTPS. A firewall doing TLS inspection, such as a FortiGate, re-signs the domain's certificate, and the agent refuses it. `seylo status` on the node names the certificate's issuer and this command (see [Troubleshooting](/troubleshooting)).
- the panel's address changed under it: you removed or changed the panel domain while the node connected over it.

A node that joined over the panel's IP and moved to the domain later does not need it: it keeps the pinned address as a fallback and connects through it once the domain failed for 5 minutes (see [When the panel gets a domain](#when-the-panel-gets-a-domain)).

### Get the command

On **Nodes**, click **Add node**, then **Create join command**, then **Network decrypts HTTPS? Join over the panel's IP instead**. Under the join command over the panel's IP, **Already joined? Point it here** has the command, filled in with the panel's IP address, agents' port and pin:

```bash
sudo seylo set-panel 'https://203.0.113.10:3443' --pin 'sha256:<key>'
```

It carries no token, so the join command above it stays unused and expires after an hour. The dialog shows it while the join command uses the panel domain and the **Agents' port** switch on the **Panel domain** card (**Settings → General**) is on. Without a panel domain, the join command itself uses `https://<panel IP>:3443` with `--pin`, and the dialog has no **Already joined?** line: take the address and pin from that command.

### What it does

Run it as root on the node. Before it writes anything, it connects to the address with the pin, resumes there as this node with the node's own key, and checks that the panel answering is the one this node belongs to, by the panel id and identity key the node recorded (see [The panel's identity](#the-panels-identity)). That is the same check the agent makes on every connect. The panel shows the node online for a moment and keeps what it knows about it (its addresses and machine details) as it was. When the check passes, the command:

1. copies `config.yml` to `config.yml.bak` (a second run replaces that copy),
2. writes the new `panel_url` and `panel_pin` to `config.yml`, keeps the old address under `fallback` until the agent has connected at the new one, and drops `insecure_transport` (set again only for a plain `http://` address with `--insecure`) and `trust_on_first_use`. New in 0.2.15, it also writes `stay_on_address: true`, so the agent asks the panel to keep the node on the new address ([Panel address](#panel-address) **Stay**). Everything else stays, the node's id and the panel's identity included,
3. restarts the agent,
4. waits up to 30 seconds for the agent to connect and prints its `Panel:` line, as `seylo status` does:

```text
Checking https://203.0.113.10:3443...
https://203.0.113.10:3443 is the panel this node belongs to (panel id <panel id>, version 0.2.13).
Wrote /var/lib/seylo/config.yml (panel_url https://203.0.113.10:3443, panel_pin sha256:<key>); the previous file is /var/lib/seylo/config.yml.bak.
Restarted the agent.
Panel:   https://203.0.113.10:3443 (connected)
```

When the agent has not connected by then, it also prints the `Error:` line and how to go back: `sudo cp /var/lib/seylo/config.yml.bak /var/lib/seylo/config.yml && sudo seylo restart`.

Nothing changes, and the command ends with "config.yml was not changed", when:

- another panel answers at the address ("answers as another panel"). To move a node to another panel, join it there with a join command from that panel's **Add node**.
- the address does not present the key `--pin` names ("did not present the key --pin names"). Copy the pin from **Add node** again. When the error names the issuer of a firewall, the network decrypts the connection to the panel's IP too, and only an exemption in that firewall helps.
- nothing answers there ("could not connect to").
- the panel refuses the node, for example because it was removed from **Nodes**. The command prints the panel's reason.

Three refusals still change the address, since the panel signs them with its identity key: the agent is connected through the old address right now (it connects through the new one after the restart), the panel needs a newer agent (the agent updates itself once it connects), or the node is disabled (it connects once it is enabled again on **Nodes**). The command says which. When `config.yml` already has that address and pin, nothing changes either. Changed in 0.2.15: if it does not have `stay_on_address` yet, for example because the address was edited in by hand, the command writes only that, restarts the agent and says "Wrote stay_on_address to it: the agent asks the panel to keep this node on that address." A node that never finished joining (`config.yml` has no `node_id`) or has no `agent.key` is refused: join it again with a new join command and `--force`.

`--pin` needs an `https://` address. Without `--pin`, the address's certificate must come from a CA the server trusts, for example a new panel domain with a Let's Encrypt certificate: `sudo seylo set-panel 'https://panel.example.org'`. A plain `http://` address on another server needs `--insecure`, as for `join`, and the agent's traffic can then be read on the way.

### After the move

Changed in 0.2.15: with agent 0.2.15 on the node, `set-panel` puts the node's [Panel address](#panel-address) on **Stay**, so the panel no longer names its domain to it and the node stays on the panel's IP. Once the firewall exempts the panel's domain, choose **Follow the panel's domain** in the node's **Settings**: the node reconnects, moves to the domain, and the pinned IP stays as its fallback.

On a node that follows the domain, the panel names it each time the node connects, so the agent tries it. Behind TLS inspection the domain's certificate is refused again: the node stays on the panel's IP, raises a **Node health check failed** alert that says its network may decrypt HTTPS, and tries the domain again after 24 hours or when the panel names another address. Before 0.2.15 an agent restart tried it again too.

### Agents before 0.2.13

`set-panel` comes with agent 0.2.13. A node that went offline before it updated can't get the update, since agents update from the panel. On that node, keep a copy of `/var/lib/seylo/config.yml` and edit it as root: set these two lines to the address and pin of the dialog's join command over the panel's IP (a node that joined over the domain has no `panel_pin` line yet, so add it),

```yaml
panel_url: https://<panel IP>:<agents' port>
panel_pin: sha256:<key>
```

then run `sudo seylo restart`. Nothing checks the address before the restart, but the agent refuses any other panel when it connects, as always. Once it is back and updated, choose **Stay on this address** in its **Settings** (see [Panel address](#panel-address)), or run the `set-panel` command with the same address and pin, which since 0.2.15 writes only `stay_on_address` then.

### Or join again

A new join command with `--force` added keeps the node too: the panel knows the node by its key, and `--force` keeps the rest of `config.yml` (see [The panel's identity](#the-panels-identity)). It needs a new token, and it forgets the panel identity the node recorded and writes down the one of the panel that takes the token, where `set-panel` only accepts the panel the node already belongs to.

## The panel's identity

New in 0.2. At its first connect to a 0.2 panel (its join, or the first connect after the update), a node writes down the panel's id and the panel's identity key in `/var/lib/seylo/config.yml`. From then on it refuses any other panel, at any address: one that names another id, or does not prove it holds that key, is closed before it can send the node anything. So someone who gets a valid certificate for the panel's domain (a lapsed domain, a hijacked DNS record) cannot take the node over, and a node with a pinned fallback address goes back to it.

The identity stays the same through updates, restarts and a restore of the panel's own backup (`panel.db` with its `master.key`). It changes when:

- the panel is installed again from scratch (a new `/var/lib/seylo/panel/`),
- `panel.db` from another panel is restored,
- the master key is rotated with `--new-panel-identity` (see [If a copy leaked](/self-hosting/backups#if-a-copy-leaked)).

After that, every node refuses the panel. It shows offline on **Nodes**, `seylo logs` on the node says the panel's address "answers as another panel" or "answers with another panel identity key", and its services keep running. Join each node again: on **Nodes**, **Add node** gives a new token (one node per token) and the panel's address and pin. Run the dialog's command with `--force` added at its end, or `seylo join` on the node itself:

```bash
sudo seylo join '<panel address>' --token '<token>' --pin '<pin>' --force
```

On the panel's own node, join over loopback:

```bash
sudo seylo join http://127.0.0.1:3000 --token '<token>' --can-build --force
```

After a key rotation, `seylo panel rotate-key` prints these commands for every node, with the new pin (see [If a copy leaked](/self-hosting/backups#if-a-copy-leaked)), and the panel still knows each node by its key, so it keeps the same node and its services.

New in 0.2: `--force` keeps the rest of `/var/lib/seylo/config.yml`. It replaces only the panel's address and pin, the token and the old panel's identity; settings you added there by hand (`no_host_shell: true`, `git_proxy_resolves: true`, `acme_ca` and the like) stay, and so do comments and keys this agent does not know. `--name` changes the node's name, and `--can-build` or `--can-build=false` the `can_build` setting in `config.yml` (the installer takes `--can-build` or `--no-can-build`); without them both stay as they were. Whether the panel sends a node builds is **Build images on this node** in the panel, which a re-join does not change. On 0.1, `--force` wrote the file again from scratch, so settings added by hand were lost.

## Latency

All traffic between a node and the panel goes over one WebSocket that the node keeps open. Reads in the panel come from the panel's own copy of each node's state, and an action is one round trip with progress pushed back, so a panel in Germany managing a node in the US feels close to a local one.

If the connection drops, the agent reconnects with backoff. Its services keep running, restarting and routing meanwhile, and anything it has to report (crashes, deploy results, cron runs, backups) waits on its disk until the panel has it.

The **Settings** action on a node:

| **Name**, **Location**, **Tags** | How the node shows up in the panel |

Used for IP:port links, exposed databases, load balancing and join commands. Uptime checks may also target it when it is a private address (see [Uptime checks](/features/uptime-checks#where-checks-run-from)). A git server on it, as on any of the node's addresses, needs an owner or admin to allow it per project (see [Git servers on private addresses](/guides/github-and-git#git-servers-on-private-addresses)). The field shows what **Auto** runs on the node now ("Auto - 7 now"), and it follows the machine: a node that comes back on other hardware gets the new number. New nodes start on **Auto**; nodes from before 0.2.15 keep their number until you pick **Auto**. It needs no agent update. In the API and MCP, `nodes.list` and `nodes.get` have `parallelBuildsAuto`, with `maxParallelBuilds` the number that applies now; `nodes.updateSettings` takes `parallelBuildsAuto` (`true` for Auto, `false` to keep the number that applies now as a fixed one), and `maxParallelBuilds` alone still sets a fixed number and turns Auto off. |
| **Logs per service (MB)**, **Keep logs (days)** | How much service log history the node keeps |
| **Panel address** | New in 0.2.15: **Follow the panel's domain** or **Stay on this address**. Not on the panel's own node. See [Panel address](#panel-address). |
| **Game servers first** | Only on nodes with Wings, see [Running next to Wings](/guides/running-next-to-wings) |
| **DNS cache for containers** | New in 0.2.17, off by default, needs agent 0.2.17: the node answers its containers' DNS lookups from a cache and passes the rest on. See [DNS cache for containers](/guides/node-health#dns-cache-for-containers). |

Builds and where they run are described in [Deploy from GitHub or Git](/guides/github-and-git#where-builds-run).

## Health, updates and reboots

Click a node's name on **Nodes** to open it. Its **Overview** has the machine actions, and the row has **Health** and **Settings**:

- **Health** runs the node's health checks: Docker, disk, clock, ports 80 and 443, DNS, the proxy, Wings and more, each with a fix. See [Node health checks](/guides/node-health).
- **Update now** updates the node's agent to the newest release on the panel's [release channel](/self-hosting/updates#release-channel), and refuses when the node already runs that release or a newer one; see [Updates](/self-hosting/updates).
- **Update Docker** upgrades Docker Engine with the system's package manager (apt, dnf or yum) and shows the versions first. With Docker's live-restore on (the installer turns it on, see [Docker live-restore](/installation#docker-live-restore)), containers keep running while the daemon restarts. When it is off, the dialog warns that every service on the node stops until the agent starts it again. New in 0.2: an update the node sends no result for within an hour (the agent restarted mid-upgrade, or the node went away) fails, and so does one for a node that was removed, so it no longer blocks later updates.
- **Reboot** reboots the machine. Services on the node are down until the machine and Docker are back; Seylo moves nothing away for you. The agent reconnects by itself.
- **Agent logs** shows what the agent wrote: connects, deploys and errors.

On the node itself, `seylo status`, `seylo health` and `seylo logs` show the same from the command line; see the [CLI reference](/reference/cli).

Changed in 0.2.15: `seylo status` names the node as the panel does. It printed the server's hostname, or the name given when it joined, so a node renamed in the panel showed under another name on the server. Once the agent has connected it shows the panel's name, a rename made while it is connected included, also after a restart while the panel is away. Before the first connect it is the name given when it joined, else the hostname, as before.

## Disk cleanup

**Settings → Docker cleanup** frees disk space on one node: unused images, build cache, stopped containers and orphaned service data, with a preview first. New in 0.2: a node can also clean up by itself, on a schedule or when a disk fills up, from its **Cleanup** view. Only what Seylo created is touched. See [Docker cleanup](/guides/docker-cleanup).

## Host shell

New in 0.2: a node's **Shell** view opens a root shell on the server itself, in the browser. It is off on every node until the owner turns it on. See [Host shell](/guides/host-shell).

## Remove a node

**Remove node** in the node's settings forgets the node and its key. Containers on the machine are not touched, so move its services away first. The node that runs the panel cannot be removed. To clean up the machine itself, see [Uninstall](/self-hosting/uninstall).
