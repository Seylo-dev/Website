Each node runs Traefik on ports 80 and 443 (or shares the one Wings runs, see [Running next to Wings](/guides/running-next-to-wings)). A service's **Domains** tab decides which hostnames reach it.

## Automatic domains

Give each node a wildcard DNS record once:

```text
*.de1.example.com   A   203.0.113.10
```

and set `de1.example.com` as the node's **Wildcard domain** in its settings on **Nodes**. From then on the **Domains** tab of a service on that node offers `<service>.de1.example.com`: click **Add** and it works right away, with no DNS change. Templates add one by themselves.

Certificates come from Let's Encrypt over HTTP, one per hostname, so the panel never needs a DNS provider token.

## Custom domains

Click **Add domain**, enter the hostname and the **Container port**. Left empty, it is the service's port: its first TCP port, or for an app built from a repository with none, the port its other domains use, else 80, the same `PORT` it gets (changed in 0.2.3: before, it suggested 3000). In **Edit routing**, an empty field keeps the domain's port. Changed in 0.2.12: the field takes any port, also one the app listens on without declaring it. On a service with TCP ports, the arrow at the end of the field lists them to pick from; before, the field was a list of those ports only. The row shows the record to create where the domain's DNS is managed: an `A` record (and `AAAA` when the node has IPv6) pointing at the node. When the zone is on Cloudflare, **Open Cloudflare DNS** opens Cloudflare with the record filled in; the panel never asks for a Cloudflare API token.

The panel checks the record through public resolvers and shows one of:

| Status | Meaning |
| --- | --- |
| DNS ok | The domain points at the node |
| Waiting for DNS | No record yet |
| DNS points elsewhere | The record points at another address |
| Behind Cloudflare proxy | Proxied by Cloudflare, so DNS shows Cloudflare's addresses. The origin check below tells whether Cloudflare reaches the node. |

New in 0.2.5: each row names the IP its record should point at, next to the status.

### Behind Cloudflare's proxy

New in 0.2.5: for a proxied domain the panel also runs an **origin check**. It asks `http://<domain>/.well-known/seylo-origin/<random>` and the node's agent answers with a signature only that node can make, so the panel knows whether the record in Cloudflare reaches this service's node, not just Cloudflare. The check runs a few seconds after you add the domain, on **Check DNS** and before **Regenerate certificate**.

- **Reaches the node**: the record in Cloudflare is right; the certificate follows.
- **Points elsewhere**: something else answered (an old server, another host). Fix the record in Cloudflare to point at the IP the row shows. Until then **Regenerate certificate** refuses, since Let's Encrypt reaches the domain the same way and would fail.
- No answer (Cloudflare's 52x, a timeout, an agent older than 0.2.5): the panel cannot tell, and says nothing either way.

A certificate that stays on **Generating** behind the proxy says why under the row: usually the record does not reach the node yet, or **Always Use HTTPS** is on (see below).

New in 0.2.8: a custom domain does not ask Let's Encrypt for its certificate until it reaches the node: its record points at the node, or behind Cloudflare the origin check says **Reaches the node**. Until then the row says the certificate waits for DNS, the route serves the node's own certificate, and no failed validation counts against Let's Encrypt's limit of 5 per host name per hour. The panel checks waiting domains again on its own, and **Check again** on the row checks at once; the certificate starts as soon as one says the domain arrived. Automatic domains (the node's wildcard record) and domains with their own certificate never wait. Also fixed in 0.2.8: a proxied domain whose certificate was issued kept showing **Generating**.

Cloudflare's free certificate covers your domain and one level of subdomain (`example.com`, `*.example.com`), not deeper ones such as `app.eu1.example.com`. For a node's automatic domains under `*.eu1.example.com`, set that wildcard record to DNS only (grey cloud) so visitors get the node's Let's Encrypt certificate. The check only connects to public addresses or this panel's own nodes, never to a private network a domain may resolve to.

As soon as the domain reaches the node, Traefik requests a certificate and the route goes live. A certificate that cannot be issued shows **Certificate failed** with the reason from Let's Encrypt, and raises an alert.

<Callout type="warn" title="Cloudflare proxy">
With Cloudflare's proxy (orange cloud) on, set SSL/TLS to **Full (strict)** and turn off **Always Use HTTPS**. Flexible mode sends plain HTTP to the node, which redirects to HTTPS, which loops. Always Use HTTPS sends Let's Encrypt's check of `http://<domain>/.well-known/acme-challenge/` to HTTPS, where the node does not answer it, so the certificate is never issued or renewed. **Redirect HTTP to HTTPS** on the domain still sends visitors to HTTPS.
</Callout>

### The panel behind Cloudflare

The panel's own domain can be proxied by Cloudflare too, with the same settings (see [Behind Cloudflare's proxy](/self-hosting/the-panel#behind-cloudflares-proxy) for how the panel checks it). Requests then reach the node from Cloudflare's addresses, not the visitor's, and Cloudflare passes the visitor's address in its `CF-Connecting-IP` header. New in 0.2: the panel reads that header. Anyone can send it, so the panel and its API believe it only on requests that came from Cloudflare's published address ranges through the node's own Traefik, its trusted proxy. On any other request, for example one sent straight to the node's IP, the header is ignored and the connection's own address counts.

That way sign-in limits, **Sessions**, the activity log and the command line approval page see each visitor's own address, instead of a few Cloudflare addresses that many people share.

### Domain options

| Option | What it does |
| --- | --- |
| **Path** | Only requests under this path reach the service. `/` is the whole domain. |
| **Strip the path before forwarding** | `example.com/api/users` reaches the service as `/users` |
| **HTTPS** | Let's Encrypt (default), a custom certificate, or plain HTTP only |
| **Redirect HTTP to HTTPS** | Send plain HTTP visitors to HTTPS |
| **Redirect only** | Send every request to another URL instead of the service, for example `www` to the bare domain. Choose **Permanent** and **Keep the path and query**. |
| **Make it the primary domain** | The primary domain is what `${{service.URL}}` and IP:port redirects point to. The first domain of a service is always primary, so for it the box is ticked and cannot be cleared. |

A service can have any number of domains, and each can route a path: `example.com/api` to the API and `example.com` to the web app.

### Who may use a hostname

A hostname belongs to the service that routes it. Adding it, or a path under it, to another service needs the right to edit the service that already has it, so a member can't take traffic (and its cookies) from someone else's service with a longer path. Nobody can put a service on the panel's own domain or on the hosts the nodes use for database web UIs and Boxes (`seylo-db-...` and `seylo-box-...`), and a custom certificate may not name hosts that belong elsewhere. The agent on each node enforces the same rules again.

### Custom certificates

**Upload certificate** in a domain's menu takes a PEM certificate chain and its private key; the domain switches to it. Use it for a certificate from your own CA, or a wildcard certificate you already have. It may only name hosts of this service or hosts no other service uses.

## Access rules

**Access rules** in a domain's menu add, per domain:

| Rule | What it does |
| --- | --- |
| Basic auth | Browsers ask for a user name and password before anything loads. Passwords need at least 8 characters and are stored hashed. |
| IP allowlist | One IP or CIDR per line. Everyone else gets 403. Empty lets everyone in. |
| Rate limit | Requests per source IP: an average, a burst, per number of seconds. Over the limit, visitors get 429. |
| Redirects | A regular expression on the full URL and its replacement; `$1` inserts a group |

## IP and port access

A new service with a port answers on the node's IP and a port the agent picks, until a domain works. The agent relays that port itself instead of publishing it through Docker, because Docker's published ports bypass ufw and similar firewalls. The **IP and port access** section on the Domains tab shows the address.

With **Close IP:port once a domain is live** on (the default), the address switches to a redirect to the primary domain once that domain is live, and closes 24 hours later. **Redirect visitors to the primary domain, keeping their session** carries cookies over through a short handoff link, so visitors stay signed in; cookie expiry and flags are set fresh by the app. **Open again** and **Close now** change it by hand.

IP:port access and other public ports relay TCP. UDP ports are coming later.

## Maintenance and down pages

Visitors see a page from the node's agent while a service is stopped, deploying for the first time or unreachable, and while maintenance mode is on.

- Per service, in **Maintenance and down pages** on the Domains tab: turn on **Maintenance mode**, set a **Message**, or **Upload custom HTML**. Without its own page, the service uses the global one.
- For everything, in **Settings → Maintenance pages**: **Maintenance mode for every service** makes every service answer with the maintenance page (HTTP 503) while the panel stays reachable. The global page is the built-in page with your message, or your own HTML.

Custom pages are full HTML documents up to 512 KB, served with a strict Content-Security-Policy: scripts and frames do not run on them, styles load inline or over HTTPS, and images and fonts over HTTPS or as `data:` URLs. New in 0.2: nodes send that policy, and `X-Content-Type-Options: nosniff`, with every page they serve, maintenance and down pages alike. On 0.1, the policy was missing, so scripts on a custom page ran on the service's own domains.

## Certificate limits

Let's Encrypt issues at most 50 certificates per registered domain per week. Many services and pull request previews under one domain can reach that. Spread them over more than one domain, or upload a wildcard certificate you already have to the domains that need it.
