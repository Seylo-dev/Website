<Callout title="New in 0.2">
Available from Seylo 0.2. Moving a running service to another project without restarting its containers also needs a 0.2 agent on its node.
</Callout>

Both live in the **More actions** menu (the `...` button) in a service's header: **Clone** and **Move to project**. To move a service to another node instead, see [Moving services](/guides/moving-services). To take a service to another panel, or keep it as a file, see [Export and import](/guides/export-and-import) (new in 0.2.10).

## Clone a service

**Clone** makes a new service with the same settings, in the same or another project and on any node. Pick:

| Field | What it does |
| --- | --- |
| **Project** | Where the clone goes. The service's own project by default. |
| **Node** | Where it runs. The service's node by default. |
| **Name** | `<name>-copy` by default (`-copy-2` and so on when that is taken), free in the target project |

The dialog lists what comes along before anything is created.

### What a clone gets

- **Copied**: the source (repository, image, Dockerfile or the newest upload), build settings, container settings and ports, health check, resources, crash policy, deploy strategy, replicas, notes, and a database's or Box's settings.
- **Volumes**: the same volumes, empty or with a copy of the data, see [Copy the data](#copy-the-data).
- **Environment variables and config files**: copied when you can read them on the source and may edit them in the target project. Otherwise they stay behind and the dialog says so; the clone starts without any.
- **A domain**: **Add the automatic domain** (ticked by default) gives the clone the target node's automatic domain (`<name>.<wildcard>`), with the main domain's access rules (basic auth, IP allowlist, rate limit, redirects) when it has any. It is offered when the service has a main port and is not a database, the target node has a wildcard domain and that host is still free. An app clone without it gets an IP:port address, like a new app.
- **Not copied**: domains, deploy history, cron jobs, backups, alerts, uptime checks, deploy triggers, tunnels, exposed ports, maintenance pages and sharing.

Previews are off on the clone. Turn them on in its **Previews** tab when you want them.

### Deploy on push

Changed in 0.2.12: a clone of an app built from a repository (a **GitHub**, **Git**, **GitLab**, **Gitea** or **Bitbucket** source) keeps the source's **Deploy on push**. Before, it was always off on the clone. For these sources the dialog has a **Deploy on push** switch, on when the source deploys on push, and the note under it says what a push to the branch does:

- On, and the source deploys on push too: "Each push to `<branch>` deploys both `<name>` and the clone."
- On, and the source does not: "Each push to `<branch>` deploys the clone. `<name>` does not deploy on push."
- On, for a **Git** source: "A git URL deploys on push through a deploy trigger URL, which the clone does not copy: make one on its Source tab." See the table below.
- Off: "Pushes to `<branch>` do not deploy the clone." You can turn it on later in the clone's **Source** tab.

Clones of other sources (an image, a Dockerfile typed in the panel, an upload), databases and Boxes have no switch.

The clone is created stopped, but a push does not wait for **Start**: with the switch on, the next push to the branch deploys and starts the clone. When it needs changes first, such as variables that [point somewhere else](#references-in-the-copied-variables) in another project, clone it with the switch off and turn it on once the clone is ready.

How the pushes reach the clone depends on how the repository is read:

| Source | How a push reaches the clone |
| --- | --- |
| **GitHub** through the GitHub App | The App's webhook, as for the source: every service that follows the branch with **Deploy on push** on gets the push |
| **GitHub** through the connected account, **GitLab**, **Gitea** or **Bitbucket** | A repository webhook of its own, with its own secret, created with the clone. Each of these webhooks delivers to one service, so the source's never reaches the clone |
| **Git** (a repository URL) | Its own [deploy trigger URL](/guides/github-and-git#deploy-trigger-url), which a clone never gets: click **Create URL** under **Deploy trigger** on the clone's **Source** tab and point the git host or CI at the new URL. The source's URL keeps deploying the source only |

The clone's webhook is made by the same rules as when you connect the repository on the **Source** tab (see [Push to deploy](/guides/github-and-git#the-connected-github-account) and [The webhook](/guides/git-providers#the-webhook)): the token must be allowed to create webhooks on the repository, and the webhook needs an address the git host can reach. That is the panel domain. Without one, the connected account makes no webhook, and a GitLab, Gitea or Bitbucket webhook points at the address you opened the panel at only when you may manage connections (the **Manage GitLab, Gitea and Bitbucket connections** action). While the webhook cannot be made, the panel reads the clone's branch every minute instead, as for any other service, and the clone's **Source** tab says why. A clone made with the switch off gets no webhook, and its branch is not polled.

Export and import are unchanged: an imported service still arrives with **Deploy on every push** off unless you turn it on in the import (see [Export and import](/guides/export-and-import#source)).

In the API and MCP, `services.clone` takes `deployOnPush`. Left out, the clone keeps the source's setting; other sources ignore it.

### References in the copied variables

Variables that named the source itself now name the clone: `${{web.API_KEY}}` in a service called `web` becomes `${{web-copy.API_KEY}}`, and so do host names like `web:3000` or `http://web/`. A value that is only the name (`web`) is kept as it is and listed.

In another project, the dialog also lists the variables that point at nothing there (**points at nothing there**) or at a different service of the same name there (**points at `<project>`'s**). Fix those in the clone's **Environment** tab before you start it.

### Copy the data

Under **Volumes**, pick **Start empty** (the default) or **Copy data**. A copy reads every volume on the source's node and writes it into the clone's folders on its node, through the panel, so it works across nodes.

- **Stop `<name>` while its data is copied** is ticked by default, for a consistent copy. The source starts again when the copy ends. Files copied from a running service may be inconsistent.
- A database always stops for its copy and starts again afterwards, because a running database's files are not a usable copy.
- While it runs, the clone's header shows **Copying the data of ...** with the size so far. Until it is done, neither the clone nor a source the copy stopped can deploy or start, and neither the clone nor its source can move to another node. A second copy from the same source is refused until the first ends.
- New in 0.2.12: a push to the clone's branch while its data is copied waits for the copy. **Recent deliveries** on the clone's **Source** tab lists it as **Failed**: "Its data is still being copied from `<source>`: this push deploys once the copy is done." When the copy is done, the clone deploys the head of its branch once, however many pushes waited, and those deliveries turn **Deployed**. A copy that failed deploys nothing into what arrived ("The data copy from `<source>` failed, so this push was not deployed."), and neither does a clone whose **Deploy on push** was turned off meanwhile. A push to a source the copy stopped is still refused while the copy runs, as before.
- A failed copy says why under the header. The clone keeps what arrived and can still start.
- Deleting the clone or the source ends its copy as failed, and starts a source the copy stopped.

A database clone that starts empty gets new passwords. One with a copy of the data keeps the source's logins, since they are in the data.

### Start the clone

The clone is created stopped and is not deployed. Changed in 0.2.13: once it is created, the panel opens the clone's page; before, it stayed on the source, with an **Open** button in the notice. Check its settings, then click **Start**: the first start deploys it (that needs permission to deploy). A clone with **Deploy on push** on also deploys on the next push to its branch, started or not (see [Deploy on push](#deploy-on-push)).

### What can be cloned

Apps, cron services, databases, Boxes, and compose members, which become standalone apps (their references to the other members of their stack only work in the same project). Compose stacks as a whole and the panel's own service cannot be cloned. Valkey, KeyDB, Dragonfly and ClickHouse clones need a 0.2 agent on the target node.

### Permissions

A clone needs permission to view the source and to create services in the target project. Each extra needs its own:

| What | Needs |
| --- | --- |
| Environment variables | Read them on the source, edit them in the target project |
| Config files | The same, plus changing files in the target project |
| Volume data | Reading the source's files; to stop it during the copy, also stopping it |
| The newest upload, for a source that deploys from one | Reading the source's files |
| A database's data | Seeing its credentials, and stopping it |
| The automatic domain | Editing domains in the target project; for the access rules, also viewing domains on the source |

When the source deploys with a git credential, a registry login, a GitHub App installation or a git provider connection, you must also be allowed to use it in the target project: you may manage it, or a service of that project already uses it for the same repository or image (see [Deploy from GitHub or Git](/guides/github-and-git#any-other-git-host)). A **Git** source on a private address also needs that host allowed in the target project, which an owner or admin does by cloning or saving a source with it there (see [Git servers on private addresses](/guides/github-and-git#git-servers-on-private-addresses)).

## Move a service to another project

**Move to project** re-homes a service: it joins the new project's private network and gets the new project's shared variables, its `${{name.VAR}}` references and its host name now resolve in the new project, and access follows the new project. It stays on its node, with its domains, volumes and deploy history.

Pick the **New project**. Before anything changes, the dialog lists what the move changes:

- services of the old project that reference it or use its host name: **they lose access to it**,
- services of the new project that already use its name: they **start reaching it**,
- its own variables that change meaning: they **will point at nothing** or at the new project's service of that name,
- shared variables of the old project it stops receiving,
- people who lose their access to it: shares on the service itself are removed,
- pending invites that no longer cover it.

Services and names you cannot see are counted, not named. When the list has anything in it, tick **I have read what changes**, then **Move**.

### What happens

- **A running service** switches networks like a deploy, without a rebuild: its running containers join the new project's network, pass their health check there, traffic switches to them, and they leave the old network. On 0.2 agents the containers keep running; older agents start new ones, so databases restart once. The **Deployments** tab shows it as a deployment started by **move**. If the switch fails, the service goes back to the old project, with its shares and invite entries.
- **A stopped or never-deployed service** changes project at once.
- **A Git source on a private address** (or a host allowed in the old project for split-horizon DNS): when an owner or admin moves the service, the move allows its host in the new project, as saving the source there would. A member's move is blocked instead (see below) until an owner or admin allows the host in the new project (**Internal git hosts** in the project's **Settings** tab, or `git.allowInternalHost`; see [Git servers on private addresses](/guides/github-and-git#git-servers-on-private-addresses)).

### What blocks a move

| Blocker | What to do |
| --- | --- |
| A compose stack or one of its members | Not supported yet |
| The panel's own service, or a preview service | Cannot move |
| Open previews | Close them first, or turn previews off |
| The new project already has a service with that name | Rename one of them |
| A deploy is running, or a clone is copying its data | Wait until it ends |
| Its **Git** source is on a host that is internal to the new project and not allowed there, and you are a member | Ask an owner or admin to move it, or to allow the host in the new project first |
| A service of the new project uses its name for more than an address (a password or one of its own variables) | That reference was written while nothing had the name, so nobody checked who may read it. Remove it first. |
| You lack access | See below |

A move needs every action on the service (the new project may give you more than you hold now), permission to create services in the new project, and, like a clone, the right to use its git credential, registry login, GitHub App installation or git provider connection there. The panel answers `403 FORBIDDEN` otherwise.

Through the API, `services.moveProjectImpact` returns the same list as the dialog, and `services.moveProject` needs `confirm: true` when it lists anything (see the [API reference](/api-reference)). AI tools need a person's approval for a move, since others lose access.
