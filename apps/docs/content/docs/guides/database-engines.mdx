How to create, connect, expose, back up and change the version of a database is the same for every engine; see [Databases](/guides/databases). This page is what differs per engine.

<Callout title="New in 0.2">
Postgres 18, pgvector, Valkey, KeyDB, Dragonfly and ClickHouse are available from Seylo 0.2. Valkey, KeyDB, Dragonfly and ClickHouse also need a 0.2 agent on the node: the panel refuses to create, move or clone them onto a node with an older agent, and says the node must be updated first.
</Callout>

## Engines and versions

Every image in Seylo's catalog is pinned to an exact release, so a redeploy runs the same bytes. The newest version is the default.

| Engine | Versions | Image | Port | Web UI | Shell |
| --- | --- | --- | --- | --- | --- |
| PostgreSQL | 18 (new in 0.2), 17, 16, 15 | `postgres` | 5432 | pgweb | `psql` |
| PostgreSQL with pgvector (new in 0.2) | 18, 17, 16, 15 | `pgvector/pgvector` | 5432 | pgweb | `psql` |
| MySQL | 8.4, 8.0 | `mysql` | 3306 | phpMyAdmin | `mysql` |
| MariaDB | 11.8, 11.4, 10.11 | `mariadb` | 3306 | phpMyAdmin | `mariadb` |
| MongoDB | 9.0 (new in 0.2.9), 8.0, 7.0 | `mongo` | 27017 | mongo-express | `mongosh` |
| Redis | 8.2, 7.4 | `redis` | 6379 | Redis Commander | `redis-cli` |
| Valkey (new in 0.2) | 9.1, 9.0, 8.1 | `valkey/valkey` | 6379 | Redis Commander | `valkey-cli` |
| KeyDB (new in 0.2) | 6.3 | `eqalpha/keydb` | 6379 | Redis Commander | `keydb-cli` |
| Dragonfly (new in 0.2) | 2.0 | `ghcr.io/dragonflydb/dragonfly` | 6379 | Redis Commander | `redis-cli` |
| ClickHouse (new in 0.2) | 26.8, 26.3 | `clickhouse/clickhouse-server` | 9000 (native), 8123 (HTTP) | ClickHouse's Play page | `clickhouse-client` |

The **New database** form lists them with their versions, except KeyDB, Dragonfly and ClickHouse, which it does not offer for now (since 0.2.9; existing ones keep working). Through the API, `databases.engines` returns every engine with the exact images (see the [API reference](/api-reference)).

New in 0.2.11: a database can run any other tag or digest of its engine's image instead of the pinned one, with **Use another image** in the **New database** form or on its **Version** card (see [Use another image](/guides/databases#use-another-image)). Such images are not tested by Seylo, and a floating tag such as `latest` can pull another release on the next deploy. Images of other repositories are refused.

## Connection strings

The **Connection** tab shows each part and the full URL, and `${{db.INTERNAL_URL}}` hands it to an app (see [Environment variables](/guides/environment-variables#built-in-variables)). The shapes, for a database service called `db`:

| Engine | Internal URL |
| --- | --- |
| PostgreSQL | `postgresql://postgres:<password>@db:5432/<database>` |
| MySQL, MariaDB | `mysql://root:<password>@db:3306/<database>` |
| MongoDB | `mongodb://root:<password>@db:27017/<database>?authSource=admin` |
| Redis, Valkey, KeyDB, Dragonfly | `redis://default:<password>@db:6379` |
| ClickHouse | `clickhouse://<user>:<password>@db:9000/<database>` |

These are the default main users; a database created through the API or a template may name its own, and since 0.2.13 the **Users** tab can change it (see [Users](#users)). The database name defaults to the service name with `-` turned into `_` (`shop-db` becomes `shop_db`). The Redis-like engines have no database name.

Exposed with TLS, the URL has the same user and password, points at the node's address or the **TLS host name** and adds what the driver needs:

| Engine | Exposed URL |
| --- | --- |
| PostgreSQL | `postgresql://postgres:<password>@<host>:<port>/<database>?sslmode=require` |
| MySQL, MariaDB | `mysql://root:<password>@<host>:<port>/<database>?ssl-mode=REQUIRED` |
| MongoDB | `mongodb://root:<password>@<host>:<port>/<database>?authSource=admin&tls=true`, plus `&tlsAllowInvalidCertificates=true` when no **TLS host name** is set |
| Redis, Valkey, KeyDB, Dragonfly | `rediss://default:<password>@<host>:<port>` |
| ClickHouse | `clickhouse://<user>:<password>@<host>:<port>/<database>?secure=true`, plus `&skip_verify=true` when no **TLS host name** is set |

With a **TLS host name**, the MongoDB and ClickHouse URLs leave that option out, also while the node has no Let's Encrypt certificate for the name yet and serves a self-signed one: add it yourself meanwhile (see [Self-signed certificates](/guides/databases#self-signed-certificates)). With a self-signed certificate, Redis-like clients must skip verification themselves, for example `redis-cli --tls --insecure`. Postgres, MySQL and MariaDB clients that do not ask for TLS are refused (see [Expose with TLS](/guides/databases#expose-with-tls)), and MariaDB 10.11, which has no TLS, cannot be exposed.

## PostgreSQL

- **Postgres 18** is new in 0.2 and the default. Its image keeps the data under `/var/lib/postgresql/18/docker`, so the data volume is mounted at `/var/lib/postgresql`; 15 to 17 keep it at `/var/lib/postgresql/data`. That matters when you browse the volume with **Files**. Since 0.2.11, Seylo sets `PGDATA` to the folder of the data before a database with its volume at `/var/lib/postgresql` changes version, so a version that cannot read it fails instead of starting on an empty database (see [Postgres and PGDATA](/guides/databases#postgres-and-pgdata)).
- **Base system**: the catalog's plain images are Alpine, the pgvector ones Debian trixie. Another base system, such as Debian's `postgres:17.6` on an Alpine database, is a risk you accept on the **Version** card: its C library may sort text in another order, so indexes on text columns may need `REINDEX`.
- **pgvector**: tick **Include pgvector** in the **New database** form. The database runs the `pgvector/pgvector` image of the same major version. The extension is installed but not turned on: run this once in each database that uses it (the **Connection** tab reminds you):

  ```sql
  CREATE EXTENSION vector;
  ```

  The pgvector images are Debian-based and the plain ones Alpine, so their data is not interchangeable: an existing database cannot switch to or from pgvector. Create a new one and restore a dump into it.

## MySQL

- **MySQL 8.4** has the old `mysql_native_password` sign-in method off. Since 0.2.11, before a change from 8.0 to 8.4, Seylo checks the running database for accounts that sign in with it, and changes nothing while there are any, until you switch them to `caching_sha2_password` or keep their logins working in 8.4 (see [MySQL 8.4 and mysql_native_password](/guides/databases#mysql-84-and-mysql_native_password)). MySQL 9 has no `mysql_native_password` at all.

## MongoDB

- **MongoDB 9.0** is new in 0.2.9 and the default. Since 0.2.11, new databases get `mongo:9.0.8`, `mongo:8.0.38` or `mongo:7.0.45`. Existing 9.0 and 8.0 databases keep the image they run until you take the patch update on their **Version** card, which needs no backup. The upgrade from 7.0 to 8.0 to 9.0, backups, the web UI and exposing over TLS ran on these images in Seylo's test setup.
- **MongoDB 7.0** stays on 7.0.45: when 0.2.11 was made, Docker Hub's `mongo:7.0.48` had only a Windows image (its Linux images are under `7.0.48-jammy`), so a node could not pull it. **Use another image** takes `mongo:7.0.48-jammy` as a patch update, like any newer release of 7.0, not tested by Seylo.
- A MongoDB database moves up one version at a time without a risk, 7.0 to 8.0 to 9.0, and Seylo sets the feature compatibility version first (see [MongoDB version changes](/guides/databases#mongodb)). Other moves, such as to `mongo:8.2.12`, are a risk you accept: Seylo runs no compatibility step for them, and MongoDB refuses data whose compatibility version it does not support. 8.2 was MongoDB's short-lived rapid release, which no longer gets fixes.

## Valkey, KeyDB and Dragonfly

They speak the Redis protocol, so Redis clients and drivers work unchanged. Like Redis, each has one user, `default`, with the generated password. Exposing one uses that same user over TLS (`rediss://`); the internal URL stays as it is. The **Users** tab (since 0.2.13) shows only `default` and changes only its password: users made with `ACL SETUSER` live in memory only, since Seylo starts these engines without an ACL file, so the next restart or deploy removes them.

- **Valkey** is a maintained fork of Redis, under the BSD license. It runs with append-only persistence, like Redis.
- **KeyDB** has had no release since 6.3.4 (2023) and gets no security fixes, including the 2025 Redis Lua scripting advisories (CVE-2025-49844 and three more). `databases.engines` says so in its `notice`, and the panel only exposes it to the **Allowed IPs** you list, never to every address. Prefer Valkey for anything new. KeyDB publishes no multi-arch version tag, so it is pinned by digest.
- **Dragonfly** has no append-only file: it saves a snapshot every 5 minutes and when it stops. A crash loses up to the last 5 minutes of writes. Only Dragonfly 2.0 is offered.

## ClickHouse

- The admin user is generated (`ch_` and 10 letters and digits) with full access management, so it can create users and grants with SQL. Since 0.2.13 the **Users** tab makes and changes SQL users too. The admin is the user the container starts with, which ClickHouse makes from its environment at every start, so a new name or password for it restarts the database, and it cannot be swapped for another user.
- Besides the native protocol on port 9000, the HTTP interface on 8123 is available inside the project. Its URL is on the **Connection** tab (**HTTP URL**, **HTTP port**) and in `${{db.INTERNAL_HTTP_URL}}` and `${{db.INTERNAL_HTTP_PORT}}`: `http://<user>:<password>@db:8123/<database>`.
- Only the native port is exposed, with TLS from the node's agent (`clickhouse-client --secure`), and clients sign in there as the admin user. The HTTP port is never exposed, so HTTP clients reach ClickHouse only from the same node.
- The web UI is ClickHouse's own **Play** page, already signed in as the admin. Requests that carry credentials of their own (`user`, `password` or `quota_key` parameters) are refused.

## Users

New in 0.2.13. How the **Users** tab works is the same for every engine; see [Users](/guides/databases#users). What each access level grants:

| Engine | **Read only** | **Read and write** | **Admin of `<database>`** | **Full admin** |
| --- | --- | --- | --- | --- |
| PostgreSQL | `pg_read_all_data` (every table of every database on the server) and `CONNECT` on the database | `pg_read_all_data` and `pg_write_all_data` (every database on the server), `CONNECT`, `CREATE` and `TEMPORARY` on the database, and `USAGE` and `CREATE` on its `public` schema | Not offered | `SUPERUSER`, `CREATEDB`, `CREATEROLE` |
| MySQL, MariaDB | `SELECT` and `SHOW VIEW` on the database | `SELECT`, `INSERT`, `UPDATE`, `DELETE`, `CREATE`, `ALTER`, `INDEX`, `DROP`, `REFERENCES`, temporary tables, `LOCK TABLES`, `EXECUTE`, views and triggers on the database; no `GRANT OPTION`, routines or events | `ALL PRIVILEGES` on the database, `WITH GRANT OPTION` | `ALL PRIVILEGES` on `*.*`, `WITH GRANT OPTION` |
| MongoDB | `read` on the database | `readWrite` on the database | `dbOwner` on the database | `root` on `admin` |
| ClickHouse | `SELECT` and `SHOW` on the database | `SELECT`, `INSERT`, `ALTER`, making tables, views and dictionaries, dropping tables and views, `TRUNCATE`, `OPTIMIZE` and `SHOW` on the database | `ALL` on the database, `WITH GRANT OPTION` | The main user's own rights on everything (`GRANT CURRENT GRANTS ON *.*`, `WITH GRANT OPTION`): the image's user lacks a few rights of `ALL`, so `ALL` would be refused |

`pg_read_all_data` and `pg_write_all_data` came in Postgres 14, so an older Postgres offers **Full admin** only. Redis, Valkey, KeyDB and Dragonfly have no users to make.

The main user and how it changes:

| Engine | Main user by default | A new name | Another user as the main one |
| --- | --- | --- | --- |
| PostgreSQL | `postgres` | Renamed in place, also the image's first user, then a restart so the health check uses it (it can wait) | Yes. The dialog keeps the old main user; the image's first user can never be dropped. |
| MySQL, MariaDB | `root` | Root stays; another main user is renamed in place | Yes, from the accounts with host `%`. Root gets the new main user's password. Deleting the old one removes only `root@%` for root, since `root@localhost` stays for the image. |
| MongoDB | `root` | No rename: use another user | Yes, from the users of the `admin` database. The old one can be deleted. |
| ClickHouse | `ch_` and 10 letters and digits | A restart with the new name | No |
| Redis, Valkey, KeyDB, Dragonfly | `default` | No | No |

A new password for the main user restarts ClickHouse, Dragonfly, Redis, Valkey and KeyDB; the others change it in the running database.

## Tested version changes

New in 0.2.11. Every version change Seylo makes without a risk ran in Seylo's test setup on the catalog's images, the way a node runs it: a new container on the same data volume, with the panel's environment and commands. Each one kept the data:

| Change | What was checked |
| --- | --- |
| MongoDB 7.0 to 8.0 to 9.0 (since 0.2.9) | The data, on 8.0.38 and 9.0.8 since 0.2.11 |
| MariaDB 10.11 to 11.4 (since 0.2.9), and 11.4 to 11.8 | The data, with the system tables upgraded on each start |
| MySQL 8.0 to 8.4 | The upgrade completes; a table, its view and procedure, and the root and app logins work on 8.4. An account made with `mysql_native_password` signs in to 8.4 once old logins are kept on. |
| Redis 7.4 to 8.2 | Both the RDB base file and the append-only file are read, and the TTLs kept |
| Valkey 8.1 to 9.0 to 9.1, and 8.1 straight to 9.1 | The same as for Redis |
| ClickHouse 26.3 to 26.8 | A MergeTree table in two parts, which 26.8 merges, and a user made with SQL |
| PostgreSQL 17 patch update, `17.6-alpine` to `17.11-alpine` | The data, on a newer Alpine too: amcheck finds the text index whole |

Some of the risks ran there too:

- MongoDB 8.0 to `mongo:8.2.12`, a version Seylo does not offer: the data was kept with no compatibility step, since 8.2 opens data whose feature compatibility version is 8.0.
- MongoDB 9.0 set to the 8.0 image: 8.0 refused the 9.0 data, the deploy failed, and the 9.0 container came back with the data.
- PostgreSQL 18 set to 17 (with `PGDATA` set), and 17 set to 18: neither got healthy, and each came back on the version it ran, with its data.

Images you give with **Use another image** are not tested by Seylo.

## Backups and restores

Backups run in a helper container from the database's own image and go straight to your bucket (see [Backups](/guides/backups)):

| Engine | Backup | Restore |
| --- | --- | --- |
| PostgreSQL | `pg_dump` (or `pg_dumpall`) | `pg_restore` or `psql` |
| MySQL, MariaDB | `mysqldump` or `mariadb-dump` | `mysql` |
| MongoDB | `mongodump` | `mongorestore` |
| Redis, Valkey, KeyDB | An RDB snapshot (`redis-cli`, `valkey-cli` or `keydb-cli --rdb`) | The RDB file is swapped in |
| Dragonfly | `SAVE RDB` into its data folder, then streamed out | The RDB file is swapped in |
| ClickHouse | `BACKUP` of every database except the system ones, as a zip in its data folder, then streamed out | `RESTORE`, see below |

New in 0.2.16, on nodes with agent 0.2.16: PostgreSQL, MySQL, MariaDB and MongoDB schedules can back up chosen databases instead of the whole server, or some tables or collections of one database (see [Choose what a database backup holds](/guides/backups#choose-what-a-database-backup-holds)). The backup and restore of a choice:

| Engine | Chosen databases | Some tables or collections | Restore |
| --- | --- | --- | --- |
| PostgreSQL | One `pg_dump` per database; several go into one `.bundle` | `pg_dump` with each table (and its partitions) | `pg_restore --clean --if-exists --single-transaction` per database, which creates a missing database first |
| MySQL, MariaDB | `mysqldump --databases` or `mariadb-dump --databases` | The dump of those tables, which creates the database if it is missing | `mysql` |
| MongoDB | One `mongodump --db` per database; several go into one `.bundle` | `mongodump` without the other collections | `mongorestore --drop` of only those namespaces |

A backup of chosen databases holds no users or roles, so a restore leaves them as they are. Redis, Valkey, KeyDB, Dragonfly and ClickHouse always back up everything. Before each dump the node lists the server with the dump's own helper and sign-in, which also measures what every database backup holds (size and approximate rows per database and table); the MySQL listing works on MySQL 5.7 images too.

A restore of the Redis-like engines also replaces the append-only files. The ones it replaced stay next to them as `<name>.before-restore-<time>`, as one undo; the next restore deletes them.

A ClickHouse restore replaces the databases the backup holds, like `pg_dumpall --clean`:

1. Each of those databases is renamed aside to `<name>__seylo_pre_restore_<time>`.
2. `RESTORE` runs.
3. Once it succeeds, the renamed copies are dropped. If it fails, whatever it created is dropped and the copies get their names back, so the databases are as they were.

While it runs the disk holds both copies. A database that cannot be renamed (one not on ClickHouse's default Atomic engine) stops the restore before anything changes. If putting the copies back fails too (the server went down), they stay under their `__seylo_pre_restore_` names and the restore's error says so. Users and grants in the backup are not restored over existing ones.

## Limits

- Postgres does not upgrade its major version in place, and no Postgres database switches to or from pgvector: create a new database and restore a dump into it. Since 0.2.11 the **Version** card takes a Postgres major as a risk, but it will most likely not start, and the old container comes back.
- Since 0.2.9 the other engines change version on the **Settings** tab. The changes Seylo makes without a risk are in [Change the version](/guides/databases#change-the-version); since 0.2.11 the others go ahead once you accept [what can go wrong](/guides/databases#what-can-go-wrong). Data files do not go back: an older version may not open them, and going back means restoring a backup into a new database.
- A new password for the main user changes it inside the running database, except for ClickHouse and Dragonfly, which read it from their environment when they start. Redis, Valkey and KeyDB take it at once but would start with the old one again. Since 0.2.13 those five restart with the new password, which needs the right to deploy the database (see [The main user's password](/guides/databases#reset-a-password)).
- Exposure on the Redis-like engines, MongoDB and ClickHouse's native port goes through TLS from the node's agent. Postgres, MySQL and MariaDB serve TLS themselves, and need a 0.2.9 agent on the node to be exposed. MariaDB always presents its own self-signed certificate, and MariaDB 10.11 cannot be exposed.
