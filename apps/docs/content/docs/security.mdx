Seylo runs on servers you own. The panel decides what runs where, and an agent on each node, running as root, carries it out. This page describes what that means for each kind of account and credential, what is checked before anything is installed, and where secrets are kept.

To report a vulnerability, see [Report a vulnerability](#report-a-vulnerability).

## Threat model

### Owners and admins

Owners can do everything; admins can do everything except change owners (see [Users and access](/people/users-and-access#roles)). By design, an owner or admin is root on every node: they deploy whatever they like, read every secret in the panel, add and remove nodes, and, once an owner turns it on for a node, open a root shell on that node from the browser.

Treat these accounts like root SSH keys: keep them to a few people and give each one an authenticator app or a passkey (see [Sign-in and security](/people/sign-in-and-security)). The root shell on a node is off until an owner turns it on, needs a sign-in from the last 15 minutes, never works with an API key or an MCP token, and raises a **Security change** alert when one opens.

### Members

A member, shown as a guest on the projects they can reach, sees and does only what was shared with them: whole projects or single services, with the actions picked when sharing. Members never get panel-wide actions (nodes, settings, people, updates), and nobody can share an action they do not hold themselves.

A member who may deploy runs code on the node, but not as root on it: Seylo starts services without privileged mode, host networking, devices, bind mounts or the Docker socket, and ignores those settings in compose files. A member can't put a service on a hostname or path that another service already routes unless they may edit that service too. A git URL does not lead into a node's network either: since 0.2 the node checks the address of every connection git makes and clones from an internal address only for a host an owner or admin allowed in the project, and since 0.2.0-rc.2 the same goes for the node's own addresses, public ones included, so a git URL cannot reach a service the node's firewall hides from the internet (see [Git servers on private addresses](/guides/github-and-git#git-servers-on-private-addresses)).

Services of different projects on one node still share its kernel and Docker. If you do not trust a member that far, keep their projects on a node of their own.

Taking access away takes effect everywhere: since 0.2 that includes a database web UI or a Box the person has open, which closes within about a minute (see [Databases](/guides/databases#web-ui-and-shell)). Since 0.2.0-rc.2, a database web UI also has a login of its own that only the node's edge holds, so code a member deploys on the project network cannot open it and act as the database admin without the right to see the credentials.

### People without an account

From the internet, people reach your services' domains and the ports you open, plus the panel's own pages: sign-in, the owner setup link (one use, one hour), invite links (one use, 1 to 30 days) and, only while the MCP server is on, its OAuth endpoints. Passwords are hashed with argon2id, and repeated wrong passwords or codes slow down and pause sign-in, counted per address (all of an IPv6 /64 counts as one) and per account (see [Sign-in and security](/people/sign-in-and-security#password)).

### API keys, MCP tokens and the assistant

- An [API key](/people/api-keys) acts as the person who made it, narrowed to the actions, projects and read-only setting picked for it. It loses access when that person does, and it can never manage sign-in methods or other keys. A key limited to some projects or actions also stays out of account-wide data, such as the person's assistant chats, their other keys and their security settings. Only a browser session with a recent sign-in can create one. The panel stores only a hash of it.
- The [MCP server](/features/mcp-and-ai) is off until you turn it on. Tokens you create are read-only unless you change that, and the OAuth consent page always starts on **Read only**, whatever the client asked for, and marks the name the client gave itself as not verified. Account security actions are never available to AI tools, and secrets in tool results come back as `[redacted]`.
- Anything that deletes something or can't be undone waits in **Approvals** when an AI tool asks for it, and runs only after a person approves it from a browser session. An API key can deny a request but never approve one.
- The built-in assistant acts with the permissions of the person talking to it, and every change it wants to make waits for approval, not only deletions.

Every action, and every refused attempt, is in **Activity** with the person and the credential behind it.

### A compromised node

Someone with root on a node gets what runs there: its services, their volumes and logs, their environment (including any credentials those services were given for services elsewhere) and the node's own agent key.

They do not get other nodes or the panel's secrets. The panel sends a node only the services placed on it, believes its reports only about those services, lets it pull and push only its own images in the registry, and caps how much it can make the panel hold in memory and store each day. Since 0.2.0-rc.2, nodes never get a backup destination's keys either: the panel signs each request of a running backup or restore for that run's own object, so a node reaches the backups of its own services while they run, not the rest of the bucket. Remove the node on **Nodes**, then change the secrets of the services that ran there. Its load balancing certificate is not revoked: it stays valid until it expires, at most 30 days.

A node with **Build images on this node** on is the exception for builds: it also gets the source, git credentials and build-time variables of every service it builds, from any project, and pushes the images other nodes then run. Treat build nodes like the panel. New in 0.2.0-rc.2: only an owner or admin turns it on, in the panel; a node that joins cannot make itself a build node, apart from the panel's own node from the installer. Each deployment shows which node built it.

The node that runs the panel is the exception: it holds `panel.db` and `master.key`, so taking it over is taking over the panel. Since 0.2.0-rc.2 only root and the panel's own user can read them there (see [On the panel's node](#on-the-panels-node)).

### A compromised panel

The panel tells every agent what to run, and agents run as root. Whoever controls the panel, through its container, its node or an owner or admin account, controls every node and can read every secret. That is why the protections above concentrate on the panel: strong sign-in for owners and admins, a recent sign-in before anything that hands out lasting access, alerts on security changes, and an activity log of everything.

A copy of `panel.db` on its own is much less: the secrets in it are encrypted with `master.key`, and passwords, sessions and keys are only stored as hashes (see [Secrets at rest](#secrets-at-rest)). It still shows everything else, such as names, domains, email addresses and the activity log.

### The network

- **Agents and the panel**: agents dial out to the panel over TLS, checked against the panel domain's public certificate, or against the panel's own key pinned in the join command (`--pin`) while the panel has no domain. Each agent signs every connection with its own Ed25519 key, so a join token is useless after its first use. Since 0.2, each agent also remembers the panel's identity key from its first connect and refuses any other panel, even one with a valid certificate for the panel's domain (see [The panel's identity](/guides/adding-nodes#the-panels-identity)). `--insecure` gives up the TLS checks and is meant for test setups only. See [Adding nodes](/guides/adding-nodes).
- **Between nodes**: load balancing traffic on port 5757 is mutual TLS with certificates from the panel's own CA, valid for 30 days since 0.2.0-rc.2 (a year before). A node without its certificate answers 404 there to everyone (see [Load balancing](/guides/load-balancing)).
- **Your browser and the panel**: plain HTTP until the panel has a domain, see below. A session needs both its HttpOnly cookie and a session key that the web app keeps for the panel's own address and port, so a copy of the cookie that a browser sends to another port of the same address signs nobody in (see [Sessions](/people/sign-in-and-security#sessions)).
- **Behind Cloudflare**: the panel takes the visitor's address from Cloudflare's header only from trusted proxies, see [The panel behind Cloudflare](/guides/domains-and-https#the-panel-behind-cloudflare).

<Callout type="warn" title="Set a panel domain before you invite people">
Until the panel has a domain, it answers on `http://<server-ip>:3000`: the setup link, your password and your session cross the network unencrypted, readable by anyone on the path. Browsers also send a cookie of `http://<server-ip>` to every port of that address, so a service a member runs on `http://<server-ip>:<port>` receives your session cookie; since 0.2 that copy alone signs nobody in, but the network path still sees everything. Give the panel a domain (**Settings → General → Panel domain**) before you invite anyone. Until then, reach the panel through an SSH tunnel, `ssh -L 3000:127.0.0.1:3000 root@<server-ip>`, and open `http://localhost:3000` instead. New in 0.2: every page the panel serves over plain HTTP says **This connection is not encrypted** and shows that command.
</Callout>

## Signed releases

Every [release](https://github.com/Seylo-dev/App/releases) is signed with the project's [minisign](https://jedisct1.github.io/minisign/) key. Its public half is:

```text
RWTwvrETQsecIkFOCm1ceiZwfxVq6sFfiEmJfWnUVv7UBIn0jWm2h1ip
```

It is the `minisignPublicKey` in `brand/brand.json` of the [app repo](https://github.com/Seylo-dev/App) and is compiled into the panel, the agent and the installer. The private half is kept offline by the maintainers and, on GitHub, only in the app repo's `release` environment: only the job that signs a release can read it, after a maintainer approves that run. The job that builds the release, and runs its npm build scripts, never sees it. Each release carries:

| File | What it is |
| --- | --- |
| `manifest.json` and `manifest.json.minisig` | The release manifest and its signature. It pins the panel image by digest, and the agent binaries and `install.sh` by SHA-256 and size. |
| `checksums.txt` and `checksums.txt.minisig` | The SHA-256 of every file in the release, and its signature |

The panel checks the manifest's signature before it offers an update, and each agent checks it again before it installs anything; see [Updates](/self-hosting/updates#signed-releases).

### Check a download by hand

With minisign installed (`brew install minisign`, `apt install minisign`, `dnf install minisign` or `scoop install minisign`), download `checksums.txt` and its signature from the same release as your files, then check both:

```bash
BASE=https://github.com/Seylo-dev/App/releases/latest/download
curl -fsSL -O "$BASE/checksums.txt" -O "$BASE/checksums.txt.minisig"

minisign -Vm checksums.txt -P RWTwvrETQsecIkFOCm1ceiZwfxVq6sFfiEmJfWnUVv7UBIn0jWm2h1ip
sha256sum -c --ignore-missing checksums.txt              # Linux
shasum -a 256 -c --ignore-missing checksums.txt          # macOS
```

minisign prints `Signature and comment signature verified` and a trusted comment with the version, such as `seylo 0.1.1 checksums.txt`. The checksum command prints `<file>: OK` for each file of the release in the folder. Anything else means the file is not the one that was released: do not run it.

The same works for the installer: save it with `curl -fsSLo install.sh https://install.seylo.dev` next to `checksums.txt`, check it as above, read it if you like, and run it with `sudo sh install.sh`.

## What the installer checks

`curl -fsSL https://install.seylo.dev | sudo sh` runs the installer as root before it can check anything itself, so the script is checked twice: by the site before it is served, and by the script before it installs.

**install.seylo.dev** serves the `install.sh` of the latest stable release (never a pre-release) only once that release checks out:

1. It resolves the latest release to its tag once and downloads `manifest.json`, `manifest.json.minisig` and `install.sh` from that tag, so the three always come from one release.
2. The manifest's signature must verify with the release key above.
3. The manifest's version must be the release's, and the SHA-256 of `install.sh` must be the one the manifest names.

If any of it fails, for example because a file in the release was replaced without the release key, it keeps serving the last installer that passed and reports the failure on its health check. Its answers carry `X-Installer-Version` and `X-Installer-Sha256`.

Join commands from **Add node** pipe the same checked installer from install.seylo.dev, never a file straight from the release assets. A released panel adds `--version` with its own release, and the installer then checks that release's signed manifest and installs its agent, so the node gets the panel's version (see [Join a server](/guides/adding-nodes#join-a-server)).

**install.sh** then, before it changes anything:

- checks the system and that the ports it needs are free,
- downloads the release manifest and checks its signature with minisign or OpenSSL 3, and stops if the signature is wrong or neither tool is installed,
- stops if the manifest names another version than the one asked for with `--version`,
- stops if the node's agent, or the panel on its node, runs a newer release than the one it would install, unless you add `--downgrade` (new in 0.2.0-rc.2),
- downloads the `seylo` binary, checks its SHA-256 against the signed manifest and that it runs, and only then installs it,
- starts the panel from the image pinned by the digest in the signed manifest, never by a tag alone (unless you name another image with `--image`).

`--allow-unsigned` skips the signature check, with a warning, for development builds that have no release key. All options are in [Installation](/installation#installer-options), and `--dry-run` prints what would happen without changing anything.

## Secrets at rest

### On the panel's node

The folder `/var/lib/seylo/panel/` is mode 0700 and belongs to the panel's user, uid and gid 61000, which no login user has, so only root and the panel container can read it. New in 0.2.0-rc.2: before, the panel ran as uid 1000, which on most cloud images is the default login user (`ubuntu`, `debian`, `ec2-user`), and that user could read `master.key` without sudo. The agent gives the folder to the panel's user the first time it starts the panel after its update. A new panel install warns when an account on the server already has uid or gid 61000.

| File | What it holds |
| --- | --- |
| `/var/lib/seylo/panel/master.key` | 32 random bytes made at install, mode 0600, outside the database |
| `/var/lib/seylo/panel/panel.db` | Everything the panel knows, with its secrets sealed by `master.key` |
| `/var/lib/seylo/panel/agent-tls.key` | The key agents pin while the panel has no domain, mode 0600. Not sealed, so a copy of the folder holds it too. |

Secrets are sealed with AES-256-GCM, with a separate key derived from `master.key` (HKDF) for each kind of secret, so a value sealed as one kind can't be opened as another. Sealed in `panel.db`:

- environment variables of projects, services and deployments, compose files and file mounts,
- Git, GitHub and registry credentials and webhook secrets,
- backup destinations, notification channels, custom certificates' private keys and Cloudflare tunnel tokens,
- authenticator app secrets, the assistant's Anthropic API key and the input of actions waiting for approval,
- the panel's identity key, which signs database web UI and Box tickets and proves the panel to its nodes, and the load balancer CA's key.

Not stored at all, only as hashes: passwords (argon2id), session tokens and session keys, API keys, MCP tokens and the passwords of basic auth rules.

So a copy of `panel.db` alone holds no secrets, and `master.key` alone is useless. Together they are every secret the panel knows: back them up, but keep the copies apart (see [Backing up the panel](/self-hosting/backups)). If a copy leaked, run `sudo seylo panel rotate-key --new-panel-identity` on the panel's node: it gives the panel a new `master.key`, seals every secret again, and replaces the identity keys and `agent-tls.key`, then prints the `seylo join` command with the new pin for each node. With `--keep-panel-identity`, when only `master.key` leaked, nodes keep working. See [If a copy leaked](/self-hosting/backups#if-a-copy-leaked).

### On every node

| File | What it holds |
| --- | --- |
| `/var/lib/seylo/agent.key` | The node's Ed25519 private key, mode 0600 |
| `/var/lib/seylo/config.yml` | The panel's address and certificate pin and, since 0.2, the panel's id and identity key, mode 0600 |
| `/var/lib/seylo/state/` | The last desired state from the panel, mode 0600. It includes the environment of the node's services, so the node can restart them while the panel is down. |
| `/var/lib/seylo/services/<id>/` | Volumes and file mounts, as your services wrote them. Seylo does not encrypt them. New in 0.2.0-rc.2: `services/` and each service's folder are mode 0700, so other accounts on the server cannot read file mounts or volume data; the **Service folders** node health check warns when one is open. |

## Telemetry and reports

Telemetry is off until an owner or admin turns it on, and then sends one small anonymous report a day; see [Telemetry](/self-hosting/telemetry). A `seylo troubleshoot` report is redacted on the node before upload, checked again for anything that looks like a secret when it arrives, and deleted after 30 days; see [Troubleshooting](/troubleshooting).

## Report a vulnerability

Report it privately through GitHub: on [Seylo-dev/App](https://github.com/Seylo-dev/App), open the **Security** tab and use **Report a vulnerability** ([direct link](https://github.com/Seylo-dev/App/security/advisories/new)). If that does not work for you, email [security@seylo.dev](mailto:security@seylo.dev). Please do not open a public issue, pull request or discussion for it.

Include what an attacker can do and what they need first (no account, a member or admin account, an API or MCP key, control of a node, a position on the network), the version (`seylo version` on a node, or **Settings → Updates**), and the steps to reproduce. We reply on the advisory, work out the fix with you there, and publish the advisory with the release that fixes it. Tell us if you want to be credited.

Only the latest release gets security fixes; the panel updates itself and every node from **Settings → Updates**. In scope: the `seylo` binary (agent and command line), the panel and its web app, the installer and install.seylo.dev, which serves it, release signing and updates, and the templates. Out of scope: the apps you deploy with Seylo and the third-party images templates use; report those to their projects.
